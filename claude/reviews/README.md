# AI 代码审计区

评审 AI 的输出目录。流程：写代码 AI 改完 → 评审 AI 出报告 → 用户让写代码 AI 去看 → 写代码 AI 自主抉择采纳 → 处理完由写代码 AI 归档。

## 报告生命周期

- 新报告命名 `YYYY-MM-DD-主题.md`，即"未完成"状态。
- 写代码的 AI 被要求查看时，**只读最近一份未加 `Done-` 前缀的报告**，不通读历史。
- 报告里的建议是参考，不是必办项；写代码 AI 自主判断哪些该做、哪些跳过。
- 处理完后，**由写代码的 AI**（不是评审 AI）把文件改名加 `Done-` 前缀（如 `Done-2026-07-21-xxx.md`）、在文件开头加一行"已完成，仅存档，无需继续阅读"，并**移入 `archive/` 子目录**。加前缀与归档这一步只有写代码 AI 能做，评审 AI 不得预先标记。
- `reviews/` 根目录只保留未完成报告；`archive/` 内的 `Done-` 报告仅作历史记录，不再进入日常阅读，避免搜索过多文件产生幻觉。
- 该约定与 `DOC/DailyPlan/`（完成计划移入 `DailyPlan/archive/` 并加 `Done-` 前缀）保持一致。

## 写报告规则（评审 AI）

- 文件头注明：审计日期、被审代码的 git 基线（提交哈希+时间；新代码通常未提交，取上一版本）。
- 措辞面向 AI：简洁、一针见血、不写客套。按"阻塞交付 / 高回报 / 可延后"分优先级。
- 无问题就直说，不凑数。目标是保证可行性、可维护性、可扩展性。
- 三周单机 Demo、无网络同步，不套大型项目冗余分层；参考经验见 `references/`。

## 目录

- `references/` — 优秀项目（Lyra / ue5-warrior）架构经验，按三周单机 Demo 规模裁剪。
- `archive/` — 已完成（`Done-`）审计报告归档，不进入日常阅读，仅供追溯。
