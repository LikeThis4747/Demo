## 一、阻塞交付

### B1. Heavy 抢占 Light 时未规定恢复移动速度快照 → 角色永久不能移动

**证据（现有代码）**

`Source/Demo/Private/Components/Physics/HeavyImpactResponseComponent.cpp`：

```
642:	Movement->StopMovementImmediately();
643:	Movement->DisableMovement();
```

`EnterPrepared` 全程不读写 `MaxWalkSpeed`；恢复路径（约 2002-2013行）用 `StopMovementImmediately()` + `SetDefaultMovementMode()` / `SetMovementMode(MOVE_Falling)`，同样不碰 `MaxWalkSpeed`。即 **Heavy 组件对 `MaxWalkSpeed` 完全无感知**。

**方案缺口**

- 第 5 节：`Heavy 进入 Prepared → 立即清除 → Inactive`
- 第 6 节：`原子清除 Active Light、动画与 Pending Request/Timer`
- 第 12 节测试第 5 条：`清Active Light、Active Montage、PendingRequest 与 PendingTimer`

三处都把抢占定义为"清除状态"，**没有任何一处要求回滚 `MaxWalkSpeed` 快照**。

**后果**

Light 处于 `Stop`（`MaxWalkSpeed = 0`）时被摆锤/冲锤命中 → Light 状态被清除但速度值仍是 0 → Heavy 起身完成后 `SetDefaultMovementMode()` 不修复 `MaxWalkSpeed` → 玩家或追猎者永久 0 速。这条正好命中方案自己的现场验收第 5 项（"起身后没有残留减速"），但实现契约里没有对应动作，靠验收兜不住。

**修法**

把"清除 Light"显式定义为两步：**先按第 7 节恢复规则回滚速度快照，再清状态/动画/Timer**。好消息是这一步是安全的——Heavy 不改 `MaxWalkSpeed`，所以在 Prepared 时刻当前值必然仍等于本组件最后写入值，第 7 节的"值未被第三方改写才恢复"判据成立。同时把测试第 5 条补上"速度已回到 Light 之前的基线"这一断言。

### B2. 玩家轻受击动画的骨架链前提不成立，需实证后再决定是否纳入第一版

**官方 MCP 回读结果**

| 对象 | 实测值 |
|---|---|
| 玩家 Mesh（`BP_ZeroEscapeCharacter` 依赖） | `SK_SciFITrooper_Man_03` |
| 该 Mesh 的 Skeleton | `CH_SciFiTrooper_Man_03_Skeleton`（76 骨骼） |
| 玩家 AnimBP `ABP_Player_Unarmed_HeavyImpact` TargetSkeleton | `SK_Mannequin` |
| `CH_SciFiTrooper_Man_03_Skeleton.CompatibleSkeletons` | `[]` |
| `SK_Mannequin.CompatibleSkeletons` | `[]` |
| `MM_HitReact_Front_Lgt_01` Skeleton | `SK_Mannequin` |
| `MM_HitReact_Front_Lgt_01` 其他属性 | `AdditiveAnimType=AAT_LocalSpaceBase`、`RefPoseType=ABPT_LocalAnimFrame`、`RefPoseSeq=None`、`bEnableRootMotion=false`、长度 0.7s |

**方案第 8 节的推理断了一环**

方案写"这些 Sequence 与玩家 AnimBP 都使用 `SK_Mannequin` 目标 Skeleton，因此无需新建重定向资产"。这只证明了 **Sequence 与 AnimBP 两者一致**，跳过了"AnimBP 目标骨架与实际 Mesh 骨架是否一致"这一环——而这一环实测为**不一致，且两侧都没有兼容声明**。

方案后半句"实际玩家 Mesh 是另一套 SciFiTrooper Skeleton……必须保留现场验收，不能宣称零风险"方向是对的，但把风险归类为"骨骼错位、脚底滑动"这种调参级问题，**低估了量级**。

**三重风险叠加**

1. **骨架链不一致**：AnimBP 目标骨架与Mesh 骨架是两个无兼容声明的独立 Skeleton 资产。Montage 播放要过 Skeleton 校验，这一环必须先实证澄清。
2. **additive 跨骨架**：`AAT_LocalSpaceBase` 是**骨骼局部空间增量**。非 additive 动画跨骨架按骨骼名映射，表现为"动作略有差异"，可接受（现有 locomotion/Heavy 已验收）；而局部增量旋转叠到参考朝向不同的骨架上，表现是**肢体朝错误方向扭转**，不是调参能救的。
3. **additive 基准不同源**：`RefPoseType=ABPT_LocalAnimFrame` 且资产位于 `Anims/`**`Rifle`**`/HitReact/`，即基准姿态是**持枪** idle。叠到 Unarmed locomotion 上，即使骨架完全相同，上半身也会带持枪姿态偏移。

**对照：追猎者侧完全没有这些问题**

| 对象 | 实测值 |
|---|---|
| 追猎者 Mesh | `SK_Sci_Fi_Character_08_Full_01` |
| 该 Mesh 的 Skeleton | `UE4_Mannequin_Skeleton`（68 骨骼） |
| `ABP_Pursuer_Locomotion` TargetSkeleton | `UE4_Mannequin_Skeleton` |
| `MM_SciFi_Character_08_standing_react_large_gut` | Skeleton `UE4_Mannequin_Skeleton`、`AAT_None`、无 Root Motion、长度 1.6s |

**Mesh / AnimBP / 动画三方骨架一致，非 additive** → 追猎者侧动画方案可直接做，无骨架风险。

**所以方案"两边同构处理"的简化在玩家侧不成立。** 第 4.4 节"两边都由组件在已有 `DefaultSlot` 上创建 Dynamic Montage；不同时支持 Sequence/Montage 两套互斥分支"这个统一决策，恰好踩在两侧唯一的实质差异上。

**修法（按成本从低到高）**

1. 第一版玩家侧 `DA_PlayerStandingImpact` 的 `FrontReaction` **留空**，走方案已有的"资产缺失回退"路径。玩家 `Stop`/`Slow` 的验收只依赖移动锁定与输入锁定——这已经足够证明玩法闭环，第 12 节现场 A/B 第 2 项本来也没依赖动画。
2. 想保留玩家动画，就先做一次独立实证（Persona 里把这条 additive 预览到 `SK_SciFITrooper_Man_03` 上，或PIE 里手动播一次），确认能播且姿态可用，再决定是否写进 DataAsset。这是几分钟的事，但决定几百行代码要不要写。
3. 第 12 节现场 A/B 第 4 项（"动画开/关对比必须一眼可见"）对玩家侧改成可选，不作为第一版验收门槛。

## 二、高回报

### H3. Light 窗口上限用尽后没有冷却，`MaxContinuousLightSeconds` 实际可被绕过

方案第 5 节规定"首次接受时记 `LightWindowStartTime`，后续刷新后的结束时间不得超过 `LightWindowStartTime + MaxContinuousLightSeconds`"，但**没有规定窗口结束后的最小重触发间隔**。

地刺每个危险相位提交一次新 `ImpactId`（`SpikeTrapHazard.h`：`RiseDuration=0.4`、`ExtendedDuration=1.5`、`HiddenDuration=2.0` 循环重复结算），Light 窗口一结束，下一次命中立刻重置 `LightWindowStartTime` 开新窗口 → 玩家可被连续 `Stop` 锁死，硬上限形同虚设。

**修法**：给 `UCharacterImpactTuningData` 加"窗口用尽后的最小冷却秒数"，冷却期内拒绝同来源轻受击并记录原因；补一条对应测试。ProcHitReact 的 Cooldown 就是解这个问题的。

### H4. AI 的 `Stop` 只压速度不取消路径跟随，会留下零进度 MoveRequest

`PursuerAIController` 关闭了 Tick（`PrimaryActorTick.bCanEverTick = false`），全靠 `ThinkInterval`（默认 0.2s）Timer；`Think()` 现有处理是：

```
67:	if (Pursuer->IsReacting())
68:	{
69:		StopMovement();
70:		return;
71:	}
```

方案第 7 节给 `Stop` 的手段是 `StopMovementImmediately()` + `MaxWalkSpeed = 0`，两者都在 CharacterMovement 层，**不取消 AIController 的路径跟随请求**。`MoveToActor` 仍 active 且零进度，容易触发 PathFollowing 的卡住/超时判定，恢复后行为不可预期。

**修法**：AI 的 `Stop` 必须由控制器侧 `StopMovement()` 配合。这与方案已要求的"分别暴露移动阻止/攻击抑制两个查询"是同一处改动，只需写明"`Stop` 必须取消路径跟随，不能只靠速度为 0；`Slow` 反之绝不能调 `StopMovement()`"。

附带：Light 结束后 AI 最多 0.2s 才恢复移动请求，属可接受延迟，但要写进验收项 3 的预期，别当bug 查。

### H5. `UMagneticObjectComponent` 从纯配置组件升级为事务 Owner，契约与代码量都要重估

现状（`MagneticObjectComponent.h` 全文52 行）：`final`、Tick 未开、**无 `BeginPlay`/`EndPlay`**、无任何运行时成员，只有 `bMagnetizable` / `SelectionPriority` / `ThrowSpeedMultiplier` 三个配置字段。文件头明确写着：

> 边界：不保存玩家全局抓取手感、不控制 Chaos 刚体，也不持有抓取状态。
> 状态 Owner：本组件只拥有道具身份配置。

方案要它承载：根 Primitive 的 Hit Delegate 生命周期、攻击有效期 Timer、完整碰撞快照（`CollisionProfileName` / `CollisionEnabled` / `ObjectType` / 完整 `ResponseContainer` / CCD / Hit 通知）、`ImpactId`、专用通道切换、消费者登记引用计数、幂等 Disarm。

两点必须落实：

1. **同步重写该文件头的职责/边界/状态 Owner 三行声明**，否则文档与实现漂移（这是项目既有约定）。
2. **第 11 节"磁力投掷来源与碰撞生命周期 220～360 行"偏低**。对照 Heavy 侧做同类事情的量：`FHeavyImpactRecoveryBaseline`（`.h` 74-97 行）+ `CapturePreContactState` / `RestoreBodyBaseline` / `RestoreCharacterShell` / `RestoreSnapshotAfterFalsePositive` 一整套快照回滚。磁力这套还多一层"两个消费者的引用计数"，建议上调估算。

### H6. 重新抓取时 Disarm 的时序要求要写得比"再交给 PhysicsHandle"更精确

`ElectromagneticGrabComponent.cpp`的 `GrabCandidate` 在**函数开头**就快照：

```
400:	HeldComponent = CandidateComponent;
401:	HeldMagneticObject = MagneticObject;
402:	PreviousAngularDamping = CandidateComponent->GetAngularDamping();
403:	PreviousPawnCollisionResponse = CandidateComponent->GetCollisionResponseToChannel(ECC_Pawn);
404:	PreviousCameraCollisionResponse = CandidateComponent->GetCollisionResponseToChannel(ECC_Camera);
```

`PhysicsHandle->GrabComponentAtLocation` 在第 413 行才调用。

方案第 9 节写"`GrabCandidate` 先调用唯一事务的 Disarm/恢复，**再交给 PhysicsHandle**"。若按字面理解为"在 `GrabComponentAtLocation` 之前"，仍会把 Armed 状态（Pawn=Block、ObjectType=`AttackProjectileBody`）当作"原始值"快照下来，之后 `ReleaseHeldObject` 把它"恢复"成攻击态，物体永久 Block Pawn。

**修法**：措辞改为"必须在 `GrabCandidate` 快照任何碰撞/阻尼字段**之前**完成 Disarm"。

### H7. 现有 AttackProjectile Tag Timer 用局部 `FTimerHandle`，迁移时一并修掉

```
163:				FTimerHandle ClearTagHandle;
164:				World->GetTimerManager().SetTimer(
```

`ClearTagHandle` 是**函数局部变量**，handle 出栈即丢，Timer 无法取消。连投两次或投掷后立即重新抓取，Tag 移除时机不可控。

方案已要求把这个 Timer 迁到磁力物事务且"不能保留第二个 Timer"，方向正确。补充两点：新事务要用**成员** `FTimerHandle`；在实施记录里注明这同时修复了一个既存缺陷（不是本方案引入的）。

### H8. `FindBestCandidate` 的对象查询是单通道构造

```
303:	const FCollisionObjectQueryParams ObjectQueryParams(ECC_PhysicsBody);
```

方案要求同时查 `PhysicsBody + AttackProjectileBody`，实施时需改为构造后 `AddObjectTypesToQuery` 两次。顺带确认：`CanGrab` 仍要求刚体在模拟物理，Armed 物体满足该条件，不会因通道切换被误排除。

### H9. 接收者类别存在双来源，缺单一权威

方案 4.4 让 `UCharacterImpactTuningData` 带 `ReceiverCategory` 字段，第 5 节又说组件拥有"接收者类别与角色侧轻受击调参资产"。把`DA_PlayerStandingImpact` 误装到追猎者身上时，谁是权威没有规定——这正是方案自己在 4.1 节强调的"没有专用栏的角色应拒绝请求并记录原因，不静默猜测"想避免的情况。

**修法**：二选一并写死。要么类别只从 TuningData 读、组件不再独立配；要么组件配类别、TuningData 的字段仅用于启动期校验，不一致就报错并停用轻受击。

### H10. 第 12 节 15 条自动化测试里有 4～5 条做不成单元测试

现有先例 `Source/Demo/Private/Physics/Tests/HeavyImpactResponseTests.cpp` 文件头写明：

> 边界：只构造瞬态 `World`、`Actor`、组件和 PCA 数据，**不依赖项目资产或真实 Chaos 求解**。

其`FScopedTestWorld` 用 `UWorld::CreateWorld(EWorldType::Game, false)`，**没有物理步进**。因此方案测试第 9、12、13、15 条（依赖真实 Chaos 阻挡命中、Arm/Disarm 全路径实测、CCD 生效、通道响应实测）在这种环境里无法产生真实 `OnComponentHit`，硬写只会得到验证 mock 的空壳测试。

可保留为自动化的：1、2、3、4、5、6、7、8、11（第 11 条读配置即可）、14。
建议移到 PIE 现场验收的：9、12、13、15。

这会让第 11 节"自动化测试 250～350 行"的估算更准，建议在写 DailyPlan 前重排工作量。

## 三、可延后

### L11. `bIsReacting` 已是死字段，拆分查询时别带进新语义

`APursuerCharacter::IsReacting()` = `bIsReacting || HeavyImpactResponse->IsBusy()`；而 `HandleHitReact`（唯一置位方）只被 `PhysicsControlHitResponseComponent` 触发，该组件按 `PursuerCharacter.h:78-80` 注释"重冲击原型期间不创建、不配置也不解引用" → **`bIsReacting` 恒为 false**。方案保留旧路径没问题，但拆分"移动阻止/攻击抑制"两个查询时要明确新查询不读这个死字段，否则会留下看似有效实则永假的分支。

### L12. `CanAcceptBodyInput()` 是单一闸门，Slow/Stop 差异需参数化

`ZeroEscapeCharacter.cpp`：`Move`(231)、`TryJump`(253)、`BeginMagneticGrab`(270)、`ThrowMagneticObject`(288) 都走 `CanAcceptBodyInput()`；`Look`(260) 与 `EndMagneticGrab`(277) **不走**。

好消息：方案要求的"`Stop` 保留相机与松手释放"与现有结构天然吻合，这两条路径不用改。
需注意：`Slow` 必须保留移动/跳跃/抓取，所以**不能**把"Light 活动"整体塞进 `CanAcceptBodyInput()`，只能让 `Stop` 进入该闸门。

### L13. 讨论稿代码片段缺 `UPROPERTY`

4.2 / 4.3 / 4.4 的结构体与 DataAsset 成员都没写 `UPROPERTY`。DataAsset 需要 `EditAnywhere` 才能在编辑器里填值；`TObjectPtr<UAnimSequenceBase>` 作为 `UPROPERTY` 成员必须`#include` 完整头文件而非前向声明——这是项目已踩过两次的坑（报错特征为"数组的大小必须大于零"）。属讨论稿简写，实施时按既有规范补齐即可。

### L14. 通道注册：方案的验证要求已足够，补一条机制说明

核实结果：`Config/DefaultEngine.ini` 中**完全没有** `[/Script/Engine.CollisionProfile]` 段，也没有任何 `GameTraceChannel` 定义 → 方案说 `ECC_GameTraceChannel1` 是首个未占用通道，**核实为真**。

方案已要求"新增通道后必须重启 Editor，再通过官方 MCP 回读玩家/追猎者 Capsule、两者 Mesh 与磁性物体的实际通道响应"，这条足够。补一句机制说明：`DefaultResponse=ECR_Block` 会成为所有未显式列出该通道的 Profile 的默认响应，因此"两个角色 Capsule 阻挡"通常无需逐 Profile 额外配置——但仍按方案要求回读确认，不要凭这一点跳过验证。
