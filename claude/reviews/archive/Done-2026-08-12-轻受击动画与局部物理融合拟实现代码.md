- P1-5：命中只映射到躯干、左上臂、右上臂三个配置 Body；手、头等末端命中上溯，不直接承受同一标量冲量。
- P1-6：官方 MCP 已确认追猎者 Mesh 为 `CharacterMesh / QueryOnly / ECC_Pawn`。拟实现稿已明确降级为局部骨骼物理表现，不再声称来源物体会被手臂真实阻挡或发生完整双向动量交换；本轮不修改 Mesh 碰撞。
- P1-7：增加 `MaxContinuousPhysicalSeconds`。
- P1-8：构造期使用 `PrimaryComponentTick.bStartWithTickEnabled=false`；Configure 成功后有意保持 Physical Animation 的 PrePhysics Tick，以更新预建 drive 的动画目标。
- 测试清单：自动化只保留数据合同；真实 Body、Tick、Heavy 抢占、性能和画面均移到 PIE/MCP 验收。

### 部分采纳

- B2 的引擎语义核对正确：`MaxAngularForce=0` 表示不限制，而不是无力。项目仍要求有限正值，避免无限角力把上半身焊成刚体墙；字段注释会明确这是项目安全约束，而非 UE 通用规则。

## 零、先撤回两处错误论证

本节只为防止写代码 AI 被前序对话误导。审计过程中我有两处结论下得比证据早，已核实为错误，**不要采纳**：

1. ~~"角色站在任何重机关的准备体积里，Light 物理每帧被清"~~ —— 错。`PreparationVolume` 是 `SetupAttachment(BobBody)` 的球，随锤头摆动，半径 = 锤头对角线 + `PreparationLookAheadDistance`（默认 500cm）。"在体积内"确实约等于"锤头此刻扫到身边"，不是房间级静态区域。
2. ~~"ETA 太早时机关每帧调 Prepare、Heavy 返回 too early、abort 被白调"~~ —— 错。三个机关**都**在 `BuildPreparationRequest` 内部先做了 ETA 上限过滤，返回 false 就 `continue`，根本不调接口：
   - `PendulumHazard.cpp:541-545`、`BatteringRamHazard.cpp:374-378`、`ThrustGuidedHazardProjectile.cpp:625-629`
   - 三处用同一套帧感知公式（`max(资产值, min(0.5s, 2.5*dt))`）
   - 摆锤资产默认 `MaximumPreparationLeadTime = 0.16f` < Heavy `MaximumPreparationSeconds = 0.18f`，字段注释已明确要求"资产值仍应位于接收端正常窗口内"

原 P0-1 因此**降级为 P1-1**，论据替换为下文两条实测路径。用户对"这是小概率事件吗"的质疑在这两点上是对的。

## 一、阻塞级（落盘前必改）

### B1 首次命中时 PhysAnim 驱动约束还不存在，`SetStrengthMultiplyer(1)` 是静默空操作

`ApplyPhysicalAnimationSettingsBelow` 只写 `DriveData` 并置延迟标志，真正建关节要等组件自己 tick：

```cpp
// Engine/Private/PhysicsEngine/PhysicalAnimationComponent.cpp:388-395
void UPhysicalAnimationComponent::UpdatePhysicsEngine()
{
    if (SkeletalMeshComponent) { SkeletalMeshComponent->WakeAllRigidBodies(); }
    bPhysicsEngineNeedsUpdating = true; //must defer until tick so that animation can finish
}
```

`SetStrengthMultiplyer` 只遍历已存在的 `RuntimeInstanceData`（同文件 489-503 行），约束为空时什么都不做。拟稿 §5.4 的首次命中顺序是"开模拟 + blend=1 + 加冲量"，但**没有任何马达**，要等下一帧 `TG_PrePhysics` 才建 drive。

- 磁力箱走 `OnHit`（物理步后派发），下一帧 PrePhysics 能补上，通常不炸；
- 地刺走 Overlap/Timer，可能落在 PhysAnim 本帧 tick 之后 → **一帧无驱动的上半身自由布娃娃**，正好命中拟稿自己的止损条件"上半身出现尸体感"。

**改法**：`Configure`（或确认 Mesh Bodies 已初始化后的 BeginPlay）就调用一次 `ApplyPhysicalAnimationSettingsBelow(Root, Settings)` + `SetStrengthMultiplyer(0)`，并让 PhysAnim 常驻 tick 完成 `UpdatePhysicsEngineImp`。命中时只做 `SetStrengthMultiplyer(1)` + 开模拟 + blend + 冲量。首次与后续行为一致，且去掉对 tick 顺序的隐式依赖。

引擎注释 "assumes constraints can only be added and not removed"，drive 常驻不会被 `Deactivate` 销毁（只有 `SetSkeletalMeshComponent` / `BeginDestroy` 才 `ReleasePhysicsEngine`），常驻安全。

顺带：`UpdatePhysicsEngine` 内部已 `WakeAllRigidBodies()`，§5.4 那次 `Mesh->WakeAllRigidBodies()` 是多余的，且范围是全身（含下半身运动学 body），删掉。

### B2 `MaxAngularForce <= 0` 判为非法是错的：0 在 Chaos 里表示"不限制"

```cpp
// Chaos/Private/Chaos/Joint/PBDJointCachedSolverGaussSeidel.cpp:2997-3005
void FAxisConstraintDatas::SetMaxForce(const int32 ConstraintIndex, const FReal InMaxForce, const FReal Dt)
{
    // We use 0 to disable max force clamping. See ApplyMaxLambda
    ConstraintMaxLambda[ConstraintIndex] = 0;
    if ((InMaxForce > 0) && (InMaxForce < UE_MAX_FLT))
```

`FPhysicalAnimationData::MaxAngularForce` 默认就是 0，官方 Physical Animation Profile 常见配置也是 0。拟稿 §4 的校验会把引擎默认值判成"参数无效"并静默关掉整个物理层。

**改法**：改成 `MaxAngularForce < 0` 才非法。若项目坚持要有限上限，必须在 DataAsset 注释里写明"0 = 不限制，本项目故意禁用"，否则后人会以为 0 = 无力。

同一处另外两个必须加注释的死参数（不改逻辑，只防误调）：

- `bIsLocalSimulation=true` 时引擎强制 `SetLinearDriveParams(0,0,0)`（`PhysicalAnimationComponent.cpp:374-385`），因此 `PositionStrength` / `VelocityStrength` / `MaxLinearForce` 在本方案里**完全无效**。
- `FPhysicalAnimationData::BodyName` 会被 `ApplyPhysicalAnimationSettingsBelow` 逐 body 覆写（同文件 109 行 `UpdateAnimationData->BodyName = BodyName;`），编辑器里暴露它属于误导。

## 二、高回报

### P1-1 Heavy abort 放在角色转发层，语义错层；两条确定路径会静默吃掉 Light 物理

拟稿 §7 把 `AbortPhysicalReactionForHeavy()` 放在 `PrepareForHeavyImpact_Implementation` 第一行。该函数的语义是"机关问了一句"，不是"身体即将被夺走"。经核实，以下两条路径会在 Heavy 完全不接管的情况下清掉 Light 物理：

**路径 A：同来源保护期 Busy + 每帧续期（可复现，周期性）**

```cpp
// HeavyImpactResponseComponent.cpp:914-924
const float CurrentTimeSeconds = World->GetTimeSeconds();
if (CurrentTimeSeconds >= SameSourceProtectionUntilSeconds) { /* 过期清理 */ return false; }
SameSourceProtectionUntilSeconds = CurrentTimeSeconds + Tuning->SameSourceProtectionSeconds;
return true;
```

`SameSourceProtectionSeconds = 0.75f`。`CompleteRecovery` 里 `BeginSameSourceProtection()` 建立保护，之后同一摆锤每次有效请求都**续期**；返回 `Busy` 不写入 `NotifiedReceiversThisSwing`（那里只收 Accepted/Duplicate），所以 60Hz Timer 会持续重试、持续续期。

后果：**追猎者被摆锤击飞→起身→锤头下次扫过 → 之后 0.75s 内它的轻受击局部物理完全不生效**，按摆锤周期反复出现（周期 2s 则约 37% 时段失效）。玩法层 Stop/Montage 正常，只有物理表现消失，且 `ShouldLogRejectedImpact` 抑制重复日志 → 静默。这段时间正是"刚击飞完、AI 起身压过来、手里有箱子"的核心战斗循环。

注意：这不是"两件小概率事件同时发生"，是必然进入的状态 + 高频操作。但也**不是**"无限延长数秒"——每次锤头在有效窗口内只停留数帧，续期后 0.75s 自然过期。

**路径 B：ETA 过晚 Invalid（必然发生，影响轻微）**

三个机关都做了 ETA 上限过滤，但**都没有下限过滤**；Heavy 侧有：

```cpp
// HeavyImpactResponseComponent.cpp:447-451
if (Request.EstimatedTimeToContactSeconds < RequiredLeadSeconds)
{
    OutReason = TEXT("Prediction arrived too late to cross a reliable PrePhysics update.");
    return false;
}
```

`RequiredLeadSeconds = max(0.02, dt*1.25)`。ETA 从 0.16 单调降到 0，末段必然低于下限 → `Invalid`。挂上 abort 后表现为"锤头贴身前一刻 Light 物理被清一次"。这是 Heavy 既有边界，本身不是拟稿引入的 bug，但拟稿把 abort 挂在此处才让它变成可见的表现损失。

**不能删 abort**：不清理的话 Heavy 会在快照阶段直接拒绝准备，**角色不会被击飞**，比丢物理表现严重得多：

```cpp
// HeavyImpactResponseComponent.cpp:602-609
BodySnapshot.bWasSimulating = Body->bSimulatePhysics;
if (BodySnapshot.bWasSimulating)
{
    OutReason = FString::Printf(TEXT("Body %s was already simulating before HeavyImpact preparation."), ...);
    return false;
}
```

**改法（推荐）**：在 `PrepareForImpact` 里 `ValidatePreparationRequest` 通过之后、`CapturePreContactState` 之前广播一次 `OnPreContactCaptureRequested`，Light 组件订阅后停物理。约 5 行 + 一个 delegate 声明，语义精确，A/B 两条路径一并解决。

这需要把拟稿"不修改 Heavy 内部"的自我约束放宽为"不修改 Heavy 的状态机与恢复流程"。成本与放在转发层几乎相同，但一个是精确的、一个是在赌 Invalid/Busy 不常走。

**若选择不改**：必须把"Heavy 起身保护期内、机关附近的轻受击无物理表现"写进方案的已知限制。否则 A/B 调参时看到"有时有物理有时没有"，第一反应会去调冲量和角向强度，根因却在状态机——那会白烧数轮调参，并可能误触止损条件"需要极端冲量才有画面"。

`SetAllBodiesBelowSimulatePhysics(Root, false, true)` 走 `BI->SetInstanceSimulatePhysics(false, ...)`（`SkeletalMeshComponentPhysics.cpp:1515-1520`），同步写 `bSimulatePhysics`，所以无论放哪一层，同一调用栈内 abort 之后 Heavy 一定能过上述检查。这部分判断成立。

### P1-2 `ClearActiveImpact` 不含物理清理，两条路径必须显式补 `StopPhysicalReaction()`

`ClearActiveImpact`（`CharacterImpactResponseComponent.cpp:294-316`）只处理 Timer、MaxWalkSpeed 和 Montage。拟稿 §5.5 正文提到了 Heavy Prepared 回调与 EndPlay 要停物理，但 §5.2 / §5.5 的代码块里都没有。

漏一行的后果是"Heavy 结束后上半身还在模拟"，而这会让**下一次** Heavy 准备被 B2 同一检查拒绝，表现为"重受击偶尔完全不触发"。要求把这两处显式写进拟稿代码，不要只留在正文。

另：§7 说 Heavy 被拒时"局部物理余势已经结束"读起来像自然结束，实际是硬切（blend weight 直接 0、模拟直接关）。措辞改为写实。

若采纳 B1 的 drive 常驻，需在方案中说明：Heavy 期间上半身关节同时挂 PhysAnim drive（强度 0，stiffness/damping 均为 0，不产生扭矩）与 PhysicsControl control。理论惰性，但必须在 PIE 实测一次 Heavy 全身布娃娃等价性，不得默认无害。

### P1-3 三条时间线关系未定义，Montage BlendIn 0.08s 与物理 Hold 0.05s 反序

现有默认 `MontageBlendInSeconds = 0.08f`（`CharacterImpactTuningData.h:36`），拟稿 `PhysicalHoldSeconds = 0.05f`。物理权重最高的 0.05s 内动画目标基本还是 locomotion；Montage 混入（0.08s 后）时驱动目标突变一次，而物理正在 Blend Out → 可能出现"先偏一下、动画再拽一下"的二段抖动。

这不是参数微调，是 Montage BlendIn / 物理 Hold / 物理 BlendOut 三者关系没在方案里定义。建议写死约束（例如物理 Hold 至少覆盖 Montage BlendIn，或 `Hold + BlendOut >= MontageBlendIn`）并在 `IsPhysicalReactionConfigured` 里校验。否则 §8 说的"两轮 A/B 内共存"很可能因时序而非强度失败，然后误触止损。

### P1-4 地刺方向语义与"上半身局部冲量"错配

```cpp
// SpikeTrapHazard.cpp:230-231
Request.WorldDirection = FVector::UpVector;
Request.ImpactPoint = Target->GetActorLocation();
```

`ImpactPoint` 是胶囊中心（在 UpperBodyRoot 之下 → 按拟稿回退到 Root），方向是正上方。地刺的表现会变成"从 spine 往上抛上半身"，像抽了一下肩膀，而不是"脚下被戳"。§9 里"地刺的 authored NormalizedStrength 会驱动同一局部物理表现"在画面上不成立。

根因是请求合同缺一个显式声明：来源没说明"我这次的 WorldDirection 是否具备物理语义"。触发类来源的方向只用于选左/中/右动画，不能当冲量轴。

**改法**：在 `UCharacterImpactSourceProfile`（来源侧，不是角色侧）加 `bDirectionHasPhysicalMeaning` 之类字段，false 时只走 Slow/Stop/Montage、不施加冲量。这不是给箱子写特判，是把已有隐含约定显式化——`RawNormalImpulse` 现在已承担一半该职责（真实刚体填、触发器留零），但拟稿 §5.4 明确不用它，信息就丢了。

### P1-5 末端 body 用同一标量冲量，手/头会被甩飞

`ResolvePhysicalHit` 会把命中点解析到 `hand_l`、`head` 这类小质量 body，然后施加同一个 `PhysicalImpulseAtFullStrength`。同样冲量在 `spine_03`（重、双侧约束）和 `hand_r`（轻、链末端）上差一个数量级的视觉幅度。

二选一：按 body 质量归一（`Impulse * BodyMass / ReferenceMass`），或限制可受力集合为脊椎+上臂、末端命中上溯到父 body。否则 A/B 会陷入"胸口刚好、打到手就抽风"的死循环。

### P1-6 Mesh 碰撞配置未在方案中定义，而它决定这是否算"真实参与解算"

§1 称"真实骨骼刚体参与物理解算"，但上半身 body 转动态后会不会与外物/墙真的接触，取决于 Mesh 当前 `CollisionEnabled` 与对 `PhysicsBody` / `WorldStatic` 的响应。C++ 只改了 `AttackProjectileBody` 与 `Camera` 两个通道（`PursuerCharacter.cpp:113-121`），其余值在 `BP_Pursuer` 里，本次审计**未用 MCP 回读**。

两种结果差别很大：

- Mesh 无物理碰撞 → 箱子不会被手臂挡住，是纯表现层，§1 措辞要降一档；
- Mesh 有物理碰撞且 Block WorldStatic → 贴墙受击时动态手臂可能被墙挤出去甚至抖爆，需在 Light 期间临时降级上半身 body 的 WorldStatic 响应。

**落盘前必须先用官方 MCP 读 `BP_Pursuer` 的 Mesh 碰撞真实值**，再定 §1 表述与是否需要降级。

### P1-7 物理反应缺总时长上限

玩法层有 `MaxContinuousLightSeconds` 兜底，物理层只有"每次命中刷新 `PhysicalReactionStartTimeSeconds`"，连续不同 ImpactId 可把上半身无限期留在模拟态。加 `MaxContinuousPhysicalSeconds`，从首次进入模拟起计，超时强制 Blend Out，与玩法层同构。

### P1-8 构造函数里 `SetComponentTickEnabled(false)` 无效

```cpp

{
```

对照：Light 组件自身构造函数（§5.1）写法正确，角色侧这处是错的。若采纳 B1 的常驻 tick，此项自然消解，但仍要显式声明常驻是有意的。

- 非法 UpperBodyRoot 只关闭物理层
- Duplicate / HeavyBusy / None 不触发物理
- Heavy 抢占后上半身无模拟残留
- EndPlay 后两个临时 Tick 均关闭

要么承认需要新增测试基建（与"不新增 C++ 文件"冲突），要么移入 PIE 验收。当前清单写得像可自动化，实际不能。

PIE 清单建议新增一条（直接命中 P1-1 路径 A，比原第 7 条更短、更可复现）：

> 用摆锤击飞追猎者 → 等它起身 → 起身后 1 秒内立刻用磁力箱砸其胸口 → 局部物理必须生效。

abort 放转发层时该条稳定失败，放 Heavy capture 前时稳定通过。

## 五、建议落地顺序

1. 先用官方 MCP 读三样：`BP_Pursuer` 的 Mesh 碰撞真实值（P1-6）、追猎者 PhysicsAsset 真实上半身 Body 名（§9 已列）、`DA_PursuerStandingImpact` 现有字段；
2. 修 B1、B2、P1-8、P1-2；
3. 定 P1-1 的 abort 层级（改 Heavy 或明确写入已知限制）、P1-3 时序约束、P1-4 来源方向语义；
4. 再进 A/B 调参与验收。

顺序理由：B1 / P1-1 / P1-3 都会以"物理时有时无"或"上半身发软"的形式表现出来，与冲量和角向强度调参的失败症状高度重合。不先修就调参，很容易把一个可行方案误判死。
