## 一、API / 编译正确性核实（全部通过，给实现方信心）

方案走的是「从 `PhysicsControlAsset` 创建 + `InvokeControlProfile`」这条路线，与旧组件 `PhysicsControlHitResponseComponent` 的「`CreateControlsFromLimbBones`」路线不同。逐一对照 UE5.8 头文件，方案用到的签名与字段**全部匹配**：

| 方案用法 | UE5.8 实际签名 | 结论 |
|---|---|---|
| `CreateControlsAndBodyModifiersFromPhysicsControlAsset(Mesh, nullptr, NAME_None)` | `(USkeletalMeshComponent*, UPrimitiveComponent*, FName) -> bool` |✓ |
| `InvokeControlProfile(Name, NAME_None, NAME_None)` | `(FName, FName=TEXT(""), FName=TEXT("")) -> bool` | ✓（`NAME_None` 等价空FName） |
| `GetAllControlNames()` / `GetAllBodyModifierNames()` | `const TArray<FName>&` | ✓ |
| `DestroyControls(names, true, false)` / `DestroyBodyModifiers(...)` | `(TArray<FName>&, bApplyToControlsWithName=true, bApplyToSetsWithName=true) -> bool` | ✓ |
| `SetControlsEnabled(names, false, true, false)` | `(TArray<FName>&, bEnable, bApply..Name, bApply..Set) -> bool` | ✓ |
| `SetBodyModifiers{MovementType,CollisionType,GravityMultiplier,PhysicsBlendWeight}(names, val, true, false)` | 均为 `(TArray<FName>&, val, bool, bool) -> bool` | ✓ |
| `PhysicsControl->PhysicsControlAsset = Tuning->PhysicsControlAsset.Get()` | 成员是 `TSoftObjectPtr<UPhysicsControlAsset>`，可由裸指针赋值 | ✓（见下注） |
| `PhysicsControlAsset->Profiles.Contains(Name)` | `TMap<FName, ...> Profiles`（public，编译后运行时数据） | ✓ |
| `PhysicsControlAsset->CharacterSetupData.LimbSetupData.IsEmpty()` | `FPhysicsControlCharacterSetupData::LimbSetupData` 为 `TArray<...>`（public） | ✓ |

**亮点**：`Validate()`（第 7 节）刻意检查**编译后**的 `Profiles` / `CharacterSetupData`，而非编辑期的 `MyProfiles` / `MyCharacterSetupData`。UE5.8 里这两组字段确实分离（`My*` 仅 `WITH_EDITORONLY_DATA`，编译后写入无前缀字段）。这个检查能精准挡住"PCA 填了但没编译，运行时 Invoke 全失败"这一最典型陷阱——方案作者对 PCA 数据模型理解到位，予以肯定。

> 注：`PhysicsControlAsset` 成员实际是 `TSoftObjectPtr`（方案未点明）。`Tuning->PhysicsControlAsset` 是硬引用 `TObjectPtr`，`.Get()` 后赋值给 SoftObjectPtr 可编译且语义正确。无需改动，知悉即可。

## 二、P0 —— 落盘前必须补齐（否则集成崩溃或留死代码）

### P0-1 追猎者旧受击链拆除清单不完整，按现稿实施会空指针崩溃

方案第 4.2 / 11.2 只写了"移除构造函数中旧 `UPhysicsControlHitResponseComponent` 的创建"，但 `APursuerCharacter` 现有受击绑定是一条链，不止构造函数一处：

- `PursuerCharacter.cpp:29` 构造函数 `CreateDefaultSubobject<UPhysicsControlHitResponseComponent>`
- `PursuerCharacter.cpp:54` `PhysicsControlHitResponse->Configure(GetMesh(), PhysicsControl, PhysicsControlHitTuning)`
- `PursuerCharacter.cpp:55` `PhysicsControlHitResponse->OnPhysicsHit.AddDynamic(this, &APursuerCharacter::HandleHitReact)`
- `.h` 成员：`PhysicsControlHitResponse`、`PhysicsControlHitTuning`
- 表现函数：`HandleHitReact` / `OnHitReactMontageEnded` / `bIsReacting` + `Config` 里的 `HitReactFromLeft/Right/Front` 蒙太奇

**若只删构造函数创建、保留 54/55 行 → `PhysicsControlHitResponse` 为空→ `Configure`/`AddDynamic` 空指针崩溃。** 落盘方案必须给出精确清单：这三行（29/54/55）一并处理，成员如何取舍。

**并且存在语义冲突**：旧 `HandleHitReact` 会 `PlayAnimMontage` 播受击动画，而 B 路线明确"飞行状态不依赖受击动画"（第 3 节、第 0节）。方案 11.2 保留 `bIsReacting` 并让 `IsReacting()` 返回 `HeavyImpactBusy || bIsReacting`。但一旦拆掉 `OnPhysicsHit` 绑定，`bIsReacting` 就没有任何置位者，`|| bIsReacting` 变成永远为 false 的**死代码**。要么明确保留旧的轻量受击动画通路（则需说明它与新组件如何共存/互斥），要么直接删除 `bIsReacting` 及其相关函数，让 `IsReacting()` 只依赖 `HeavyImpactResponse->IsBusy()`。现稿两头不靠。

### P0-2 玩家 Jump 输入门与"不拆 Enhanced Input 绑定"的表述自相矛盾

方案 11.3 声称"不要在 Enhanced Input 层拆绑定；给已有动作入口增加统一状态门"，并给出 `TryJump()` 包装。但现状 `ZeroEscapeCharacter.cpp:115` 是：

```cpp
EnhancedInput->BindAction(InputConfig->JumpAction, ETriggerEvent::Started, this, &ACharacter::Jump);
```

Jump **直接绑引擎函数**，没有自定义入口可加门。要接`TryJump()` 门，**必然要改这行BindAction 的目标**为 `&AZeroEscapeCharacter::TryJump`。Move / BeginMagneticGrab / ThrowMagneticObject 是本类自定义函数（可在函数体内加门，无需改绑定），唯独 Jump 例外。落盘方案需订正11.3：明确"Jump 需改 `JumpAction` Started 的绑定目标为 `TryJump`"，否则实现者会照字面"不改绑定"而使Jump 门永远不生效。

（`StopJumping` 走 Completed/Canceled，无需门；`EndMagneticGrab` 方案要求 Busy 时仍允许，现状绑定可保留，符合。）

## 三、P1 —— 首轮 PIE 必看，直接决定首版画面成立

### P1-1 `ActorToPelvisZ` 用站立姿态固定偏移，倒地后胶囊必然悬空

`EnterPrepared`（第 9.5 节）以命中前站立姿态计算 `ActorToPelvisZ = ActorZ - PelvisZ`（约等于半个身高），之后 `UpdatePhysicalFollow` 全程用它把 Actor 抬到 `PelvisZ + ActorToPelvisZ`。问题：`Downed` 时骨盆贴地，仍加一个"站立高度"的偏移 → **Capsule/Actor 悬在倒地身体上方约一个身高**。这不是边缘情况，是倒地后几乎必现的画面/落点判定错位（相机、交互原点、后续起身探测都会偏）。

建议：`Settling`/`Downed` 阶段的落位改为「骨盆水平位置 + 地面探测命中点 + 胶囊半高」，而不是复用飞行期的固定 `ActorToPelvisZ`。`HasGroundSupport()` 已经在做地面 LineTrace，落位可复用其命中 Z。此项优先级高于其它 P1。

### P1-2 `Downed` 的"睡眠"与持续 Tick 跟随互相矛盾

`EnterDowned`（9.9）`PutAllRigidBodiesToSleep()` 后仍 `SetComponentTickEnabled(true)`；而 `TickComponent`的 Downed 分支条件是 `Mesh->IsAnySimulatingPhysics()`——**睡眠 body 的 `IsAnySimulatingPhysics()` 仍返回 true**（sleep ≠ not simulating）。结果：Downed 后每帧仍 `UpdatePhysicalFollow` + `VInterpTo`，既没达到"睡眠省开销"的意图，又对已静止骨盆做无谓逼近。PCG 同屏多个倒地追猎者时线性累积开销。

建议：首版就落地 9.9 里提到的 `DownedKinematic` 备选（稳定后把 body 切 Kinematic 冻结当前姿态、`UpdatePhysicalFollow(bSnap=true)` 定位一次、再关 Tick）；或至少用 body sleep 状态作为停跟随判据，而不是 `IsAnySimulatingPhysics()`。别把这个取舍留到"以后看效果"，它每帧都在跑。

### P1-3 胶囊直立跟随的穿模/嵌地/悬空未列入验收

`UpdatePhysicalFollow` 让 Actor/Capsule 保持直立、`TeleportPhysics` 跟随骨盆水平位置。骨盆飞到空中、倒在墙角或斜坡时，直立胶囊瞬移到该XY 很可能穿墙、嵌地或悬空。方案 P1 清单只提了"相机落后"（第 16 节 P1-6），未列胶囊本身的穿模。建议把"Capsule 跟随时穿模/悬空/卡几何"补进第 14.2 失败判据与第 16 节 P1 观察项；首版可先只观察不修，但必须在验收表里。

### P1-4 玩家与追猎者Capsule 对 `ECC_PhysicsBody` 初值不一致，第 2 节碰撞桥接描述对追猎者不准确

`PursuerCharacter.cpp:50` 已把追猎者 Capsule 对 `ECC_PhysicsBody` 显式设为 **`ECR_Ignore`**；而`ZeroEscapeCharacter` 未设置，走 Pawn preset 默认。方案第 2 节表格写"平时 Capsule(Pawn) ←摆锤 Overlap 用来提前预测"，对追猎者不成立：追猎者 Capsule 对 PhysicsBody 是 Ignore，Bob 本体根本不会撞它；提前预测其实靠**摆锤预测体积对 Pawn 通道的 Overlap**（第 12 节），与 Bob(PhysicsBody) 无关。

影响：方案 `EnterPrepared` 统一把 Capsule 设 `QueryOnly`，对追猎者是"从 Ignore→QueryOnly"（本就不挡锤，无害），对玩家是"从默认→QueryOnly"（玩家 Capsule 对 PhysicsBody 的默认响应若为 Block/Overlap，则 Prepared 前 Bob 可能提前撞/触发玩家 Capsule）。建议：落盘前用 MCP 读一次玩家 Capsule 对 `ECC_PhysicsBody` 的实际响应，并把第 2 节描述订正为"预测靠预测体积 vs Pawn 通道；两角色 Capsule 对 PhysicsBody 初值不同，Prepared 统一改QueryOnly"。

## 四、P2 —— 可延后 / 文档与健壮性

- **P2-1 去重记录时机与注释不符**：`PrepareForImpact`（9.5）先 `ValidatePreparationRequest` 再 `RecordRecentImpactId`。注释称"接受后立刻记 ID，后续准备失败也不无限重试"，但**校验失败分支在记ID 之前 return**。若失败原因是结构性稳定的（如 `SourceComponent` 不 Block `ECC_PhysicsBody`），同一摆次每帧 Overlap 都会重跑校验并 `UE_LOG(Warning)` 刷屏。建议：结构性失败也记ID，或对该告警限流。

- **P2-2 `DestroyControls/DestroyBodyModifiers` 注释语义错误**：9.11 里 `true, // Remove records` 把第二参数误注为"移除记录"，其实是 `bApplyToControlsWithName`（第三参 `false` 才是"不按集合名匹配"）。传值功能正确，仅注释误导后续维护者，修正即可。

- **P2-3 `InvokeControlProfile(Inactive)` 后立即 `SetComponentTickEnabled(false)`**（9.3）：Inactive profile 的 BodyModifier 目标（Kinematic/QueryOnly）可能未经一帧 PhysicsControl tick 应用即被冻结。首版因 body 初始本就 Kinematic 而无害，但应加注释说明"此处依赖 body 初始即 Kinematic"，避免将来给 Inactive 加真实 body 变更时静默失效。

- **P2-4 玩家被击倒后在起身实现前"卡死"是首版已知限制**：Committed 后 `Movement->DisableMovement()` 且 `IsBusy()`拦截全部身体输入，`Downed` 属 committed，故玩家倒地后无法移动直到起身接入。这是设计预期（第 3 节允许停在 Downed），但请在第 14 节验收文档显式标注为"已知首版限制"，避免 PIE 时误判为bug。
