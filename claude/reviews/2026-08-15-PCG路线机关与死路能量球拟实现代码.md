**有条件通过。** 算法方向（坍缩前软偏好引导 + 坍缩后图分析 + Population 权重调整）与现有架构契合，没有硬约束/软规则的混淆，也没有引入不必要的 Manager/组件体系。但草案有 5 处必须先改稿再落盘的问题：其中 B1、B2 是被草案 §7 性能分析完全漏掉的真实性能回归源，B3 是阶段顺序上无法落地的规则，B4、B5 是拟实现代码本身的缺陷（字段进不了 DataAsset、统计字段被污染）。

另外建议把 A 块拆成 A1/A2 两个检查点：A 的生产代码量估计明显偏低，`600` 行止损线大概率会在功能只做一半时触发。

## 一、阻塞交付（落盘前必须改草案）

### B1. 删掉词典序评分会连带废掉"完美即早退"，每层必然跑满 3 棵 WFC 树

`ZeroEscapeGridLayoutSolver.cpp:740-746` 现在的早退判据是四个整数分量同时为 `0`：

```
if (Score.OrdinaryDeficit == 0 && Score.TotalDeviation == 0
    && Score.RouteCoverageDeficitMicros == 0
    && Score.LongStraightExcessSquared == 0) break;
```

草案 §2.7 把它换成连续 `Quality01` 后没有给新的早退判据。`RewardBranchFit`、`AlternativeRouteFit`、`ArtifactFit` 几乎不可能同时恰好等于 `1.0`，实际效果是**每层每次都要跑满 3 棵树**（`MaxWfcSolveAttemptsPerFloor = 3`，`ZeroEscapeGenerationTypes.h:27`）。这是本轮最大的规划耗时增幅来源，量级远超草案 §7 讨论的图分析开销，而 §7 完全没提。

要求：草案里显式定义新的早退条件（例如"硬密度达标 + `Quality01 ≥ 阈值`"），并把"每层平均消耗的 WFC 树数不上升"写进检查点 A 门槛，而不是只记 P50/P95。

同时 `DensityFit` 定义不完整：现有词典序里 `OrdinaryDeficit`（单侧、普通格缺口）优先级最高，`TotalDeviation`（双侧、总格数）第二，草案合成一个 `abs(Actual-Preferred)/Preferred` 且权重只有 `0.15`，既没说用哪个计数，也让"普通格不足"可以被支线/替代路线的加分买过去。要么拆成两项，要么把普通格缺口保留为前置筛选。

### B2. 路线分析挂在 `BuildRouteMetrics` 后面 = 挂进 WFC 的每叶验收回调

`BuildRouteMetrics` 不是"每层一次"，它在 `ValidateCandidate` 里被调用（`ZeroEscapeGridLayoutSolver.cpp:676-691`），是传给 `FWfcSolver::Solve` 的完整叶验收回调；求解器支持 `Reject` 后继续搜索（`ZeroEscapeWfcLayoutTests.cpp:554、613、663` 就有多叶用例）。把 §2.6 的"逐边移除 + BFS"塞在它后面，成本会按**被访问的完整叶数量**放大，而不是按接受的楼层数。

另一个副作用：`BuildRouteMetrics` 返回 `false` 在这里被当作 `Fatal`（硬非法，直接终止整层），路线分析里的任何数值异常都会被误判成"WFC 输出非法"。

要求：分析放在 `bSolved` 成立之后、`ScoreCandidate` 之前（每棵树至多一次），与硬合法性验收彻底分开，失败只降分不报 Fatal。

### B3. §1.3 条件 4 在楼层求解阶段不可判定，阶段顺序必须写清

`SelectPlayerSpawn` 在 Planner 阶段执行（`ZeroEscapeMultiFloorLayoutPlanner.cpp:2912`），发生在楼层 WFC 之后。草案让求解器直接产出 `FZeroEscapeGeneratedRewardBranch`，而 §1.3 条件 4 要求"支线不含 Enter、Leave、玩家、追猎者或 Exit"——求解器此时不知道玩家/追猎者/Exit 在哪，这条规则无处落地。

而 §5 的文件表又写 Planner 负责"出生点排除端点"，与 §1.3 是两个相反方向的做法，草案没有二选一。任何一种都得补充说明：

- 若选"Planner 事后过滤支线"：`RewardBranches` 会在候选评分之后再变少，§4.2 的门槛"光团数 == RewardBranch 数"仍成立，但 §2.7 的 `RewardBranchFit` 只能是候选期近似值，必须明说；
- 若选"出生点/Exit 排除端点"：`SelectPlayerSpawn` 目前只排除 Pursuer/Exit 和结构格（`:2941-2955`），再排除全部端点等于缩小可选集，会把草案 §2.9 自己担心的"WFC 通过后在出生点阶段失败、浪费整栋重试"风险搬到端点上，必须给容量兜底（例如端点集为空时按稳定顺序释放一个）。

顺带：Population 侧应加一条断言"光团端点 ≠ 玩家/追猎者/Exit 地址"，不要只依赖上游过滤。

### B4. §3.2 的成本结构体字段缺 `UPROPERTY`，DataAsset 里改不了；缺 Pendulum 成本

草案 §3.2：

```cpp
USTRUCT(BlueprintType)
struct FZeroEscapeHazardBudgetCostTuning
{
    GENERATED_BODY()
    float SpikeTrap = 1.0f;   // 没有 UPROPERTY
    ...
};
```

四个字段都没有 `UPROPERTY`，既不会序列化也不会出现在 `DA_Population_Default` 面板里，而 §5 又要求"修改 Population DataAsset 的预算成本"——直接自相矛盾。同一问题出现在 §2.3 的每层摘要新增字段（`int32 RewardBranchCount = 0;` 等），`FZeroEscapeGeneratedFloorSummary` 现有字段全部是 `UPROPERTY(VisibleAnywhere, BlueprintReadOnly)`（`ZeroEscapeGenerationTypes.h:303-340`），新字段必须保持一致。

同时：`FZeroEscapeHazardBudgetCostTuning` 没有 Pendulum 成本，但 §3.2 循环第一行就用 `MandatoryPendulumBudget`，取值未定义。强制摆锤数量来自 `HighCeilingRoom` 结构数（`ZeroEscapePopulationPlacementPolicy.cpp:938-945`），必须给它一个明确成本（建议 `1.0` 并在结构体里显式列出）。

另外按项目惯例，新增 tuning 字段要带 `meta = (ClampMin/ClampMax)` 并进 `IsValid...Tuning` 校验（参考 `ZeroEscapePopulationPlacementPolicy.cpp:778-817`），草案没提。

### B5. §4.2 把光团塞进 `ResourcePlacements` 会污染既有统计与 Class 加载

`ZeroEscapePopulationPlacementPolicy.cpp:2230-2233` 直接用数组长度赋值：

```cpp
InOutPlan.KindCounts.MagneticResources = InOutPlan.ResourcePlacements.Num();
InOutPlan.ResourceStats.ActualCount = InOutPlan.ResourcePlacements.Num();
InOutPlan.ResourceStats.UnderfilledCount = ...
```

草案 §4.2 第 4 步"追加一个光团"到 `WorkingPlan` 之后，`ResourceStats.ActualCount` 与 `ResourcePlacements.Num()` 就不再相等，任何按数组长度断言资源数的测试都会失真；`UnderfilledCount` 语义也被搅乱。

要求：加独立的 `EnergyOrbPlacements` 数组 + 独立计数（草案自己也说"光团不占普通磁力资源预算"，那就不该混在同一数组里）。连带必须改的地方，草案 §5 只写了 `FindClassReference`，实际还有：

- `LoadUsedClasses`（`ZeroEscapeGameplayPopulator.cpp:84-105`）要遍历新数组，否则光团 Class 根本不会被加载；
- `PlacementKindName`（`:40-52`）要加 `EnergyOrb`，否则日志打 `Unknown`（两个 switch 都有 `default`，不会编译失败，但诊断会退化）；
- `ValidateActorBudget`（`:2236-2261`）要计入新数组。

还有一处顺序问题：草案说"Actor 安全预算会把光团计入"，但 `ValidateActorBudget` 是事后检查，而上游 `WorstActorCount` 预估（`:983-985`）只算机关+资源。光团数量在规划前就已知（`RewardBranches.Num()`），应该并入前置预估，不要等到规划完成再原子失败。

## 二、高回报（建议在实施前一并改掉）

### H1. 凸增覆盖会撞 `MaxAbsLog2Score` 顶，把其他五个通道压平

`MaxAbsLog2Score = 5.0`（`ZeroEscapePlacementTypes.h:53`），六通道求和后统一钳制。草案 §3.3 的 `0.45x + 0.05x²` 在 `x = 8`（图距离 11）时单通道就达 `6.8`。此时所有远端候选的总分都贴在 `+5`，组合、多样性、进度、组压力**全部失效**——恰好摧毁了 §3.5 想要的"奖励支线组合放大"。草案表格里"10+ 继续增长，最终受总 `MaxAbsLog2Score=5` 有界截断"把这当成安全网，实际是设计缺陷。

建议：给覆盖项自身上限（如 `3.0`），保留总钳制作为最后防线；检查点 B 增加断言"存在覆盖极高的候选时，组合通道仍能改变排序"。

另外必须显式定义"当前还没有任何机关"的取值。现有实现对 `UnreachableDistance` 特判返回 `signal = 1.0`（`ZeroEscapePopulationPlacementPolicy.cpp:1373-1379`，`UnreachableDistance = MAX_int32/4`），新公式若直接算 `x = D - 3` 会溢出成天文数字。

### H2. §3.4 与现状不符两处，"只是把 1.5 调成 1.75"的说法不成立

现有 `LauncherCombinationDistanceSignal(Distance, GroupRadiusTiles)`（`ZeroEscapePopulationPlacementPolicy.cpp:693-705`）是"紧邻 0 分 + 按组半径归一"的数据驱动曲线：`D<=1 → 0`，否则 `(D-1)/(GroupRadius-1)`。草案换成硬编码 `1/7, 4/7, 1`：

1. `D = 1` 从 `0` 变成 `+0.25` log2（`1.19×`）——**开始奖励紧邻**，与草案自己写的"保持远距配合优于紧邻"和代码注释"紧邻不加分"都相反；
2. 丢掉 `GroupRadiusTiles` 依赖（DA 可调 `1..8`，`ZeroEscapePlacementTypes.h:66-68`），以后改组半径曲线不跟随，属于把数据驱动改回硬编码。

同一 scale 还乘在 `LauncherCombinationPressureBonus` 上（`:1339-1341`），改曲线会一起改组压力诊断，草案没提。

建议：保留归一化形式，只调 `LauncherCombinationLog2Bonus`；确实要改曲线形状就在草案里写明"接受与组半径解耦"并同步改注释。

### H3. 预算语义变更缺数据迁移与单位重标定

`ExpectedHazardsPer100GameplayCells` 的字段注释是"每 100 个玩法面积格期望出现多少**处**机关；一组地刺按一处计数"（`ZeroEscapePlacementTypes.h:183-186`）。改成"预算单位"后，同一数值在全便宜类型（刺轮 `0.5`）下最多产出 2 倍机关处数，三档现值必须重标定，字段注释/命名也得改，否则以后调参会按错误单位理解。

另建议：预算用整数十分之一（`10 / 10 / 7 / 5`）而不是 `float` 累加，和项目既有 `RouteCoverageDeficitMicros` 的整数化风格一致，避免浮点累加影响同 Seed 复现。

### H4. `Quality01` 用浮点比较与现有确定性风格相反

现有评分刻意把比例转成整数（`RouteCoverageDeficitMicros`，`ZeroEscapeGridLayoutSolver.cpp:282、349-353`）。草案的 `Quality01` 是浮点加权和，"同分时按诊断字段固定顺序比较"在浮点下几乎永远不会触发。建议量化成 `int32` micros 再比较，让平局规则真正生效。

### H5. `EffectiveBranchTarget` 可能为 0，`RewardBranchFit` 会把"有支线"判成最差

`MaxByCapacity = floor(PreferredOrdinary × Ratio / MinLength)`，小楼层可得 `0`。此时 `1 - Clamp(((Actual-0)/max(0,1))², 0, 1)`：`Actual = 0` 得满分、`Actual ≥ 1` 得 0 分——方向反了，会主动挑没有支线的候选。必须把 `EffectiveBranchTarget` 下限 Clamp 到 `1`，或在 `target = 0` 时该通道退化为常数并把 `0.25` 权重按比例摊给其他项。

### H6. A 块生产代码量估计偏低，建议拆成 A1/A2

`ZeroEscapeGridLayoutSolver.cpp` 现在总共 746 行。A 块要在它里面加：方向感知最短路（含状态定义与代价表）、支线有界候选搜索、偏好写入与冲突消解、稳定主路重建、Run 压缩与转弯统计、degree-2 链回溯、逐边 BFS 替代路线、统一归一评分，再加 DataAsset 校验、Plan 字段、Hash、Planner 汇总。按本项目的防御式校验密度和中文注释密度，`320–400` 行不现实，更接近 `500–700`。

后果不是估错数字，而是 §0 的"超过 600 行立即止损"会在功能只做一半时触发。建议现在就拆：

- **A1**：DataAsset 字段 + 私有开口偏好 + 候选权重叠加 + 兜底加权抽样（可独立验证"提示不 Ban、同 Seed 稳定、权重方向正确"）；
- **A2**：坍缩后图分析 + 统一评分 + RewardBranch 进 Plan/Hash（可独立验证支线定义、伪凸起、替代路线、Seed Sweep）。

各自独立提交与门槛，止损线分别算。

## 三、可延后 / 提示

- **L1**：§2.6 第 7 步"逐边移除 + BFS 判 Enter→Leave 是否仍连通"在数学上等价于"该边不是桥"（删非桥边不影响连通性；删主路上的桥必然分离 Enter/Leave）。草案把桥分析写成"以后才优化"，其实现在一次 Tarjan 就能算完，而且能在测试里互相断言。保留 L×BFS 也可以，但建议加一条"两种算法结果一致"的测试。
- **L2**：§7 的"单层最大 216 格"是当前 Profile 值，不是代码上限（`MaxGridCells = 1024`、`MaxGridAxis = 64`，`ZeroEscapeGenerationTypes.h:18-20`）。性能门槛要么按代码上限给最坏估算，要么明写"仅对当前 Profile 成立"。
- **L3**：Plan 已有 `FZeroEscapeJunctionMetrics.DeadEndCount` 和 `CycleRank`，度数统计在 Planner 的 `MeasureJunctions`（`:2426`）里。新增支线/一格凸起统计会形成第二套度数计算，建议复用或至少加不变式断言：`RewardBranchCount ≤ DeadEndCount`、`OneCellTerminalSpurCount ≤ DeadEndCount`。
- **L4**：§3.6 删除硬间距的工作量不止"新增测试"。至少牵动 `ZeroEscapePopulationPlacementTests.cpp:266/739/849/937/955/1524/1554` 七处既有用例、`Policy:855` 的校验、`:2157-2167` 的剔除段、`:2187-2194` 的覆盖信号（当前拿最小间距当比例尺）。B 块测试项应写成"新增 + 改写"。`SpacingRejectedCount` 是私有 stats，可直接删。
- **L5**：新增 Plan 字段进 `ComputeCanonicalLayoutHash` 会改变**所有既有 Seed** 的 hash（`ZeroEscapeGenerationCore.cpp:260-525`）。DataContract 测试、文档里记录过的 hash、以及 `ZE_PCG_RESULT schema=6` 日志约定（`ZeroEscapeRuntimeLevelGenerator.cpp:953`）都要同步；建议顺手把 schema 号 +1。
- **L6**：§2.4 的 `FPreferredPathState.StraightRunLength` 只写"超过上限后封顶即可"，没给上限值；封顶后 `+80 × Excess²` 不再增长，长直惩罚会饱和（§7 又写成 5 档，等于 `Excess` 最大 1、惩罚最大 80）。建议写死上限 ≥ `Preferred + 4`（状态数 `216 × 5 × 9` 依然微不足道），并在测试里断言"8 格直线严格贵于 5 格"。
- **L7**：兜底求解的随机 salt 硬编码 `LocalAttempt = 3`（`ZeroEscapeGridLayoutSolver.cpp:769-772`），恰好等于最大树数上限。§2.8 让兜底也读草图后，如果以后放宽 `MaxWfcSolveAttemptsPerFloor`，兜底会与第 4 棵真实树共用随机流。A 块顺手换成独立随机域即可。

## 五、给写代码 AI 的最短处理路径

1. 先改草案：B1（新早退判据 + DensityFit 拆项）、B2（分析移出验收回调）、B3（两阶段支线过滤，二选一并写清容量兜底）、B4（`UPROPERTY` + Clamp + Pendulum 成本）、B5（独立 `EnergyOrbPlacements` + 三处 Populator/预算同步）。
2. 顺手吸收 H1（覆盖项自身上限 + Unreachable 特判）、H2（保留归一化或明示解耦）、H5（`EffectiveBranchTarget` 下限 1）——这三条改动都在 10 行以内，收益明确。
3. 把 A 拆成 A1/A2，止损线分别计算；检查点 A 门槛补两条：**每层平均 WFC 树数不上升**、**分析只在接受候选后执行一次**。
4. H3/H4/L4/L5 是"实施时别漏"的清单项，不需要改算法。
