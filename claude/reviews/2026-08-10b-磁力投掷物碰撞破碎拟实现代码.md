## 0. 先确认已核实为正确的部分（不必再怀疑）

这几条容易被误判成 bug，已逐条核对引擎源码，写代码时不要"顺手改掉"：

1. `SetTimerForNextTick(this, &Func)` 在 UE5.8 **返回 `FTimerHandle`**（`TimerManager.h:249`），文档写法可编译，且句柄可被 `ClearTimer` 清除。项目内 `PhysicsControlHitResponseComponent::HandleMeshHit` 已是同一写法。
2. `UPrimitiveComponent::BodyInstance` 在 UE5.8 仍是 **public UPROPERTY**（`PrimitiveComponent.h:1445`），`ThrownBody->BodyInstance.bNotifyRigidBodyCollision` 读法有效。
3. Chaos 的刚体命中通知按**双方各自的 flag 独立 dispatch**，所以"只在武装期开投掷物一侧的 notify"是必要且充分的，不会因为追猎者那侧已开就自动拿到回调。同理，碎片替身默认不开 notify，不会污染追猎者受击。
4. `CrumbleActiveClusters()`(739)、`bEnableDamageFromCollision`(1058)、`bAllowRemovalOnSleep`(1062)、`bAllowRemovalOnBreak`(1066)、`InitialVelocityType`(1094)、`InitialLinearVelocity`(1098) 在 UE5.8 `GeometryCollectionComponent.h` 全部存在，名字无变化。
5. "先 `SpawnActorDeferred` + `FinishSpawningActor` 成功、再 `OwnerActor->Destroy()`"顺序正确：既没有一帧空洞，又因为同帧内完成、物理 tick 在后，不会出现原物体与替身重叠爆炸；`AlwaysSpawn` 是这个顺序下的必需项。
6. 文档 3.3 "不在Hit 回调里立即销毁"的顾虑成立，且方案已覆盖：`UPhysicsControlHitResponseComponent::HandleMeshHit` 同样把处理推到下一帧 `ProcessPendingHit`，但它只保存值拷贝（Region / BodyBone / ImpactPoint / WorldImpulse / Score），**不持有 `OtherActor` 指针**，因此下一帧销毁原 Actor 不会打断追猎者受击链，两个 next-tick timer 的先后顺序也无所谓。这是当前唯一的跨帧消费方，没有隐藏依赖。
7. `AMagneticPrototypeProp` / `AMagneticFractureActor` 标 `final` 不影响蓝图派生（`BP_MagneticProp` 已是现成反例）。`TSubclassOf<>` / `TObjectPtr<>` 成员用前向声明满足 UHT，不触发"UPROPERTY 必须完整类型"那条坑。

## 1. 阻塞交付

### B1. 碎片替身的碰撞契约完全缺失，会直接破坏受击表现和玩家移动

`AMagneticFractureActor` 构造函数只设了 Mobility 和三个 Removal/Damage 开关，**没有任何 collision profile / object type / channel response**。核对引擎：`UGeometryCollectionComponent` 构造函数和 `AGeometryCollectionActor` 构造函数都**不设置** collision profile，因此落到 `FBodyInstance` 默认值——**ObjectType = WorldStatic、对所有通道 Block**。后果：

- 投掷命中追猎者时，追猎者下一帧才进入 `ProcessPendingHit` 激活 PhysicsControl 区域；而碎片同一帧带着碰撞后速度生成、Block 一切，18 块碎片会打在正在做局部物理反馈的追猎者身上，受击表现被二次污染，且冲量来源无法归因。
- 碎片 Block `ECC_Camera`：项目已经为此吃过一次亏（`GrabCandidate` 里对持有物 `ECC_Camera` 设 `ECR_Ignore` 的注释就是这个原因）。近距离破碎会触发第三人称弹簧臂回缩糊脸。
- 碎片 Block `ECC_Pawn`：18 块碎片可以把玩家顶开、卡在角落或垫高。
- ObjectType 是 `WorldStatic` 而不是 `PhysicsBody`，对一个模拟中的动态物体语义是错的。（副作用上"意外正确"：`FindBestCandidate` 用 `OverlapMultiByObjectType(ECC_PhysicsBody)` 查询，WorldStatic 碎片天然不入选，所以"碎片不可抓取"当前靠的是这个错误默认值+ 无 `MagneticObjectComponent` 双重保险，不要依赖前者。）

要求：在 `AMagneticFractureActor` 构造函数显式定契约并写进文档第 6 节和验证矩阵。建议起点——ObjectType `ECC_PhysicsBody`；Block `WorldStatic` / `WorldDynamic`；Ignore `ECC_Camera`；`ECC_Pawn` 与 `ECC_PhysicsBody` 由体验决定（先建议 Ignore Pawn，避免碎片干扰玩家和追猎者的物理状态，等PIE 确认碎片是否需要与玩家互动再放开）。碰撞契约定在 C++，不要留给蓝图。

### B2. `SafetyLifetimeSeconds = 4.0` 与 Remove On Break 节奏冲突，后备机制会变成主导机制

文档 2.2 自己写的体验方向是"先保持碎裂状态约数秒，再快速缩小清除"。如果 `GC_MagneticCrate4_P0` 的 RemoveOnBreak（起始延迟 + 收缩时长）总时长 ≥ 4s，`SetLifeSpan(4.0)` 会在碎片仍在视野中时直接 `Destroy` 整个 Actor，表现为"一堆碎片凭空整体消失"——比不清理更难看，而且这个 bug 在 PIE 里很容易被误判成 GC 资产问题。

要求：先从 `GC_MagneticCrate4_P0` 读出RemoveOnBreak 的真实总时长 T，把 T 写进文档第 2.2 节，令 `SafetyLifetimeSeconds ≥ T + 明确余量`（并在属性注释里写清这个不变式）；或者改成"监听碎片全部移除后再销毁"，`SetLifeSpan` 只作为兜底上限。当前 4.0 是凭感觉填的数字，且没有任何地方声明它必须大于 T。

## 2. 高回报

### H1. `Demo.Build.cs` 片段的写法和理由都要改

- 理由错误：文档 7.5 说保留 `Chaos` 依赖"因为本模块直接引用了 `EInitialVelocityTypeEnum`"。该枚举来自 `GeometryCollection/GeometryCollectionSimulationTypes.h`，属**GeometryCollectionEngine**，与 `Chaos` 模块无关。按文档自己的"直接使用才显式依赖"原则，应该只加 `GeometryCollectionEngine`，不要加 `Chaos`。
- 写法有坑：现有 `Demo.Build.cs:14` 是 `PrivateDependencyModuleNames.AddRange(new string[] { "PhysicsControl", "Slate", "SlateCore" });`，上面还有一行说明 SlateCore 用途的注释。文档给的是一个包含 5 项的完整 `AddRange`，实现时很容易整段替换掉那一行连带注释，或者追加后重复添加 `Slate/SlateCore`。请明确写成"在现有 `AddRange` 的数组里追加 `GeometryCollectionEngine`"。

### H2. 高速投掷缺 CCD 讨论，隧穿会导致"穿墙不碎 + 永久 Armed"

首次 Blocking Hit 是整套状态机的唯一触发源。`ThrowSpeed` 较大时，若 `BP_MagneticProp` 的 `MagneticBody` 未开 `bUseCCD`，箱子可能直接穿过薄墙或斜擦而不产生 Blocking Hit，物体永久停在 `Armed`。项目在自动周期冲锤任务里已有 CCD 经验可直接复用。

要求：实施前用官方 MCP 回读 `MagneticBody.bUseCCD` 的真实值并写进文档 2.1；验证矩阵加"贴近墙面高速投掷""斜射薄墙/栏杆""朝地面近距离投掷"。

### H3. `ArmForFormalThrow` 的5 个失败条件全部静默，PIE 无法归因

`ThrowHeldObject` 忽略返回值，`ArmForFormalThrow` 里 `!bConfigurationValid` / 状态非 `Unarmed` / `ThrownBody != MonitoredBody` / 未模拟物理 四类原因合并成一个 `return false`。PIE 里"投了不碎"是最可能出现的现象，届时无法区分是没配替身类、状态残留、还是 Body 不匹配。

建议：至少把"状态不是 `Unarmed`"和"`ThrownBody != MonitoredBody`"各输出一次 `Warning`（含当前状态名），其余保持静默。这条和 H9 合起来做成本很低。

### H4. 出手瞬间的自碰撞窗口没有处理

`ArmForFormalThrow` 在 `ReleaseHeldObject(true)` **之后**调用，此时 `ECC_Pawn` / `ECC_Camera` 响应已恢复为原值（Block）。若持有点贴近玩家（`HoldDistance` 较小）、玩家贴墙、蹲在角落或朝脚下投，出手后的第一次 Blocking Hit 很可能是玩家胶囊或脚下地面 → 道具在脸前立刻破碎并被消耗掉。这是玩家能稳定复现的操作，不是极端边界。

建议：给武装加一个极短宽限——出手后 0.05~0.1s 内忽略 `OtherActor == 投掷者` 的命中（或忽略与 Owner Pawn 的命中），并写进矩阵：贴墙投、朝地面投、角落投、跳起向下投。

### H5. `Armed` 永不过期，长期潜伏成"随机碎"

投掷后未命中任何 Blocking 表面而滚停的物体会**无限期**保持 `Armed`。几十秒后追猎者路过一撞、或玩家推另一个物体去碰它，就会破碎并被消耗。文档只写了"Tag 过期后仍破碎"（有意），但没有讨论"停止后长期武装"的后果。

建议：要么明确写成设计意图并加进矩阵（"投掷落地静止 30s 后被追猎者撞到 → 仍破碎"）；要么给 `Armed` 加一个超时（可与 `ThrownWeaponActiveDuration` 对齐，或独立参数）后回 `Unarmed`。P1 要做"可再次投掷的小磁力物"时，这条会直接影响关卡资源节奏。

### H6. 首次命中不看强度，轻擦一下就消耗道具

`HandleBodyHit` 只判断 `Hit.bBlockingHit`。滚落时的小磕碰、蹭到栏杆、擦过箱子角都会立即消耗掉一个磁力物。文档第 1 节讨论了"要不要加径向冲量"，但没有讨论"多轻算命中"。

建议：加一个下限，用 `NormalImpulse.Size()` 或命中前的相对速度（阈值参数放 `MagneticObjectComponent` 或组件自身的 `EditDefaultsOnly`，别硬编码）。不满足阈值时保持 `Armed`，不进`BreakQueued`。这是玩法手感的关键旋钮，第一版就该有。

### H7. `TryDisarmForGrab` 的调用点约定要写进代码边界注释

结论正确：当前只有 `GrabCandidate` 会建立 Physics Handle，所以单点调用是完备的。但这是一个"未来新增抓取入口就会静默失效"的隐式约定（例如以后加自动吸附、传送带、AI 夺取）。

建议：在 `ElectromagneticGrabComponent.cpp` 的文件头边界说明里写明"任何新增的抓取入口必须先调用 `TryDisarmForGrab`，且必须在保存物理快照之前"。顺带：`GrabCandidate` 因 `TryDisarmForGrab` 返回 false 而提前 `return` 时完全静默，玩家按左键无任何反馈，也没有日志；至少加一条 `Verbose`。

### H8. 组件挂在 `AMagneticPrototypeProp` 构造函数 = 每个未配置替身类的实例都刷一条 Error

破碎组件用 `CreateDefaultSubobject`挂在 C++ 父类上，意味着**所有**磁力物都带它。`BeginPlay` 里 `FractureActorClass` 为空时打 `Error`。未来PCG 运行时生成大量磁力物、或存在有意不破碎的磁力物时，日志会被 Error 刷满，污染夜间构建/断言判断。

建议："未配置替身类"降为 `Log`/`Verbose`（这是合法配置，文档第 9 节自己也说"保持普通磁力物行为"）；`Error` 只留给"根组件不是模拟刚体"这类真正的装配错误。

### H9. 状态机零可观测性

`Unarmed → Armed → BreakQueued → Consumed / BreakFailed` 全程没有任何调试输出。三周Demo 里加一个 `EditDefaultsOnly bool bLogStateTransitions` 或 CVar 打印状态跃迁 + 触发命中的 OtherActor 名，排查成本立刻下降一个量级，代价几行。

## 3. 可延后

- **D1** `SpawnActorDeferred` 的 Owner 传 `OwnerActor->GetOwner()`，对磁力物恒为 `nullptr`，语义模糊。直接传 `nullptr` 并注释"替身不挂 Owner，避免被销毁链牵连"更清楚。
- **D2** 命中帧 → 替换帧 → crumble 帧，共 2 帧延迟（60fps ≈ 33ms），玩家可能感觉"撞墙后顿一下才碎"。可在 PIE 里试一次"`BeginPlay` 同帧直接 `CrumbleActiveClusters()`"，若簇结构已就绪就能省 1 帧；不行再退回 next-tick。别为此改结构，实测优先。
- **D3** 验证矩阵缺3 个场景：两个 `Armed` 投掷物空中互撞（预期各自破碎、生成两个替身）；投掷物命中另一个正被玩家持有的磁力物（预期只有投掷物碎，Physics Handle 不受影响）；破碎瞬间玩家正在拉取第三个物体（预期拉取曲线不受影响）。
- **D4** 文档第 8 节要求在 BP 上再设一遍 `EnableDamageFromCollision` / `AllowRemovalOnSleep` / `AllowRemovalOnBreak`，与构造函数默认值重复，形成两处可漂移的真相源。建议这三项只在 C++ 定，BP 只填 `RestCollection` + `SafetyLifetimeSeconds`。另注：`bEnableDamageFromCollision` 带 `BlueprintSetter=SetEnableDamageFromCollision`；当前在 deferred spawn 阶段（组件未注册）直接赋值成员是有效的，但将来若改成 spawn 之后再改，必须走 `SetEnableDamageFromCollision()`。
