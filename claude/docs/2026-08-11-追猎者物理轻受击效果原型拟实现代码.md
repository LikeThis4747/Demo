# 追猎者物理轻受击效果原型拟实现代码

> 状态：实施前最终预览，尚未写入任何功能资产。
>
> 结论：第一轮新增 C++ 为 0；只用一个测试 Physics Control Asset、一个测试 Blueprint 和一个独立测试关卡验证画面。

## 1. 目标

只验证一件事：追猎者上半身在真实碰撞发生前已经处于由动画目标约束的局部物理状态时，与这些上半身 Physics Asset Body 形成有效阻挡接触的普通 Chaos 模拟刚体，能否同时产生：

- 外物肉眼可见的失速、偏转或旋转变化；
- 与胸口、左肩、右肩命中位置一致的身体让位；
- 稳定的骨盆、腿和脚；
- 不依赖 Montage、角色补冲量或物理开关闪切的自然回稳。

箱子只是用户手里的测试物。轻受击效果不认识箱子、磁力物或机关类型。

本文所说的“真实碰撞”，只表示作用来自同一次 Chaos 接触求解，而不是收到 Hit 事件后再用脚本给角色补 `AddImpulse`；它不表示现实世界精度，也不预先保证一定能产生肉眼可见的效果。

## 2. 最小结构


## 4. 测试 Physics Control Asset

新建独立 `PCA_PursuerPhysicalLightImpactTest`，不能修改生产 `PCA_PursuerHeavyImpact`。可以用复制后完整清空的正常编辑器工作流建立，但最终必须回读确认没有 Heavy Profile、腿部 Limb、额外 Set 或初始更新残留。

Limb 与默认控制数据编辑完成后必须先 Compile、Save，再允许 Blueprint 使用。Compile 数据为空或失败时不得进入效果测试。

Physics Asset：

`/Game/Sci_Fi_Character_08/Mesh/Character/SK_Sci_Fi_Character_08_Full_01_PhysicsAsset`

只定义四条 Limb，顺序从叶子到父链：

| Limb | Start Bone | Include Parent | World Control | Parent Control | Modifier |
|---|---|---:|---:|---:|---:|
| Head | `head` | false | false | true | true |
| ArmLeft | `upperarm_l` | false | false | true | true |
| ArmRight | `upperarm_r` | false | false | true | true |
| Spine | `spine_02` | false | false | true | true |

该配置应只覆盖九个真实 Physics Asset Body：

- `spine_02`、`spine_03`、`head`；
- 左右 `upperarm`、`lowerarm`、`hand`。

明确排除 `spine_01`、pelvis、thigh、calf 和 foot。任何下半身 Body 出现在创建集合中都视为配置失败，不自动猜骨骼兜底。

## 5. 测试 Blueprint

`BP_PursuerPhysicalLightImpactTestTarget` 以普通 `Actor` 为父类。

### 组件默认值

`PursuerMesh`：

- Skeletal Mesh：`SK_Sci_Fi_Character_08_Full_01`
- Physics Asset：`SK_Sci_Fi_Character_08_Full_01_PhysicsAsset`
- Relative Location：`(0, 0, -89)`
- Relative Rotation：`(Pitch=0, Yaw=-90, Roll=0)`
- Relative Scale：`(1, 1, 1)`
- 材质：使用 Skeletal Mesh 默认材质，不创建替代材质
- Animation Mode：Use Animation Asset
- Animation：`ThirdPersonIdle`
- Looping：true
- Simulate Physics：false；具体九个 Body 由 Physics Control Asset 创建时切换
- Collision Enabled：QueryAndPhysics
- Object Type：Pawn
- Block：PhysicsBody 与项目现有 `AttackProjectileBody`
- 其他无关通道：Ignore

`PhysicsControl`：

- Physics Control Asset：`PCA_PursuerPhysicalLightImpactTest`
- Auto Activate：true

### 唯一 Blueprint 逻辑

Blueprint 只有一个测试开关 `bEnableControlledUpperBody`，用于同一资产生成 Kinematic 与 Controlled 两个实例。

```text
Event BeginPlay
  -> Branch(bEnableControlledUpperBody)
       false: 不做任何事，作为 Kinematic 对照
       true : PhysicsControl.Activate
              -> Success = CreateControlsAndBodyModifiersFromPhysicsControlAsset(
                     PursuerMesh,
                     WorldComponent = None,
                     WorldBoneName = None)
              -> Branch(Success)
                   true : 进入测试
                   false: 输出一次明确错误并停止；禁止兜底
```

该节点是 UE Physics Control Component 的官方 `BlueprintCallable` API。Blueprint 必须检查返回值，不能静默失败。它仍不绑定 `OnHit`，不检查 Actor、Tag、类名或机关类型，不播放动画，不给角色或外物补力，也不创建 Timer。

如果官方 MCP 无法安全创建该 EventGraph 或编辑 Physics Control Asset 的嵌套 Limb 数据，就停止自动编辑并让用户按上述表格在编辑器中完成；禁止改写成 C++ 动态创建作为绕过。

## 6. 独立测试关卡

不修改 Level0。新关卡 `L_PhysicalLightImpactTest` 只放：

- 当前项目 GameMode / PlayerStart，使现有玩家和磁力能力正常生成；
- 一个带 WorldStatic 碰撞的地面；
- 能看清身体与阴影的基础灯光和固定观察区域；
- 一个 `bEnableControlledUpperBody=false` 的 Kinematic 对照目标；
- 一个 `bEnableControlledUpperBody=true` 的 Controlled 目标；
- 若干现有可投掷物。

两个目标相距足够远，避免物体串台。目标 Actor 的放置高度按上述 Mesh `-89 cm` 偏移校准到脚底贴地；不得用缩放或不同姿势补偿。测试目标不实现 Standing Impact 接口，所以现有 Stop / Slow / Montage 不会触发；可投掷物只负责提供真实 Chaos 碰撞。

如果当前磁力箱的破碎画面遮挡身体观察，先寻找项目中现有的不破碎可投掷物。没有合适资产时，再向用户申请创建一个纯配置测试物 Blueprint；不能因此向轻受击逻辑添加箱子分支。

## 7. 为什么这不是箱子特判

效果实现只包含：

```text
九个上半身刚体提前 Simulated
ParentSpace Controls 持续追随 Idle
Mesh 阻挡真实物理物体
```

它没有来源接口。另一个物体若是 Simulate Physics 且与 Mesh 双向 Block，就具备进入同一次 Chaos 接触求解的条件：

- 磁力箱可以撞；
- 未来真实物理气罐可以撞；
- 其他普通刚体也可以撞。

双向 Block 本身不保证画面一定明显。Physics Asset 形状、实际模拟状态、质量比、速度、CCD、控制强度和 Chaos 求解都会影响结果；能否得到可见且合理的双向响应，正是本原型要验证的事情。

地刺这类目前只有 Overlap / Damage 的机关没有真实运动刚体，所以不会因为这套效果自动获得物理动量。以后必须单独决定它继续只做玩法 Stop / Slow，还是由机关提供一个明确的物理力；该决定不改变角色侧身体控制原理。

## 8. 第一轮测试

固定 60 FPS：

1. 静置 Controlled 目标十秒，确认没有持续下垂、抖动或尸体感；
2. 用同类物体分别砸 Kinematic 和 Controlled 的胸口；
3. 再砸 Controlled 的左肩、右肩；
4. 每个位置至少三次；
5. 必要时只在同一 PCA 中更改一组 Strength / Damping 参数并重启测试。

必须由用户画面判断：

- 外物相对 Kinematic 对照是否明显失速、偏转或改变旋转；
- 命中 Body 与相邻关节是否按真实方向让位；
- spine_01、pelvis、腿和脚是否稳定；
- 上半身是否依靠持续控制自然回到 Idle；
- 是否出现全身软掉、Human Fall Flat 式移动或瞬间闪切。

## 9. 技术验证

- 官方 MCP 回读 PCA：Physics Asset、四条 Limb、无腿部/Heavy 残留、默认 Parent Control 和 Body Modifier；
- 官方 MCP 回读 Blueprint：Mesh、Physics Asset、Idle、碰撞、PhysicsControlAsset、唯一 BeginPlay 分支；
- PCA Compile / Save 成功；Blueprint 创建节点返回 true；
- Blueprint 编译时 Warning 视为 Error，并保存资产；
- PIE/SIE 确认运行时恰好创建九个 Body Modifier，并且对应九个上半身 Body 已模拟；缺少或多出任意一个都不得进入画面验收；
- 观察测试物确实与 Mesh Physics Asset 阻挡，而不是与不存在的 Capsule 接触；
- 由于没有新增 C++，仍可在关闭编辑器后执行一次 `-Module=Demo -NoEngineChanges` 构建，确认共享工程没有编译回归。

## 10. 止损条件

出现任一项立即停止，不继续堆内容：

- 需要给角色补 `AddImpulse` 才能看到效果；
- 需要 Montage 遮盖恢复；
- 需要启用 pelvis 或腿部模拟；
- 需要识别箱子、磁力组件或具体机关；
- 需要 Hit 状态机、ImpactId、预测、租约或恢复 Timer；
- 三组参数内仍只有可有可无的摆动，或持续下垂/抖动；
- 为了测试开始修改生产 Heavy、磁力、破碎、玩家或追猎者。

## 11. 效果通过后的生产阶段

效果通过只证明“来源无关的局部上半身 Physics Control 画面成立”。它不能直接证明任何生产架构。随后另开方案，依次比较：

1. 使用正式追猎者 ABP 验证移动和攻击姿势，而不是继续固定 Idle；
2. 比较普通可受击状态局部常开与通用短时预激活；
3. 如何避免 Light 与 Heavy 同时写同一身体，以及 Heavy 是否应保持最高优先级；
4. 玩家骨架单独装配并验证；
5. 各机关与角色身体层之间最窄的输入边界，区分真实碰撞、持续力和纯玩法状态。

生产共享组件是否需要抽取，也只在这一步根据实际重复职责决定。当前倾向是让单一身体控制层拥有 Skeletal Mesh、Physics Control Records 和身体模式切换，但这仍需结合 Heavy 等价回归后评估；原型阶段不创建、不迁移、不预留接口。
