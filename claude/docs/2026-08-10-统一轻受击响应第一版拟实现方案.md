- Owner：Codex `/root`
- 日期：2026-08-10
- 状态：代码落盘前的讨论稿；**尚未获得 Source / Config / Blueprint / DataAsset 实现授权**
- 目标：让玩家与追猎者共享同一套轻受击接收和状态优先级，同时允许同一机关对两者产生不同的站立结果；现有 HeavyImpact 继续作为已验收的重受击执行权威。
- 审计处理：已完整阅读 `claude/reviews/2026-08-10-统一轻受击响应第一版方案审计.md` 并逐条取舍；本版已吸收速度恢复、AI 路径、磁力事务、单一类别权威与测试边界等成立意见，审计报告在代码实施和验证完成前保持未归档。

> 文中的 `CharacterImpactResponse`、`ReceiverCategory` 等都是本项目拟用名称，不是 UE 官方系统名称。UE 官方能力仍是 CharacterMovement、Anim Montage、Chaos 碰撞与现有 Physics Control。

## 1. 先给结论

第一版采用：

```text
机关或物体提供来源配置与真实命中数据
                │
                ▼
    角色侧 CharacterImpactResponse
      ├─ 读取玩家/追猎者对应栏
      ├─ 执行 None / Slow / Stop
      ├─ 播放可选轻受击动画
      └─ Heavy 到来时先恢复轻受击改过的速度，再清除轻受击
                │
                ▼
      现有 HeavyImpactResponse
      独占 PCA、击飞、倒地、起身
```

这里的“对应栏”只是：

| 接收者 | 当前例子 |
|---|---|
| 玩家 | Stop |
| 追猎者 | Slow |

它不是自动判断算法，也不会生成 `玩家停顿接口`、`AI减速接口` 等组合。来源只提交一次统一请求，接收组件自行选取对应栏。

## 2. 为什么不让机关单独决定，也不让角色单独决定

### 只让机关决定的问题

- 地刺代码会开始判断玩家、追猎者并硬编码分支。
- 以后增加敌人类型时，每个机关都要修改。
- 机关容易直接改角色速度、AI路径和动画，破坏状态所有权。

### 只让角色决定的问题

- “玩家软、AI硬”的全局规则会覆盖具体玩法。例如玩家遇到气流想减速，遇到地刺却可能想停顿。
- 用户尚未看齐各机关效果，现在提取全局硬度会过早固化策划。
- 同一个角色面对不同来源仍需要不同结果，最终还会补来源特判。

### 第一版选择

- **来源配置决定玩法意图**：对玩家与追猎者分别填 `None / Slow / Stop`。
- **角色组件决定执行方式**：怎样改移动、怎样恢复、怎样处理动画和 Heavy 抢占。
- **物理数据决定连续细节**：方向、接触位置、减速深度和持续时间；第一版动画幅度不做连续缩放，也不允许原始冲量自行把 `Slow` 升级为 Heavy。
- **角色全局硬度暂不实现**：等至少三个来源现场验证后，如果确实反复出现“追猎者统一更抗打”的规律，再增加角色侧倍率或上限。

## 3. 第一版刻意限制的结果集合

拟定义一个站立结果枚举：

```cpp
UENUM(BlueprintType)
enum class EStandingImpactResult : uint8
{
    None,
    Slow,
    Stop
};
```

不把 Heavy 放入这个枚举。原因不是否认以后会调整策划，而是当前 Heavy 有真实能力前提：

1. 来源必须在接触前提交预测；
2. 来源必须有将参与碰撞的动态刚体组件；
3. 真实 Chaos 接触必须在准备后到达；
4. HeavyImpact 本身不制造假冲量。

摆锤、冲锤已经满足；当前地刺不满足。用户已确认本轮地刺只做站立 `Slow / Stop`，不做物理击飞，也不预埋脚本击飞。地刺以后若要真实击飞，必须届时另行选择：

- 把刺改成可预测、会真实顶撞角色的运动刚体；或
- 明确新增一种脚本击退执行器。

第一版不会放一个地刺实际上执行不了的 `Heavy` 选项，也不会用 `LaunchCharacter` 冒充真实撞击。

## 4. 数据合同

### 4.1 接收者类别

```cpp
UENUM(BlueprintType)
enum class EImpactReceiverCategory : uint8
{
    Player,
    Pursuer
};
```

第一版只有当前项目真实存在的两类角色，不引入 GameplayTag 规则树、任意 `TMap` 或可嵌套条件。以后新增正式敌人类别时再扩展枚举；没有专用栏的角色应拒绝请求并记录原因，不静默猜测。

类别只有一个运行时权威：玩家/追猎者 C++ 在装配组件时分别传入固定的 `Player / Pursuer`，该值不暴露给 Blueprint，也不再在 Tuning DataAsset 中复制一份。来源 Profile 只按这个不可编辑类别选栏。

### 4.2 单栏反应规格

```cpp
USTRUCT(BlueprintType)
struct FStandingImpactReactionSpec
{
    UPROPERTY(EditAnywhere, BlueprintReadOnly)
    EStandingImpactResult Result = EStandingImpactResult::None;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, meta = (ClampMin = "0.0", Units = "s"))
    float DurationSeconds = 0.0f;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, meta = (ClampMin = "0.0", ClampMax = "1.0"))
    float SpeedMultiplier = 1.0f;

    UPROPERTY(EditAnywhere, BlueprintReadOnly)
    bool bPlayReactionAnimation = false;
};
```

约束：

- `None`：Duration 为 0，SpeedMultiplier 为 1。
- `Slow`：SpeedMultiplier 必须在 `(0, 1)`。
- `Stop`：执行时速度视为 0，不调用 `DisableMovement`。
- 配置资产必须在编辑器和运行时验证非法组合并输出明确字段名。

### 4.3 来源配置资产

```cpp
UCLASS(BlueprintType)
class UCharacterImpactSourceProfile : public UDataAsset
{
    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
    FStandingImpactReactionSpec PlayerReaction;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
    FStandingImpactReactionSpec PursuerReaction;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, meta = (ClampMin = "0.0"))
    float MinimumPhysicalImpulse;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, meta = (ClampMin = "0.0"))
    float FullStrengthPhysicalImpulse;
};
```

第一版使用两个明确的接收者字段，不做组合表编辑器、不做优先级规则、不做继承链。后两个物理阈值只供磁力投掷这类真实模拟刚体来源归一化强度；地刺等触发来源直接提交作者强度，不读取它们。`FullStrengthPhysicalImpulse` 必须大于 `MinimumPhysicalImpulse`。

建议首轮资产初值：

| 来源 Profile | PlayerReaction | PursuerReaction | 用途 |
|---|---|---|---|
| MagneticThrown | None | Stop | 先验证磁力物真实撞击 AI；玩家不是当前主要目标 |
| SpikeTrap | Stop | Slow | 第二验收点，验证同一来源对两类角色的不同站立结果 |

这只是 DataAsset 初值，不会写进机关或角色 C++。用户以后交换 `Stop / Slow / None` 不需要改接口。

### 4.4 角色执行调参资产

玩家与追猎者各使用一份 `UCharacterImpactTuningData`。第一版明确使用各自骨架的底层 `UAnimSequenceBase`，两边都由组件在已有 `DefaultSlot` 上创建 Dynamic Montage；不同时支持 Sequence/Montage 两套互斥分支。

```cpp
UCLASS(BlueprintType)
class UCharacterImpactTuningData : public UDataAsset
{
    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
    TObjectPtr<UAnimSequenceBase> FrontReaction;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
    TObjectPtr<UAnimSequenceBase> LeftReaction;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
    TObjectPtr<UAnimSequenceBase> RightReaction;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, meta = (ClampMin = "0.0", Units = "s"))
    float MontageBlendInSeconds;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, meta = (ClampMin = "0.0", Units = "s"))
    float MontageBlendOutSeconds;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, meta = (ClampMin = "0.01"))
    float MontagePlayRate;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, meta = (ClampMin = "0.0", ClampMax = "1.0"))
    float MinimumStrengthDurationScale;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, meta = (ClampMin = "0.0", Units = "s"))
    float MaxContinuousLightSeconds;
};
```

- 追猎者三方向引用现有三条底层 Sequence，不读取旧 `UPursuerConfig` 里的 Montage 字段。
- 玩家不再使用 Rifle 目录下的 Local-space Additive 候选；改为把追猎者三条非 Additive Sequence 复制后替换为玩家 `CH_SciFiTrooper_Man_03_Skeleton`，分别填入玩家三方向字段。
- 若玩家重定向资产尚未完成，三字段保持空并明确记录“玩家动画未覆盖”；玩法状态仍可验证，但不能把玩家受击画面标成已验收。
- `MaxContinuousLightSeconds` 只限制一次连续 `LightActive` 窗口，防止同一窗口被不断刷新；V1 不承诺跨投掷、跨地刺周期的免疫，也不预建通用冷却。若现场真的出现同一机关连续锁死，再增加来源级保护。
- `CharacterImpactTuningData.h` 直接包含 `Animation/AnimSequenceBase.h`；这些反射字段不能只靠前向声明或省略 `UPROPERTY`。

### 4.5 一次命中请求

```cpp
USTRUCT(BlueprintType)
struct FStandingImpactRequest
{
    UPROPERTY()
    FGuid ImpactId;

    UPROPERTY()
    TObjectPtr<AActor> SourceActor;

    UPROPERTY()
    TObjectPtr<UPrimitiveComponent> SourceComponent;

    UPROPERTY()
    TObjectPtr<UCharacterImpactSourceProfile> SourceProfile;

    UPROPERTY()
    FVector WorldDirection;

    UPROPERTY()
    FVector ImpactPoint;

    UPROPERTY()
    float NormalizedStrength = 1.0f;

    UPROPERTY()
    FVector RawNormalImpulse;
};
```

- `ImpactId` 标识一次来源事件，防止一次 Chaos 接触产生多骨骼、多回调重复受击。
- `WorldDirection` 表示身体被推向哪里，而不是表面法线的模糊正负号。
- `NormalizedStrength` 由具体来源用可解释的范围得到。磁力物只在自身来源 Profile 的冲量区间内归一化，地刺直接提交策划值；不跨来源使用一条“万能冲量公式”。
- `RawNormalImpulse` 只用于诊断和后续调参，不作为跨来源通用判级公式；Overlap 来源可为空。
- 伤害值不放入此请求，生命结算仍由 `HealthComponent / ApplyDamage` 负责。

第一版只保留一个强度权威：`EffectiveStrength = Clamp(Request.NormalizedStrength, 0, 1)`。

- `Slow`：在 1.0 与配置的 `SpeedMultiplier` 之间按 EffectiveStrength 插值；越强减速越明显。
- `Stop`：始终把移动速度压到 0，但有效持续时间随强度缩放。
- 两者持续时间均为 `DurationSeconds * Lerp(MinimumStrengthDurationScale, 1, EffectiveStrength)`。
- 强度不把 `Slow` 自动升级成 `Stop`，也不进入 Heavy。
- 第一版动画幅度不按强度连续缩放；物理数据先负责方向选择和玩法强度，避免为调 Montage 权重再扩写 AnimGraph。

## 5. 运行时组件与状态所有权

新增一个 `UCharacterImpactResponseComponent`，同时装配到玩家和追猎者。它不是 UE 官方类，而是本项目的受击协调组件。

它拥有：

- 当前轻受击是否活动；
- 当前来源与 `ImpactId`；
- 轻受击结束 Timer；
- 本组件写入前的移动速度快照；
- 本组件最后写入的速度；
- 当前轻受击 Montage 弱引用；
- 由玩家/追猎者 C++ 装配时传入、运行中不可编辑的接收者类别，以及角色侧轻受击调参资产；
- 对现有 `UHeavyImpactResponseComponent` 的非拥有引用。

它不拥有：

- Heavy 状态副本；
- PCA 记录；
- 倒地、起身和同机关 Heavy 保护；
- 伤害或生命值；
- AI决策状态。

状态只需要：

```text
Inactive
  └─ 接受 Slow / Stop ───────────────► LightActive

LightActive
  ├─ 更强或更新的有效轻命中 ────────► 替换并重算有界结束时间
  ├─ 相同 ImpactId 的重复回调 ───────► 忽略
  ├─ Heavy 进入 Prepared ────────────► 安全恢复速度基线，再清除 → Inactive
  └─ Timer 到期 ─────────────────────► 恢复 → Inactive

Heavy Busy
  └─ 任意轻命中 ─────────────────────► 拒绝，不排队
```

重复命中规则：

- 同一 `ImpactId` 只接受一次。
- 请求在命中当帧即时处理，不增加 NextTick 缓冲。不同来源同帧到达时按 `Stop > Slow > None` 即时升级/忽略；同级比较 EffectiveStrength，因此调用顺序不会让弱结果覆盖强结果。
- `Stop` 可以升级活动中的 `Slow`；`Slow` 不能把 `Stop` 降级。
- 同级命中不叠加速度倍率、不重播动画，只更新最新有效方向和较强强度。
- 首次接受轻受击时记录 `LightWindowStartTime`；后续刷新后的结束时间不得超过 `LightWindowStartTime + MaxContinuousLightSeconds`。
- 不跨来源累计冲量，不让两个弱来源偶然合成 Heavy。
- Heavy 进入 `Prepared` 时必须先执行与正常结束相同的速度恢复判据：仅当当前 `MaxWalkSpeed` 仍等于 Light 最后写入值时，恢复进入 Light 前的快照；然后再一次性清除 Active Light、Active Montage 与轻受击结束 Timer。Heavy 结束后不重放此前活动的轻受击。

## 6. 与现有 HeavyImpact 的兼容方式

现有 `IHeavyImpactReceiver` 暂不删除，摆锤、冲锤与制导机关也不迁移。两个角色继续把现有 Heavy 接口直接转发给 `UHeavyImpactResponseComponent`；不为了“统一入口”增加一层纯转发函数。新的协调组件只订阅 Heavy 状态变化：

```text
旧 Heavy 机关
   │ IHeavyImpactReceiver::PrepareForHeavyImpact
   ▼
角色
   └─ 直接转发给现有 HeavyImpactResponse::PrepareForImpact

HeavyImpactResponse 真正进入 Prepared
   └─ OnStateChanged 同步通知总协调组件
      └─ 先安全恢复 Light 速度快照，再原子清除 Active Light、动画与结束 Timer
```

不能在调用 Heavy 前预先清 Light。`Busy / Invalid / Duplicate / TooLate` 等被拒绝请求不得破坏当前轻受击；只有现有 Heavy 组件真实进入 `Prepared` 后才能抢占。现有 Heavy 不读写 `MaxWalkSpeed`，因此速度回滚仍由 Light Owner 完成。V1 不排队轻受击：Heavy Busy 时新请求当场拒绝，因此 Heavy 结束后不存在旧请求补交。

这仍然是两个外部接口，但不是按玩家、AI或效果组合拆分：

- 轻受击是命中确认后的即时请求；
- Heavy 是真实碰撞前的两阶段准备请求。

两者生命周期不同，强行塞进一个带大量 `Phase / Optional` 字段的接口只会增加误用。运行时的角色总协调仍只有一个，Heavy 内部状态权威仍只有现有组件一个。

## 7. 移动效果

### Slow

- 开始时记录当前 `MaxWalkSpeed`。
- 写入 `BaselineSpeed * SpeedMultiplier`。
- 不清空速度；玩家继续移动和转向，AI继续寻路。

### Stop

- 调用 `StopMovementImmediately()` 清除已有平移速度。
- 暂时写入 `MaxWalkSpeed = 0`。
- 不调用 `DisableMovement()`，避免覆盖 Heavy 的 MovementMode 快照与恢复。

### 恢复

- 若当前 `MaxWalkSpeed` 仍等于本组件最后写入值，恢复进入轻受击前的快照。
- 若已被别的系统修改，记录冲突并不盲目覆盖新值。
- 正常 Timer 结束、被 Heavy `Prepared` 抢占、组件停用和 EndPlay 都必须走同一个恢复入口；“清状态”不能绕过速度恢复。
- 第一版不提前建立毒、冰冻、Buff 的通用移动修正栈；当前项目还没有第二个正式运行时减速 Owner。以后真出现并行写入，再抽取统一修正栈。

### 玩家输入规则（用户已确认）

- `Slow`：保留移动、视角、跳跃、磁力操作。
- `Stop`：停止位移与跳跃，拒绝新抓取和投掷；保留相机与松手释放，避免手中物体被锁死。

### AI规则（用户已确认）

- `Slow`：立即打断当前攻击并禁止轻受击期间发起新攻击，但 AI 继续按降低后的速度寻路。
- `Stop`：立即打断当前攻击、禁止新攻击，并由 `PursuerAIController::StopMovement()` 取消当前 PathFollowing 请求；不能只把 `MaxWalkSpeed` 设为 0 后留下零进度路径请求。
- `Slow` 绝不调用 Controller `StopMovement()`；Light 结束后 `Stop` 最多等待现有 `ThinkInterval`（默认 0.2 秒）才重新发起追击，这是预期行为。
- Heavy：继续完全阻止移动和行动。
- 因此不能再用现有一个 `IsReacting()` 同时代表“不能移动”和“不能攻击”。追猎者需要分别暴露“移动是否被阻止”与“攻击是否被抑制”，AI Controller 也要分别读取。
- 新查询不读取旧 `bIsReacting / IsReacting()` 死路径；旧字段只为回退保留，不赋予新语义。

## 8. 第一版画面策略

### 已由官方 MCP 验证的真实资产情况

- 玩家运行时 AnimBP：`/Game/ZeroEscape/Characters/Animation/ABP_Player_Unarmed_HeavyImpact`
- 追猎者 AnimBP：`/Game/ZeroEscape/Enemies/Animation/ABP_Pursuer_Locomotion`
- 两者都继承 `UHeavyImpactAnimInstance`，且 AnimGraph 已有全身 `DefaultSlot`；官方 MCP 回读的真实链分别是玩家 `StateMachine → ControlRig → DefaultSlot → Heavy Pose Blend`、追猎者 `BlendSpace → DefaultSlot → Heavy Pose Blend`。
- 两者骨架不同，不能共享同一动画资产。
- 第一版只在 `Stop` 播放全身反应，`Slow` 默认不播这组三条全身动画，因此现有 `DefaultSlot` 就是合适入口，无需修改两个 AnimBP。使用 Dynamic Montage 仍然经过 AnimBP Slot，并不是绕开 AnimBP。

### 追猎者候选（用户已确认是这三条方向动画）

- `MM_SciFi_Character_08_standing_react_large_gut`
- `MM_SciFi_Character_08_standing_react_large_from_left`
- `MM_SciFi_Character_08_standing_react_large_from_right`

它们无 Root Motion，但都是非 Additive 的全身大反应，长度约 1.0～1.77 秒。Front/Left/Right 语义沿用旧 `DA_Pursuer` 配置，真实方向观感仍需现场 A/B。第一版由组件从底层 Sequence 创建 Dynamic Montage：

- `Stop` 可按方向播放并在轻受击窗口结束时 Blend Out；
- `Slow` 默认不播放这组三条，防止移动脚滑；
- 若现场仍显得过重，就关闭动画，不让逻辑依赖它们。

### 玩家候选

不再使用 `/Game/Characters/Mannequins/Anims/Rifle/HitReact/MM_HitReact_Front_Lgt_01..04`。审计确认它们是以持枪局部姿势为基准的 Local-space Additive，且资产骨架不是玩家 Mesh 的 `CH_SciFiTrooper_Man_03_Skeleton`；这不是值得赌的调参风险。

玩家改用追猎者三条非 Additive Sequence 的玩家骨架副本：

- `/Game/ZeroEscape/Characters/Animation/MM_Player_standing_react_large_gut`
- `/Game/ZeroEscape/Characters/Animation/MM_Player_standing_react_large_from_left`
- `/Game/ZeroEscape/Characters/Animation/MM_Player_standing_react_large_from_right`

这复用已经由 GetUp 验收过的项目流程：复制追猎者 Sequence → 对副本执行“替换骨架”为 `CH_SciFiTrooper_Man_03_Skeleton` → 重命名/移动 → Persona 预览 → Save All。官方 MCP 已回读现有玩家 GetUp 产物正是 `CH_SciFiTrooper_Man_03_Skeleton`、非 Additive、无 Root Motion，并且 `retargetSourceAsset` 来自追猎者 Mesh；用户已确认两套骨骼的最终效果可接受。

官方 MCP 当前没有安全的 Replace Skeleton / IK Retarget 操作，也不能代替 Persona 的动作观感判断。因此这三条的“复制后替换骨架、预览、保存”由用户按 GetUp 相同步骤手动完成；AI 不会用构造期路径、Skeleton Compatibility 或未经验证的 additive 资产绕过。AI可在用户完成后用官方 MCP回读最终骨架、Additive类型、Root Motion、路径和 dirty 状态，再装配 DataAsset。

### 为什么 V1 不改 AnimBP

- 当前优先画面是磁力命中追猎者 `Stop`、地刺命中玩家 `Stop`；角色本来就停止，全身 `DefaultSlot` 合理且不会损失移动腿部表现。
- 地刺对追猎者的 `Slow` 第一版只验证减速与攻击打断，默认不播全身大反应，避免滑步。
- 当以后明确要求玩家或 AI 在 `Slow` 中“腿继续走、上半身明显受击”时，才进入 V2：在两套 AnimBP 正常增加轻受击上半身分层（例如专用 Slot + `Layered Blend Per Bone`，从 `spine_01` 开始），并由用户在 Slot Manager/Persona 完成人工配置与画面验收。届时不会用 C++ 骨骼偏移冒充该 ABP 工作。
- UE 官方文档也把全身 Slot 用于覆盖式全身动作，把上半身 Slot 与 `Layered Blend Per Bone` 用于保留下半身 locomotion；本版按真实需求选择前者，而不是因为 MCP 难操作才回避后者。

### Slot 抢占

- Light 只记录并停止自己启动的 Montage。
- 只有 `OnStateChanged` 确认真正进入 `Prepared` 时，才用零 BlendOut 即时停止精确的 ActiveLightMontage 并清动画事务；不能让已暂停的 Montage 残留到起身阶段。
- Heavy 忙碌时不播 Light。
- 追猎者 `PlayAttackMontage()` 成功后必须记录精确的 ActiveAttackMontage，并在正常结束回调中清空；`Stop` 与 `Slow` 都通过角色提供的定向中断函数只停止该攻击 Montage，禁止调用无差别的 `Montage_StopAll`。
- 新组件不调用旧 `HandleHitReact()`，旧 `bIsReacting`/旧 Montage EndDelegate 路径继续保持未装配，避免两个状态 Owner 争用同一动画回调。
- Light Montage 的 EndDelegate 只清动画句柄；Slow/Stop 的玩法 Timer 才是状态时长权威。动画提前结束或被打断不得提前恢复移动。
- Light 与攻击 Montage 的结束回调都必须比较 `EndedMontage == 当前记录的 Montage`，Light 最好再比较事务序号；旧 Montage 被新 Montage 打断后的迟到回调不得清掉新句柄。

第一版不新增程序化骨骼 AnimGraph，也不重新启用局部 Physics Control。原因是两者真正风险在双骨架调姿和脚底稳定，代码与节点不多，但现场调参成本高；先用现成动画做可关闭 A/B，更快判断画面是否成立。

## 9. 来源接入分两个验收点（磁力物优先）

### A. 磁力投掷物：第一条纵向切片，验证真实物理输入

磁力物由来源侧在真实 `OnComponentHit` 时主动提交，不能让角色每帧扫描世界。一次投掷保持同一个 `ImpactId`，第一次有效命中角色后消费。

每次投掷事务由 `UMagneticObjectComponent` 唯一拥有：攻击碰撞快照、`ImpactId`、根刚体 Hit Delegate、攻击 Tag、成员 `FTimerHandle` 与结束清理都放在这里。`UElectromagneticGrabComponent` 缓存目标后严格执行“释放 PhysicsHandle → 调用一次 `ArmThrownImpact()` → `AddImpulse`”；现有 Grab 内部使用函数局部 Timer Handle 的 AttackProjectile Tag Timer 迁移到该事务并删除，这同时修复“重新抓取/再次投掷时旧 Timer 无法取消”的既存缺陷。

V1 只有 Light 一个根 Hit 消费者，不为尚未落盘的磁力破碎预建消费者登记、引用计数或分发总线。若破碎以后实际接入，第二个功能在落盘前必须把两个监听收口为单一根 Hit Owner；不能直接在当前事务旁边再绑定一套 Delegate/通知快照。这个兼容门槛保留在并行章节，但不转化为本轮代码。

`ArmThrownImpact()` 返回 `bool`：先完整校验 Primitive、模拟物理、CollisionEnabled 与来源 Profile，再开始修改。任一步失败都立即走幂等回滚，不留下 Tag、Timer、Delegate 或专用通道；抓取组件记录原因但仍照常施加本次投掷冲量，只是这次没有轻受击事务。

当前追猎者 Capsule 忽略 `PhysicsBody`，Mesh 在普通状态又是 QueryOnly，所以不能假设“绑定角色 Mesh OnHit”就会自动工作。`UMagneticObjectComponent` 将从“纯身份配置组件”升级为“磁性身份 + 单次正式投掷受击事务 Owner”；实施时必须同步重写其文件头职责、边界和状态 Owner 注释。第一版采用以下可回退策略：

- 在 `DemoCollisionChannels.h` 中把首个未占用的 `ECC_GameTraceChannel1` 定义为项目常量 `AttackProjectileBody`，并在 `DefaultEngine.ini` 注册为默认 Block 的 Object Channel（不是 Trace Channel）；它与现有 Actor Tag `AttackProjectile` 是两个不同机制；
- 为处于攻击有效期的磁力投掷物临时使用 `AttackProjectileBody`；
- 该通道默认由 WorldStatic/WorldDynamic 阻挡，玩家与追猎者 Capsule 永久阻挡；普通松散 PhysicsBody 继续走原通道并被角色忽略，避免 AI 被杂物卡住；
- 投掷开始时快照 CollisionProfileName、CollisionEnabled、ObjectType、完整 ResponseContainer、CCD 与原始 Hit 通知，切入攻击碰撞状态并生成一个 `ImpactId`；UE 切换 ObjectType 后会把 Profile 视为 Custom，不能只恢复一个 ObjectType；
- Arm 只接受仍在模拟物理且 CollisionEnabled 含 Physics 的 Primitive，并临时确保 Pawn 双向 Block、`SetNotifyRigidBodyCollision(true)` 与 `SetUseCCD(true)`；当前 2500 cm/s 投掷速度不能省略 CCD；
- 该来源是模拟刚体阻挡命中，使用 `NormalImpulse.Size()` 与来源 Profile 的 `MinimumPhysicalImpulse / FullStrengthPhysicalImpulse` 计算 `NormalizedStrength`；低于最小阈值不提交轻受击，不能在组件里硬编码神秘除数；
- 请求的 `WorldDirection` 必须表示目标被推走的方向，优先使用 `-Hit.ImpactNormal`；法线异常时才使用取反并经点积校正的 `NormalImpulse` 方向。禁止使用命中回调后的物体速度，因为物体可能已经反弹；
- 首次有效角色命中、攻击有效期结束、被重新抓取、再次武装、组件/Owner EndPlay、Primitive 失效都进入同一个幂等 `DisarmThrownImpact()`；它清成员 Timer、解绑根 Hit Delegate并精确恢复完整快照，重复调用无副作用；
- 不在物理 Hit 回调中途直接改变同批接触的碰撞状态；首次有效角色命中只标记已消费，并安排下一安全时点恢复快照、解绑 Delegate；
- Heavy Busy 时总协调明确拒绝 Light；Heavy 状态下投掷物是否仍被当前角色外壳物理阻挡，按现有 Heavy 碰撞状态处理，不作为 V1 合同，也不为此暗改 Heavy；
- 同一投掷物命中墙面后是否仍保留攻击性，沿用当前攻击有效期规则，不在轻受击系统里猜测。

拟新增配置：

```ini
[/Script/Engine.CollisionProfile]
+DefaultChannelResponses=(Channel=ECC_GameTraceChannel1,DefaultResponse=ECR_Block,bTraceType=False,bStaticObject=False,Name="AttackProjectileBody")
```

`DefaultResponse=ECR_Block` 通常会让未显式覆盖新通道的 Collision Profile 继承 Block，但这只是引擎默认机制，不替代验证。新增通道后必须重启 Editor，再通过官方 MCP 回读玩家/追猎者 Capsule、两者 Mesh 与磁性物体的实际通道响应；不能在旧 Editor 会话里假设通道已经加载。Mesh 是否 Block 只作为 Heavy 共存诊断，不把它升级为本版 Heavy 合同。

来源同时保存投掷者弱引用：有效期内与投掷者自身发生物理接触仍按碰撞正常处理，但不提交轻受击请求，避免物体刚从持有点释放就先把玩家停住。第一次阻挡命中任何实现统一接收接口的其他角色后，本次请求都视为已消费；即使接收端正在 Heavy、该栏为 None 或返回重复，也不能让物体卡在外壳边缘持续重试。

当前磁力候选查询只搜索 `PhysicsBody`。攻击有效期内物体临时属于专用通道，因此 `FindBestCandidate` 必须用默认构造的 `FCollisionObjectQueryParams`，再分别 `AddObjectTypesToQuery(ECC_PhysicsBody)` 与 `AddObjectTypesToQuery(AttackProjectileBody)`；`CanGrab()` 仍要求目标正在模拟物理。若玩家重新抓取仍在攻击状态的物体，`GrabCandidate()` 必须在写入 `HeldComponent`、阻尼或 Pawn/Camera 碰撞等任何抓取快照之前先调用 `DisarmThrownImpact()`，不能只保证在 `PhysicsHandle->GrabComponentAtLocation()` 前恢复。磁性物体 Blueprint 静止默认仍保持 PhysicsActor/PhysicsBody，不把资产永久改成攻击通道。

绑定顺序必须是：释放 PhysicsHandle → Arm（切通道、开 Hit 通知与 CCD、绑定 OnHit）→ `AddImpulse`。否则高速物体可能在 Delegate 建立前已经发生首次碰撞。

不推荐把角色 Skeletal Mesh 永久恢复为 QueryAndPhysics 来监听所有物体，因为这会重新引入多骨骼接触、移动推物、抖动和 Heavy 基线冲突风险。

这一条必须先证明：物体真实撞到角色、会反弹或停留，角色反应方向与接触一致，而不是物体穿过角色后由代码凭空播放受击。

### B. 地刺：补充验证策划对应表与状态恢复

当前地刺有可靠的危险相位和 Overlap，适合在磁力物之后补充证明同一 Profile 可以做到：

- 玩家：Stop；
- 追猎者：Slow；
- 两者都保持站立；
- 重叠期间不会每帧重启反应；
- AI受反应但当前不要求扣血。

地刺提交的方向为向上，强度为作者配置值。它只能验证策划结果和状态，不作为真实物理冲量验证。

## 12. 自动化与现场验收

### 自动化测试

至少覆盖：

1. 同一来源 Profile 对玩家、追猎者选取不同栏。
2. `Slow / Stop / None` 参数校验。
3. 相同 `ImpactId` 不重复触发。
4. 同一次连续 Light 窗口不会超过最大占用时间；不把不同投掷/不同地刺周期误当成同一窗口。
5. Heavy Prepared 先把 `MaxWalkSpeed` 恢复到 Light 前基线，再清 Active Light、Active Montage 与结束 Timer；Heavy Busy 当场拒绝 Light，Heavy 结束后不得补交旧请求。
6. Light 清理不恢复已被第三方改写的速度。
7. 组件结束、角色销毁和 Montage 中断时无悬挂 Timer/Delegate。
8. 来源无 Profile、方向非法、强度非法时明确拒绝并记录原因。
9. 不依赖物理步进的磁力事务状态：Arm 前置校验、完整快照结构、成员 Timer 清理、幂等 Disarm、一次消费与无效接收结果不重试。
10. 磁力候选查询参数同时包含 PhysicsBody 与 AttackProjectileBody；重新抓取调用顺序在任何抓取快照之前先 Disarm。
11. `AttackProjectileBody` 配置名称确实对应 `ECC_GameTraceChannel1` 且是 Object Channel。
12. 来源 Profile 缺失、Primitive 非模拟、CollisionEnabled 不含 Physics 或作者阈值非法时，Arm 明确拒绝且不留下半套事务。
13. 同帧请求按 `Stop > Slow > None` 和强度即时升级/忽略；弱结果不能覆盖强结果，也不引入一帧延迟。

上述瞬态测试 World 不进行真实 Chaos 物理步进，因此不会为了“自动化覆盖率”制作假的 OnHit/CCD Mock。真实 `OnComponentHit`、高速 CCD 防穿透、Capsule 实际 Block、投掷物反弹/停留、重新抓取完整流程与碰撞快照最终回读全部放入下面的 PIE/MCP 验收。

### 现场 A/B

1. 磁力物从正面、左右和斜擦命中，物体真实被角色外壳阻挡，反应方向稳定且同一物体不连续刷反应。
2. 地刺 B 验证玩家 Stop：期间镜头与松手可用，移动、跳跃、新抓取和投掷被锁；结束后全部正确恢复。
3. AI Slow 继续寻路但速度明显下降；AI Stop 不再追击；二者都立即打断当前攻击并禁止轻受击期间发起新攻击。
4. AI与玩家各自三方向动画开/关对比；玩家使用已手工替换骨架的非 Additive 副本。若玩家资产尚未制作，只能验收玩法状态，玩家画面保持“未覆盖”，不能用 Rifle additive 代替。
5. Light 活动中被摆锤/冲锤命中，Heavy 立即接管；起身后没有残留减速或旧动画。
6. 30/60/120 fps 各验证一次磁力物命中，不允许因帧率改变玩法结果。
7. 地刺同时命中玩家和AI：按来源 Profile 分别 Slow/Stop，均不倒地、不制造冲量。
8. PCG 只负责放置原机关类；生成多份地刺时每个实例使用同一 Profile，不新增每实例 Tick。
9. 磁力物仍正常撞墙、地板和其他刚体；有效期内可重新吸回，吸回后不再触发受击，到期后恢复为 PhysicsBody 并可正常选择。
10. 物体从持有点释放时不会对投掷者自触发；方向没有左右/前后取反。
11. AI Stop 取消当前 PathFollowing；Light 结束后允许在下一次 Think（默认最多约 0.2 秒）重新追击，不把这段事件驱动延迟误判为卡死。

## 13. 并行、回退与 Git 门禁

- 当前共享工作区仍可能存在审计或其他机关文档改动；本任务不覆盖、不移动、不提交并行文件。在用户授权实现后，首次改功能文件前必须重新检查归属，并按项目规则完成全工作区基线 commit/push、远端核验和干净状态。
