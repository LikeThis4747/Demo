## 一、结论先行

**你的三个点子不是「两个玩法」，而是一条完整的玩法主线加一个能力，且比我 v2 的方案更省工。**

三项合计我估 **1.5 天**，不是 3 天。理由在第三节的技术核实里。

但 4 天装不下「全部新玩法 + 两项未完成功能 + L4 感知层 + 打包」。**必须砍东西**，我在第六节给出明确取舍建议。

## 二、你的设计比我的好，三处改进

### 改进一：守场落在终点房间（关门），而不是散布装置

这是**减法**，而且解决了我方案里最脏的一块。

| | 我的 v2（散布装置 + 警戒圈） | 你的方案（终点房间 + 关门） |
|---|---|---|
| PCG 工作 | 要新增装置点生成规则、间距约束、可达性验证 | **零**，复用现有 Exit 位置 |
| 边界状态机 | 出圈暂停 → 回来继续，要写状态与进度保留 | **不存在**，出不去 |
| 玩家理解成本 | 「这个圈是什么、能不能出去」需要教 | 门关了，一眼就懂 |
| 戏剧性 | 一个地面圆圈 | **门砰地落下，无路可退** |

「不允许出来」把一个需要状态机的模糊规则，换成了一条物理上不可违反的硬约束。**更简单、更清楚、更有戏。**

各难度守场时长不同也对——它天然复用现有 `FZeroEscapeDifficultyDefinition` 结构，是纯数据配置。

### 改进二：死胡同放光球，把负面变正面

这是三个点子里我最欣赏的一个，因为它**解决了一个真实存在的体验缺陷**。

WFC 生成的迷宫必然有死胡同（`FZeroEscapeGeneratedStats::DeadEndCount` 就在统计它）。当前死胡同 100% 是负面体验——走进去，发现没路，退出来，浪费 15 秒。

放上光球后，同一个空间变成：

> 走进去有奖励，但**你现在处在唯一没有退路的地方**。

而且这个风险结构是自动成立的，不需要设计：死胡同只有一个出口，追猎者堵在门口时你无处可躲。「拿到光球 → 转身发现它堵在唯一的门口 → 想办法脱身」这个场面**是死胡同的几何形状自己产生的**，不是我们编排的。

**这是本次讨论里性价比最高的一项。** 一条 Population 规则，把整个迷宫的死胡同从负资产变成正资产。

### 改进三：终点房间刷资源，让守场变 Boss 战

我 v2 依赖「房间里恰好有铁桶和摆锤」，而 PCG 无法保证每局都合适。你的「房间内定期刷新资源物」把这个不确定性直接消除了——**打光了还会来**，玩家永远有物理手段可用。

偶尔刷光球让玩家在战斗中获得爆裂能力，这就形成了战斗内的小节奏：普通投掷压制 → 攒到光球 → 一次爆裂清场 → 继续。

## 三、技术核实：为什么比你想的省工

我核实了三个前提，全部成立。

### 前提一：PCG 已经知道死胡同在哪 ✅

```291:298:Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h
	UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = "Generated")
	int32 DeadEndCount = 0;
```

`FZeroEscapeGeneratedStats` 已在统计 DeadEnd，`FZeroEscapeWfcShapeWeights` 里有 `DeadEndWeight`（`ZeroEscapeGenerationAssets.h:183`）——**说明 WFC 的 Tile 类型里 DeadEnd 是一个一等公民，不需要新写图分析算法。**

而今天验收的 Population 规则已支持形状筛选：现有 `FZeroEscapePlacementRule` 就有 `bStraightCorridorOnly` 这种按格子形状过滤的字段，还有「合法 1x2 高厅必放摆锤」这种按房间类型放置的能力。

**结论：光球放死胡同 ≈ 增加一条「只放 DeadEnd 格」的放置规则，与已有的「只放直走廊」同构。**

### 前提二：爆裂可以完整复用破碎系统的命中事件 ✅

你说「第一次碰撞时小范围爆炸」，而这个精确语义**项目已经实现过一遍了**。

```61:67:Source/Demo/Public/Components/Magnetism/MagneticThrowBreakComponent.h
	/** 接收共享事务已过滤投掷者的 Blocking Hit，并按冲量门槛只排队一次。 */
	void HandleThrownBlockingHit(
```

`UMagneticObjectComponent::OnThrownBlockingHit()` 是一个**多播委托**（`DECLARE_MULTICAST_DELEGATE_FiveParams`），已经处理好了全部脏活：

- 只有正式 `ThrowHeldObject()` 后的投掷才 Arm
- 已过滤投掷者自碰撞
- 提供 NormalImpulse 用于强度门槛
- 有 8 秒监听硬上限，防止很久以后随机触发
- 破碎组件就是它的一个订阅者，且用 next-tick 收尾模式

**爆裂就是这个委托的第二个订阅者。** 破碎组件 143 行的头文件已经把范式演示完了——照它写，不需要碰磁力事务、碰撞快照或 CCD。

再加上 HeavyImpact 已有正式的提交接口（机关已在用），所以爆裂 = 订阅已有委托 + 范围查询 + 提交已有 HeavyImpact + 一个 Niagara。

**这是「加小功能」，不是「加系统」。**

### 前提三：守场关门不需要新的胜负框架 ✅

`AZeroEscapeExitVolume` 已有 `Activate()` 与 `OnExitReached` 广播，`GameState` 已有 `InProgress/Won/Lost` 与 `TransitionTo()`。守场只是在「到达出口」与「判胜」之间插入一段计时，**不改胜负判定结构**。

## 四、整合后的完整一局

```
开局：迷宫，追猎者略快于你，你必须移动
  │
  ├─ 主路线：奔向终点，途中躲机关
  │
  └─ 可选：死胡同里有光球
       ├─ 收益：充能（攒满解锁一次爆裂投掷）
       └─ 风险：唯一出口可能被堵，要用物理脱身
  │
终点房间：门落下，无路可退
  ├─ 守场 N 秒（难度不同）
  ├─ 房间定期刷新磁力资源 → 永远有武器
  ├─ 偶尔刷光球 → 战斗中获得爆裂
  └─ 撑到时间 = 胜利；血量归零 = 失败
```

**这个结构比原来「跑到出口就赢」强得多**，因为：

1. **有了终局高潮。** 原来的胜利是「走进一个球体」，现在是一场硬仗。答辩演示有了明确的爆点。
2. **风险回报贯穿全程。** 每个死胡同都是一次「要不要赌」的决策。
3. **资源有了用途。** 光球攒的能量必须花在守场，形成「前期积累 → 终局爆发」。
4. **你所有物理系统同时被激活。** 磁力、投掷、破碎、Heavy 击飞、机关、爆裂，全部在终点房间里同时有用。

## 六、明确建议：砍掉物理轻受击

**这是我这次评估最重要的一条建议。**

理由，按重要性排序：

1. **它是唯一一个「装不下」的项。** 上面的账已经零缓冲，任何一项超时都会挤掉打包或回归。
2. **审计已指出 2 个阻塞项 + 1 个静默失效路径。** B1（首次命中时驱动约束还不存在，`SetStrengthMultiplyer(1)` 是空操作）、B2（`MaxAngularForce=0` 被误判为非法，而这是引擎默认值）、P1-1（Heavy 同来源保护期 0.75s 内静默吃掉 Light 物理，摆锤周期下约 37% 时段失效）。**修完还要调参，调参还要验收。**
3. **历史返工率最高。** 画面已被你否过一次，方案推翻两轮（全身常驻 → 隔离探针 → 局部 PhysAnim）。
4. **玩家感知远低于其他项。** 上半身骨骼让位数厘米 vs 有没有撞击声和爆炸特效——后者的感知强度高一个数量级。
5. **已有的 Slow/Stop + 方向受击 Montage 完全够用。** 玩法层不受影响，砍掉的只是表现细节。

**砍法**：保留已提交的代码，把 `bEnablePhysicalReaction` 全部置 false，不再投入调参和验收。代码留在仓库不影响任何东西，答辩后想做再做。

省下的 0.5~1.5 天给 L4 和缓冲。

## 九、需要制作人确认

1. **接受砍掉物理轻受击吗？** 这是能否装下新玩法的关键。若坚持要做，我需要你指定砍掉上面哪一项（我建议不要砍 L4 和打包）。
2. **守场时长**：Easy / Normal / Hard 分别多少秒？我建议 20 / 30 / 45。低于 15 秒不够形成 Boss 战体感，高于 60 秒会从紧张变消耗。
3. **守场失败判定**：只有血量归零算失败，还是也允许「时间到就赢」之外的其他结束方式？我建议只有血量归零，规则最简单。
4. **光球攒几个能放一次爆裂？** 我建议 3 个，让它是一个「攒起来的大招」而不是常规手段。
5. **终点房间刷资源频率**：我建议每 6~8 秒补一个，房间内同时存在上限 3~4 个，避免玩家囤积。

## 十、我的总体判断

**你这三个点子把项目从「技术演示」变成了「游戏」，而且成本比我 v2 的方案更低。**

「终点房间关门守场」是三个点子里最关键的一个——它把我需要状态机才能表达的规则，换成了一扇门。这是好设计的典型特征：**用物理约束代替规则说明。**

时间够，但只在一个前提下够：**放弃物理轻受击。**

它是当前唯一一个「投入不确定、感知不明显、历史返工率高」的项，而你手上正好有三个「投入确定、感知强烈、能救活整个项目」的点子。这个交换在剩 4 天时是明显划算的。
