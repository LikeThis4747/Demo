## 0. 先看这一页

本轮不重写项目架构，只在现有链路上增加少量纯值数据和评分：

```text
结构与楼梯先放置
  -> 每层二维 WFC（局部邻接仍负责合法性）
  -> 坍缩前：用“软路线草图”调整合法 OpeningMask 的抽样权重
  -> 每棵 WFC 求解成功后：只分析一次真实通行图，评价主路线、候选支线、替代路线和伪凸起
  -> Planner：先用候选支线保护出生点选择，再按玩家/追猎者/Exit 定稿 RewardBranches
  -> 输出 GeneratedLevelPlan + 最终 RewardBranches
  -> 项目中的 Population 读取同一 Plan
  -> 机关按 log2 权重抽样
  -> 普通资源按独立随机流抽样
  -> 每条合格奖励支线尽头确定性放一个投掷能量补给光团
```

“软路线草图”是**本文方案名**，不是 UE 或 WFC 官方术语。它只是坍缩前的一组“希望哪些边更可能打开/关闭”的提示；提示不删除任何合法候选，不保证最终路线照着草图生成。

## 1. 规则总表：什么会失败，什么只改变概率

### 1.1 技术硬约束

硬约束只保护“能生成、能连通、不会重叠、能原子提交”。命中时会删候选、回溯或令当前生成失败。

| 层 | 保留的硬约束 | 原因 |
|---|---|---|
| 结构/WFC | 网格边界、结构占用、结构必开/必闭边、相邻 OpeningMask 对称 | 否则几何或拓扑非法 |
| 结构/WFC | 全部可走格同属进入点连通分量，Required Enter/Leave 可达 | 否则地图不可通行 |
| 结构/WFC | 总可走格硬上下限、至少保留普通格、搜索/回溯预算 | 容量与运行安全 |
| 结构/WFC | `MaxConsecutiveStraightTiles` 的硬值继续传网格长轴，实际只防异常；策划值 `4` 仍是软偏好 | 不把长走廊变成生成失败 |
| Population | 玩家、追猎者、Exit、必要结构格和**最终**奖励光团端点不可被机关占用 | 流程与奖励点必须可用 |
| Population | 同格占用或机关运行/操作包络冲突 | 防止实体重叠与错误运行 |
| Population | Class、Transform、刺轮预生成配置、Actor 安全预算有效 | 保证 Spawn 可原子完成 |
| 资源 | 同一个锚点只能放一个 Actor；机关占用格和能量球尽头不可放普通资源 | 防止同点重叠 |

本轮**删除**“两个资源图距离至少 3 格”的硬约束。资源可以相邻，只要不是同一锚点，也不与机关/能量球重叠。

### 1.2 软规则

以下全部只改变相对概率或“多个合法结果中选哪一个”，不会把地图或机关候选变成不可能：

| 软规则 | 生效阶段 | 作用 |
|---|---|---|
| 软路线草图开口匹配 | WFC 每次选择合法 OpeningMask 时 | 提高有合理转弯、主路和支线形状的候选概率 |
| 长直走廊平方惩罚 | WFC 选择 + 完整候选择优 | 7 格比 5 格明显更差；一格侧凸不能洗掉主直线 |
| 主路线转弯质量 | 完整候选择优 | 奖励间隔合理的转弯，惩罚每格左右摆的锯齿 |
| 奖励支线数量钟形目标 | 完整候选择优 | 过少、过多都扣分；难度中心值约 3/4/5，但受楼层容量折算 |
| 替代路线覆盖 | 完整候选择优 | 奖励真正能绕过一段主路的不同路线，不只看局部小环 |
| 一格终止支路惩罚 | 完整候选择优 | 惩罚 T 口旁边只突出一格；不会误伤普通 L 型转角 |
| 机关路线覆盖凸增 | Population 位置分 | 图距离从 4 开始奖励，越久没机关增长越快 |
| 类型、组合、组压力、多样性、进度、诊断 | Population 现有六通道 | 保持合法候选非零，形成组合簇、峰谷和随机性 |
| 高压组资源支持、普通资源覆盖 | 资源独立随机流 | 只提高概率，不保证每组一定有资源 |

### 1.3 “奖励支线”不是地图硬约束

“奖励支线”也是**项目内部分类**，只决定哪些终点获得能量光团和支线组合倍率，不决定地图合法性。

奖励支线分两阶段，因为楼层求解时还不知道玩家出生点。

**楼层候选支线**满足：

1. 从度数为 `1` 的普通格终点开始；
2. 沿度数为 `2` 的格连续回溯，直到真正的汇入口；转角不会中断回溯；
3. 汇入口位于本层稳定的 Enter→Leave 主路线；
4. 候选支线不包含 Enter、Leave 或必要结构格；
5. 支线长度至少 `3` 条通行边；
6. 支线内部至少发生 `1` 次方向改变，因此不是一根纯直杆；
7. 终点必须是普通格，才能安全放光团。

**Planner 最终定稿**再做：

1. 先按 Endpoint、Gateway、Path 稳定排序候选支线；
2. `SelectPlayerSpawn` 第一轮排除所有候选支线 Path 和 Endpoint；
3. 如果因为保护支线而没有合法玩家出生点，第二轮回到当前出生规则，不因软目标令整栋重试；
4. 玩家位置确定后，删掉 Path/Endpoint 与玩家、追猎者或 Exit 冲突的候选支线；
5. 只把过滤后的数组写入 `GeneratedLevelPlan.RewardBranches`。

因此完整候选的 `RewardBranchFit` 是楼层阶段的近似分；最终光团数始终等于定稿后的 `RewardBranches.Num()`。Population 还会再断言每个光团端点不等于玩家、追猎者或 Exit 地址。

不满足这些条件的短枝、直枝仍然是合法地图，只是得不到“奖励支线”身份和能量光团。

## 2. A 块：房间/路线结构优化

### 2.1 当前代码事实

- 项目每层仍使用二维 WFC；局部状态是 `OpeningMask 0..15`。
- 当前策划直线值 `4` 已经是软偏好：候选超过后按 `1 + Excess²` 降权，权重下限 `1`。
- 当前完整候选择优是按“普通格缺口 → 总量偏差 → 路线覆盖 → 长直平方”词典序比较。长直排在最后，前面任一项略有差异就可能完全压过它。
- 当前最长直线检测要求同一格同时有东西或南北两个对向开口；T 字和十字仍计入直线。因此“长走廊旁加一格”**现在不能伪装成断掉的直线**。真正缺口是：这根一格凸起本身没有被惩罚，而且确定性兜底用均匀前沿扩张，容易制造这种枝杈。
- 当前最多比较 3 棵合法 WFC 结果；若都失败，兜底先 BFS 接通必需格，再均匀随机扩张前沿。

`PreferredRewardBranchCellRatio` 同时限制“支线不要反客为主”。有效目标不是硬写 3/4/5，而是：

```text
MaxByCapacity = floor(
    PreferredOrdinaryWalkableCells
  * PreferredRewardBranchCellRatio
  / MinimumRewardBranchLengthTiles)

EffectiveBranchTarget = min(PreferredRewardBranchCount, MaxByCapacity)
```

例：Normal 一层若只有 24 个普通格，`floor(24×0.30/3)=2`，有效中心值是 2，不会为了凑 4 条支线让支线占满楼层。若 Seed Sweep 长期达不到 3/4/5，再提高 Generation Profile 的普通格软目标，而不是解除占比保护。

状态中的直线长度封顶为：

```text

```

初始偏好值为 `4` 时可一直区分到 `12` 格；`8` 格草图路径必须严格比 `5` 格贵。更长路段虽在草图状态中封顶，坍缩后的真实长直平方惩罚仍使用完整长度，因此 20 格不会与 6 格等价。

每一步的整数代价：

```text
基础移动                         +100
同方向且超过偏好直线长度 4      +80 × Excess²
上一段只有 1 格就立刻转向        +150
上一段有 2~4 格后转向             -15（最终步成本仍 > 0）
```

效果是：

- 直线太长会快速变贵；
- 每格左右摆的锯齿也很贵；
- 2~4 格后转一次弯略有优势；
- 路径长度仍有基础成本，不会为了转弯无限绕远。

支线提示从主路线上的分散 Gateway 出发，在 `3..6` 步内做有界候选搜索：要求至少一次转向、不得重入主路线或既有提示支线、优先 2~4 格再转向。按 `Seed + Floor + Gateway` 派生独立随机流做稳定加权选择，不消费 WFC 自身的候选随机序列。

草图只写偏好：

- 主路线：只写沿途 `PreferredOpenMask`，不要求关闭额外开口；
- 支线内部：写路径开口，也偏好关闭非路径方向；
- 支线终点：偏好关闭回头边之外的三个方向；
- 同一 bit 同时被要求开/关时，Open 偏好胜出并清掉 Closed 偏好；
- 结构已有 RequiredOpen/RequiredClosed 永远优先，草图不覆盖结构合同。

### 2.5 WFC 候选权重

修改现有 `CalculatePreferredCandidateWeight`，先保留当前长直平方降权，再乘草图匹配权重：

```cpp
const int32 Relevant = CountBits(PreferredOpen | PreferredClosed);
const int32 Matched =
    CountBits(Variant.OpeningMask & PreferredOpen)
  + CountBits((~Variant.OpeningMask) & PreferredClosed & 0x0F);
const int32 Mismatched = Relevant - Matched;

const float Signal = Relevant > 0
    ? static_cast<float>(Matched - Mismatched) / Relevant
    : 0.0f; // [-1, 1]

const double Multiplier = FMath::Pow(
    2.0, Signal * Settings.OpeningPreferenceLog2Strength);

return ClampPositiveIntWeight(CurrentStraightAdjustedWeight * Multiplier);
```

初值 `Strength=1.5`：

| 匹配信号 | 权重倍率 |
|---:|---:|
| `+1.0` | `2^1.5 ≈ 2.83` |
| `+0.5` | `≈ 1.68` |
| `0` | `1.0` |
| `-0.5` | `≈ 0.59` |
| `-1.0` | `≈ 0.35` |

所有合法候选权重最少为 `1`。草图不能 Ban 状态，也不参加 `Connected`、`Count` 或局部邻接传播。

### 2.6 坍缩后真实路线分析

`BuildRouteMetrics` 保持原职责：它仍是 WFC 完整叶的**硬合法性验收回调**，里面不运行本节软分析。只在一棵搜索得到 `bSolved=true` 后、`ScoreCandidate` 之前调用一次：

```cpp
void AnalyzeCollapsedRouteStructure(
    const FZeroEscapeConstrainedFloorInput& Input,
    TConstArrayView<uint8> OpeningMasks,
    FZeroEscapeConstrainedFloorResult& InOutResult);
```

这样每棵成功 WFC 树最多分析一次，不会按求解器访问的完整叶数重复放大。软分析若遇到数值/诊断异常，该候选仍保持合法，但路线质量按最差值、候选支线为空并记录 `SoftRouteAnalysisFailed`；不得返回 `Fatal`。

分析顺序：

1. 用固定邻居顺序重建一条稳定 Enter→Leave 最短路；
2. 把方向相同的连续边压成 Run，统计有意义转弯、1 格 Run 比例和最长直线；
3. 对每个非 Enter/Leave 的度 `1` 终点，沿度 `2` 链回溯到度 `>=3` 的 Gateway；
4. Gateway 必须位于稳定主路线，才可能成为奖励支线；
5. 长度、转弯、普通终点满足第 1.3 节条件后写入 `CandidateRewardBranches`；
6. 长度 `1` 且挂在度 `>=3` Gateway 上的终止枝计为 `OneCellTerminalSpurCount`；普通 L 型主路转角没有度 `1` 侧枝，不会被误伤；
7. 逐条临时移除稳定主路边并 BFS。仍能从 Enter 到 Leave 的边算“可绕过边”，得到真正的替代路线覆盖率。

替代路线指标：

```text
AlternativeRouteCoverageRatio =
    BypassableEdgesOnStableMainRoute / StableMainRouteEdgeCount
```

它比单看 `CycleRank` 更接近“玩家有明显不同路线”：主路外一个无关的小环不会得到很高分；能绕过一大段主路的环才会提高比例。

首轮保留这个简单的 `L × BFS`，不为了理论上的线性复杂度另引入 Tarjan 桥边实现。若 A2 的 P95 超标，再把它作为定点优化；当前先用已知图构造用例验证“桥边不可绕、非桥边可绕”。

### 2.7 完整候选混合评分与早停

不删掉所有层级。`OrdinaryDeficit` 仍是第一比较项，因此支线或绕路不能“买掉”普通格不足；但不再让总格数差一格无条件压过所有路线质量。

二级质量分为：

```text
Quality01 =
    0.15 × DensityFit
  + 0.25 × MainRouteFit
  + 0.25 × RewardBranchFit
  + 0.20 × AlternativeRouteFit
  + 0.15 × ArtifactFit
```

| 项 | 具体计算 |
|---|---|
| `DensityFit` | `1 - Clamp(TotalDeviation/max(PreferredTotalWalkable,1), 0, 1)`；普通格缺口已由一级比较保护 |
| `MainRouteFit` | 现有路线覆盖达标度、合理转弯数量、`1格 Run` 反向比例的组合 |
| `RewardBranchFit` | `1 - Clamp(((Actual-EffectiveTarget)/max(Target,1))², 0, 1)`，过少过多对称扣分 |
| `AlternativeRouteFit` | `Clamp(ActualRatio/PreferredRatio, 0, 1)` |
| `ArtifactFit` | `1 / (1 + 0.5×OneCellSpurs + LongStraightExcess² + SawtoothRatio²)` |

当 `EffectiveBranchTarget == 0` 时，`RewardBranchFit` 通道设为中性并从分母移除，其余活跃项按权重总和重新归一。不把目标强行抬到 1，也不让“容量为 0 但恰好有一条支线”成为最差情况。`PreferredAlternativeRouteCoverageRatio == 0` 时同理将替代路线通道当作关闭，不做除零。

比较不直接用浮点：

```cpp
struct FFloorSoftQualityScore
{
    int32 OrdinaryDeficit = MAX_int32;       // 先比，越小越好
    int32 QualityPenaltyMicros = 1000000;    // Round((1-Quality01)*1e6)
    int32 TotalDeviation = MAX_int32;         // 质量量化同分时再比
    // 其余稳定诊断平局项……
};
```

`IsBetterThan` 依次比较 `OrdinaryDeficit → QualityPenaltyMicros → TotalDeviation → 稳定诊断字段`，不增加 RNG 消耗。完整合法候选不会因质量分低被拒绝。

新早停条件：

```cpp
if (Score.OrdinaryDeficit == 0
    && Score.TotalDeviation == 0
    && Score.QualityPenaltyMicros
        <= RoundToInt((1.0 - RouteQualityEarlyAcceptThreshold) * 1000000.0))
{
    break;
}
```

初值 `RouteQualityEarlyAcceptThreshold=0.82`。它不将“完美路线”变成硬合法条件，只是在密度精确、质量已足够好时不再浪费后续 WFC 树。

### 2.8 兜底生成

不重写 `BuildDeterministicFallbackFloor`。只做两处小改：

1. BFS 到同层等距父节点时，优先采用草图希望打开的边；
2. 前沿扩张从均匀随机改为正权重抽样，草图边得到 `2^Strength` 加权，其余边仍有权重 `1`。

因此 WFC 失败后的兜底不会完全忘掉路线意图，但仍以连通和目标格数为第一职责。

兜底不再假借 `LocalAttempt=3` 生成 salt，改用独立的 `MakeFloorFallbackSalt(Seed, FloorIndex)` 常量域；以后增加 WFC 尝试数也不会与兜底共用随机序列。

### 2.9 “地面层至少两个普通格”本轮处理

**本轮保留，不把它当质量目标，也不继续扩写策划解释。** 当前 `SelectPlayerSpawn` 明确排除追猎者、Exit 和结构格；若硬下限降为 `1`，某些楼层会先通过 WFC，再在玩家出生点选择阶段失败并浪费整栋重试。保留 `2` 不会促成长走廊，也不影响正常地图的软目标。

若以后要删除，应同时把“玩家出生点容量”提前合并进统一结构容量验证，而不是只把数字改成 `1`。

## 3. B 块：机关放置与普通资源

### 3.1 类型基础权重

基础权重是**比例，不是固定数量**。忽略上下文时的基准如下：

| 难度 | 地刺 | 冲锤 | 发射器 | 刺轮 | 基准概率约值 |
|---|---:|---:|---:|---:|---|
| Easy | 5 | 3 | 3 | 2 | 38.5% / 23.1% / 23.1% / 15.4% |
| Normal | 4 | 4 | 4 | 2 | 28.6% / 28.6% / 28.6% / 14.3% |
| Hard | 3 | 6 | 4 | 4 | 17.6% / 35.3% / 23.5% / 23.5% |

Hard 的发射器不再最高；冲锤最高。发射器和刺轮在高难度增加，是为了配合其他机关，不代表它们单独更难。

实际抽取仍是：

```text
TypeWeight = BaseTypeWeight × 2^(Top3AnchorMean × TypeContextStrength)
```

其中 `TypeContextStrength=0.5`。类型概率会随当前位置、组合、覆盖和压力改变，不能把上表当最终出现百分比。

### 3.2 全局机关预算成本

将现有 `ExpectedHazardsPer100GameplayCells`（“处数”）重命名为 `ExpectedHazardBudgetUnitsPer100GameplayCells`（“预算单位”）。这是资产语义迁移，不会沿用原值 `26/28/30`。

成本用“十分之一单位”的整数存储，避免浮点累加参与同 Seed 分支：

```cpp
USTRUCT(BlueprintType)
struct FZeroEscapeHazardBudgetCostTuning
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Budget",
        meta=(ClampMin="1", ClampMax="10"))
    int32 PendulumCostTenths = 10;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Budget",
        meta=(ClampMin="1", ClampMax="10"))
    int32 SpikeTrapCostTenths = 10;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Budget",
        meta=(ClampMin="1", ClampMax="10"))
    int32 BatteringRamCostTenths = 10;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Budget",
        meta=(ClampMin="1", ClampMax="10"))
    int32 GuidedLauncherCostTenths = 7;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Budget",
        meta=(ClampMin="1", ClampMax="10"))
    int32 SpikeWheelCostTenths = 5;

```

它作为跨难度共享配置挂在现有 `FZeroEscapeHazardPopulationAssembly`：

```cpp
UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Budget")
FZeroEscapeHazardBudgetCostTuning BudgetCosts;
```

难度字段仍使用设计师可读的浮点“单位/100 格”，但进入 Policy 立即一次性量化为整数：

```cpp
UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Budget",
    meta=(ClampMin="0.0", ClampMax="100.0"))
float ExpectedHazardBudgetUnitsPer100GameplayCells = 23.5f;
```

首轮 DataAsset 初值为 Easy / Normal / Hard = `22.0 / 23.5 / 24.5`。它们是按已确认类型比例和 `1.0/1.0/0.7/0.5` 成本估算的“约等于原 26/28/30 处”起点，必须在 Seed Sweep 后以实际 Actor 数重定标，不宣称两种单位等价。

预算只控制全局填充进度，不改变基础压力和组合压力：

| 类型 | 放 1 处消耗 |
|---|---:|
| 强制摆锤 | `1.0` |
| 地刺 | `1.0` |
| 冲锤 | `1.0` |
| 发射器 | `0.7` |
| 刺轮 | `0.5` |

循环改成：

```cpp
const int32 TargetBudgetTenths = FMath::RoundToInt(
    ExpectedHazardBudgetUnitsPer100GameplayCells
    * GameplayCellCount * 10.0 / 100.0);
int32 UsedBudgetTenths = MandatoryPendulumCount * Costs.PendulumCostTenths;
const int32 EffectiveBudgetTenths = FMath::Max(
    TargetBudgetTenths, UsedBudgetTenths);

while (UsedBudgetTenths < TargetBudgetTenths)
{
    BuildAllNonEmptyTypePools();
    if (Pools.IsEmpty()) break; // 允许欠填，不换 Seed 强补

    const FSelectedHazard Selected = PickTypeAnchorVariant(Pools, HazardRng);
    Commit(Selected);
    UsedBudgetTenths += BudgetCostTenthsForKind(Selected.Kind);
}
```

不因“剩余 0.4”硬禁掉地刺/冲锤；最后一次允许最多超出 `1.0` 预算单位，避免尾段只剩便宜机关的抽样偏差。统计同时记录实际 Actor/机关数以及 `Target/Used/UnderfilledBudgetTenths`。

`IsValid...Tuning` 对预算目标做 finite/范围检查，对五种成本做 `[1,10]` 检查；任一非法值都是 `InvalidConfiguration`，不在运行时静默修正。

最坏 Actor 预算按“每预算单位最多生成多少 Actor”估算，而不是按机关处数：

```text
MaxActorsFromHazardBudget = ceil(EffectiveBudgetTenths * max(
    PendulumActorCountPerPlacement / 10.0,
    SpikeActorCountPerPlacement / 10.0,
    1.0 / 10.0,
    LauncherActorCountPerPlacement / 7.0,
    1.0 / 5.0))
```

用 `EffectiveBudgetTenths` 是为了防止强制摆锤成本已高于密度目标时前置低估。整体前置 `WorstActorCount` 还要加上普通资源上限与 `Plan.RewardBranches.Num()`；后置 `ValidateActorBudget` 再用三个实际放置数组做最终一致性验证。

### 3.3 机关路线覆盖凸增

“距离”始终是整栋通行图最短边数，拐角、T 口、楼梯都按实际连接边累计，不会在转角清零。

在现有 `FZeroEscapeHazardPlacementScoringTuning` 中，用下面四个字段替换单一 `RouteCoverageLog2Bonus`，并替换当前会在距离 6 饱和的线性信号：

```cpp
UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Coverage",
    meta=(ClampMin="1", ClampMax="32"))
int32 RouteCoverageStartDistanceTiles = 4;

UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Coverage",
    meta=(ClampMin="0.0", ClampMax="2.0"))
float RouteCoverageLinearLog2PerTile = 0.35f;

UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Coverage",
    meta=(ClampMin="0.0", ClampMax="1.0"))
float RouteCoverageQuadraticLog2PerTileSquared = 0.03f;

UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Coverage",
    meta=(ClampMin="0.0", ClampMax="5.0"))
float RouteCoverageLog2Bonus = 5.0f;
```

```text
x = max(0,
    NearestHazardGraphDistance - RouteCoverageStartDistanceTiles + 1)
CoverageLog2 = min(5.0, 0.35x + 0.03x²)
```

| 最近机关图距离 | log2 加分 | 单看本项的权重倍率 |
|---:|---:|---:|
| 1–3 | 0 | 1.00× |
| 4 | 0.38 | 1.30× |
| 5 | 0.82 | 1.77× |
| 6 | 1.32 | 2.50× |
| 7 | 1.88 | 3.68× |
| 8 | 2.50 | 5.66× |
| 9+ | 自身上限 3.00 | 8.00× |

这不是“每 4 格必须放机关”。某个远点只会获得更高概率；组合、组压力、类型安装条件和随机抽样仍可让它落空。距离 20 仍比距离 6 强（`8.0×` 对 `2.5×`），但不会用单一覆盖通道撞穿总 `±5` 边界、把组合等其他通道压平。

当尚未接受任何机关时，`NearestHazardGraphDistance` 是不可达哨兵值，覆盖贡献显式取中性 `0`，不对哨兵值做减法或平方。测试必须证明：覆盖已到自身上限时，改变正组合贡献仍能改变候选排序。

覆盖参数全部进 finite/范围校验，覆盖上限为 0 时视为关闭该通道，运行时不静默修正非法资产。实施时根据用户“距离 6 后仍继续增长、距离 20 不能等同普通空白”的要求，没有采用审计建议的 `+3` 上限，而是保留 `+5`。这意味着极长空白在某一步会优先于其他正奖励；随着机关补入、最近距离缩短，后续抽样重新释放组合、压力和多样性通道。该取舍仍需实玩观察。

### 3.4 发射器远距组合

保持已确认的设计：紧邻有弱奖励，两格有中奖励，三格及以上的同组配合最强。这次不再宣称只是把旧最大值从 `1.5` 调到 `1.75`；它确实改了曲线形状，因此在 `FZeroEscapeHazardPlacementScoringTuning` 中用三个可校验字段替换现有单一 `LauncherCombinationLog2Bonus`：

```cpp
UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Combination",
    meta=(ClampMin="0.0", ClampMax="4.0"))
float LauncherAdjacentCombinationLog2Bonus = 0.25f;

UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Combination",
    meta=(ClampMin="0.0", ClampMax="4.0"))
float LauncherTwoTileCombinationLog2Bonus = 1.00f;

UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Population|Hazards|Combination",
    meta=(ClampMin="0.0", ClampMax="4.0"))
float LauncherFarCombinationLog2Bonus = 1.75f;

float LauncherCombinationLog2ForDistance(int32 Distance)
{
    if (Distance <= 0) return 0.0f;
    if (Distance == 1) return LauncherAdjacentCombinationLog2Bonus;
    if (Distance == 2) return LauncherTwoTileCombinationLog2Bonus;
    return LauncherFarCombinationLog2Bonus;
}

float LauncherCombinationPressureScale(int32 Distance, int32 GroupRadiusTiles)
{
    if (Distance <= 1 || GroupRadiusTiles <= 1) return 0.0f;
    return Clamp01((Distance - 1.0f) / (GroupRadiusTiles - 1.0f));
}
```

| 图距离 | log2 奖励 | 权重倍率 |
|---:|---:|---:|
| 1 | `+0.25` | `1.19×` |
| 2 | `+1.00` | `2.00×` |
| 3 及以上、仍在组半径内 | `+1.75` | `3.36×` |

距离 `0` 仍是同格且由占用硬约束排除。图距离奖励的形状明示与 `GroupRadiusTiles` 解耦；组半径只决定这个配对是否在可搜索邻域内。压力诊断则继续用现有按组半径归一的信号，不因为调整抽样奖励而暗中改变组压力语义。

配置校验除 finite/范围外，还要求 `Adjacent <= TwoTile <= Far`；不用运行时排序或 Clamp 偷偷改掉资产意图。

发射器基础压力保持低值、全局预算成本为 `0.7`；因此它出现后不会像完整地刺/冲锤一样明显挤走附近机关。

### 3.5 奖励支线的组合放大

从 `LevelPlan.RewardBranches` 构建只读地址集合：Gateway + Path 中除 Endpoint 外的格子。候选锚点落在集合内时，只放大**正的组合贡献**：

```cpp
if (BranchApproachAddresses.Contains(Candidate.AnchorAddress)
    && BestCombinationLog2 > 0.0f)
{
    BestCombinationLog2 *= 1.2f;
}
```

效果示例：

| 组合 | 普通区域 | 奖励支线接近区 |
|---|---:|---:|
| 刺轮 + 冲锤 | `+3.0` → `8×` | `+3.6` → `12.13×` |
| 刺轮 + 地刺 | `+2.25` → `4.76×` | `+2.70` → `6.50×` |
| 发射器远距 | `+1.75` → `3.36×` | `+2.10` → `4.29×` |

solo 刺轮 `-0.5` 不乘倍率；组压力/过载仍会抑制无限堆叠。

### 3.6 删除资源硬间距

删除：

```cpp
FZeroEscapeResourcePopulationTuning::MinimumRouteSpacingTiles;
NearestResourceDistances;
SpacingRejectedCount;
```

资源候选只做无放回抽样，同一格不会重复，但相邻格允许连续出现。

资源覆盖改为独立的软参数，不再偷用“最小间距”当比例尺：

```cpp
int32 RouteCoverageFullBonusDistanceTiles = 3;

CoverageSignal = NearestContentDistance == Unreachable
    ? 1.0f
    : Clamp(NearestContentDistance / 3.0f, 0.0f, 1.0f);

Weight = 2^(SupportLog2 + CoverageSignal * RouteCoverageLog2Bonus);
```

只修改普通资源参数时，机关随机流、机关位置和能量球端点都不变。

### 3.7 log2 权重如何合成

现有六个通道不增加：

```text
TotalLog2 = Clamp(
    Position + Progress + GroupPressure
  + Combination + Diversity + Diagnostic,
    -5, +5)

Weight = 2^TotalLog2
```

| log2 贡献 | 相对中性候选倍率 |
|---:|---:|
| `-5` | `1/32` |
| `-1` | `1/2` |
| `-0.5` | `0.707` |
| `0` | `1` |
| `+0.5` | `1.414` |
| `+1` | `2` |
| `+2` | `4` |
| `+3` | `8` |
| `+5` | `32` |

最大合法候选和最小合法候选的极端相对差可到 `1024×`，但最小权重仍大于零。组合和远距覆盖可能同时加分，最终仍由总边界 `±5` 控制。

## 4. C 块：死路投掷能量补给光团

### 4.1 Population 数据

### 4.2 规划顺序

```cpp
TSet<FIntVector> ReservedOrOccupiedAddresses;

// 1. 先预留 Planner 定稿后的全部合格支线终点。
for (const FZeroEscapeGeneratedRewardBranch& Branch : Plan.RewardBranches)
{
    if (Branch.EndpointCoordinate == Plan.PlayerSpawnCoordinate
        || Branch.EndpointCoordinate == Plan.PursuerSpawnCoordinate
        || Branch.EndpointCoordinate == Plan.ExitCoordinate)
    {
        OutError = TEXT("EnergyOrbEndpointConflictsWithFlowAnchor");
        return EPopulationPlacementResult::InvalidPlan;
    }
    ReservedOrOccupiedAddresses.Add(Branch.EndpointCoordinate);
}

// 2. 机关规划：终点不进入机关合法候选。
PlanHazards(..., ReservedOrOccupiedAddresses, ...);

// 3. 普通资源规划：终点也不进入普通资源候选，仍只消费 ResourceRng。
PlanResources(..., ReservedOrOccupiedAddresses, ResourceRng, ...);

// 4. 每个终点确定性追加一个光团，不消费任何 RNG。
AppendEnergyOrbPlacements(
    Plan.RewardBranches,
    ResourceAssembly,
    WorkingPlan.EnergyOrbPlacements,
    WorkingPlan.KindCounts.EnergyOrbs);
```

每条合格支线**恰好一个**光团。光团不占普通磁力资源预算；它的数量在规划前已知，先并入 `WorstActorCount`，规划后再并入 `ValidateActorBudget`。若存在奖励支线但 `EnergyOrbClass` 未配置，Population 以 `InvalidConfiguration` 原子失败，不生成半套结果。

### 4.3 Spawn

`ZeroEscapeGameplayPopulator.cpp` 需要把第三层放置完整贯穿，不只是加一个 Class switch：

1. `PlacementKindName` 增加 `EnergyOrb`；
2. `FindClassReference` 返回 `Resources.EnergyOrbClass`；
3. `LoadUsedClasses` 遍历 `EnergyOrbPlacements`；
4. `BuildSpawnRequests` 的前置计数并入光团；
5. 同函数的 `AppendLayer` 追加第三个数组，检查光团恰好一个有限 Transform；
6. Spawn Request 构建与普通 Spawn 循环接受 `EnergyOrb`；
7. 成功日志分开打印 `resources` 和 `energy_orbs`。

```cpp
case EPopulationPlacementKind::EnergyOrb:
    return &Profile->Resources.EnergyOrbClass;
```

光团使用普通 `SpawnActor<AActor>`；不需要 Deferred Spawn、Tick 或新的运行时接口。

## 7. 性能可行性

当前 Generation Profile 的单层是 `18×12=216` 格；代码安全上限是 `MaxGridCells=1024`、`MaxGridAxis=64`。WFC 只有 16 个 OpeningMask，且每层最多比较 3 棵成功搜索结果。以下“便宜”结论仅对当前 216 格 Profile 成立，不冒充全代码上限的实测结论。

新增主要成本：

- 草图主路：初始直线偏好 4 时，方向状态上界约 `216×5×13`，一次小型最短路搜索；
- 支线提示：每个 Gateway 最深 6 步的有界搜索；
- 支线识别：`O(V+E)`；
- 替代路线覆盖：主路每条边做一次小图 BFS，最坏约 `O(L×(V+E))`；
- Population：只多常数次公式和一个支线地址 `TSet` 查询。

真正需要防的性能回归不是单次小图 BFS，而是丢失早停后每层都跑满 3 棵 WFC 树。因此基线必须同时记录每层 WFC 树数、软分析调用数、整栋 P50/P95。

在 216 格规模下，每棵成功树一次的图分析应远小于 WFC 回溯成本；这是工程推断，仍以 A2 实测为准。测试再对一个 1024 格纯通行图合成 fixture 记录分析耗时，但不要求跑完一个最坏 WFC 回溯树。若路线分析让整栋 P95 超过当前两倍，第一步才是把“逐边 BFS”改为一次桥边分析；不先扩框架。

## 8. 已知限制

1. 软路线草图提高概率，不保证每局都有 3/4/5 条奖励支线；合法性优先，容量不足时有效目标会下降。
2. 完整候选择优最多比较现有 3 棵 WFC 结果；若参数方向正确但变化不明显，先调草图强度和现有尝试数，不新增生成阶段。
3. 楼层分数用候选支线，Planner 事后可因出生点/出口冲突删掉少量支线；这是为了不让软目标引发整栋重试的有意取舍。
4. 一条稳定最短路用于诊断，不宣称它是玩家唯一或实际选择的路线。
5. 当前地刺/冲锤相位仍不由 Population 控制，组压力继续是近似诊断。
6. 机关覆盖从图距离 4 开始凸增并在图距离 12 左右达到 `+5 log2` 上限；距离 20 不会被当成普通空白，但在上限区间内不再继续区分。到达总分上限时，其他正奖励的排序空间会暂时变小，属于首轮实玩重点。
7. 光团首版只有可识别视觉与碰撞，不包含吸收后的能量玩法。
8. 每层 3/4/5 是设计中心值，不是硬配额；当前实际楼层格数可能要求后续提高普通格软目标。

## 9. 网络资料依据与本项目取舍

- 原始 [WaveFunctionCollapse 实现](https://github.com/mxgmn/WaveFunctionCollapse)使用模式频率/权重影响观察阶段的抽样，而局部相容性负责排除非法组合。本文沿用“合法性与概率分开”的方向，但保留项目现有 16-mask、Connected 和回溯实现。
- Scurti 与 Verbrugge 的论文 [Generating Paths with WFC](https://arxiv.org/abs/1808.04317)展示了用路径草图特征影响 WFC 输出，并明确指出简单随机行走容易产生锯齿、局部 WFC 难以保证全局路径性质，仍需后处理过滤短小退化路径。本文不移植其 Overlapping Model、图像 Pattern 或 Unity 工具，只借鉴“坍缩前引导 + 坍缩后图分析”的分工。
- Merrell 的 [Model Synthesis](https://graphics.stanford.edu/~pmerrell/thesis.pdf)说明局部样例合成可结合用户定义的较大尺度约束。本文没有引入完整 Model Synthesis，只用现有项目的纯值约束和候选权重完成最小版本。
