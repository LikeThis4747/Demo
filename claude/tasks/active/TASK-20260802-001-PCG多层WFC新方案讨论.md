## 已核对基线

- 当前 Runtime PCG 是二维 `20x12` Grid-WFC，逻辑格 `600cm`；每格只保存同层 `N/E/S/W OpeningMask` 与 `RegionKind`。
- WFC 已有局部开口一致性、非空格数量、最大连续直线、全图连通、有界时间序回溯和最终 Start→Exit 路线校验。
- 成功 Plan 先展开为 `300cm` 表现结构件，再以 HISM 提交；灯光、Population 与 GameFlow 保持在空间求解器之外。
- `Level0` 当前加载且非 Dirty。V1/V2 分别为 1836/1857 Actor；V2 保持 `600cm` 网格与 `Z=0/450/900` 三层走行面。
- V2 包含四座不可拆的 2x2 双层楼梯、一座贯通三层的 2x2 楼梯间、三层各一间 1x2 高天花板房间，以及上层楼梯支撑和房间净空所需的保留占用。
- V2 可通行逻辑格数量（含每层两格高厅占用）为 L1/L2/L3=`33/27/25`；高厅位置为 L1 `(1,4)/(1,5)`、L2 `(6,4)/(6,5)`、L3 `(1,4)/(1,5)`。

## 当前核心缺口

- 二维 `FIntPoint GridSize` 与单层 `FZeroEscapeCollapsedTile` 无法表达楼层坐标、完整楼梯/房间记录、跨层占用和保留区。
- 单一 4-bit `OpeningMask` 无法表达接口宽度、FloorZ、净高类别、垂直连接、左右手性、落脚区和 StyleFamily。
- 现有 2x2 Room 只是四个 Required 格，无法保证整间房必须完整出现。
- 当前结构展开只从同层闭边派生墙/顶/柱，缺少共享边唯一所有者、临空栏杆、楼梯固定装配、上层挖空和高度过渡派生。
- 当前 Count/Connected/路线验收只面向二维单层图；尚无每层楼梯配额、跨层全局连通和完整楼梯不可拆分约束。

## 2026-08-02 双方案评估（讨论稿，未冻结）

### 共同前提

- 两种方案都需要三维 Plan/占用数据；真正的分歧是“WFC 候选域是否也统一升为三维”，不是要不要保存楼层坐标。
- 正交三维网格通常是 `±X/±Y/±Z` 六个面邻居，不是八邻居；楼梯通常横跨多个 `XY` 与楼层，不能只靠单格 `Up/Down` 开口表达。
- 高厅的上层空间是不可通行净空占用，不是垂直道路；通行连接、实体占用和净空保留必须分开建模。

### 首选方案：先放完整跨层结构，再逐层运行二维 WFC

- 先以有界回溯放置完整的双层楼梯、贯通三层的楼梯间和高天花板房间，并一次性写入所有受影响楼层的占用、支撑、净空与接口。
- 把完整结构的结果转换成各层的 Required/Blocked/Reserved/固定开口约束，再按“约束最多优先、楼层号稳定打破平局”的顺序调用现有二维 WFC。
- 各层完成后，把平面 OpeningMask 边与完整楼梯内部跨层边合并成整栋通行图，统一验证跨层连通、每对相邻楼层的连接配额、Start→Exit、循环/逃生路线和垂直切换次数。
- 第一版失败策略保持简单且确定：单层失败先消耗该层预算；持续失败则放弃本次完整跨层结构布局并以新的派生 Seed 重启整轮，而不是维护复杂的跨阶段局部回滚。
- 可基本保留当前 `ZeroEscapeWfcSolver.*` 与 `ZeroEscapeWfcConstraints.*` 的 16 状态二维核心；主要新增完整楼梯/房间定义与放置、三维 Plan/占用、整栋通行图验收和跨层结构展开。

### 方案 B：统一三维 WFC

- 把 Wave 地址改为 `(X,Y,Z)`，邻接传播扩为六个面方向；Tile Variant 改为六面带类型接口，而不能只把 4-bit OpeningMask 扩成 6-bit。
- 双层/三层楼梯和高天花板房间若放入统一三维 WFC，需要类似 Tessera Big Tiles 的多格完整结构：每种旋转/左右朝向拆成内部 Part Variant，并用强制内部邻接保证整组同时出现；边界还要禁止残缺结构。
- 当前 `uint16 FWfcDomain`、16 状态权重、四方向传播、Connected 展开图、MaxConsecutive、回溯 Trail、Plan Hash 和自动化测试都需直接改造。
- 统一域能自然传播任意上下层局部关系，但峰值 Domain、兼容表、全局回溯范围和矛盾定位都会显著扩大；固定 `GridSize.Z` 仍然只是有限三维 WFC，并不会自动获得无限楼层或流式生成。

### 当前比较结论

- 对固定 `2~6` 层，首选方案更符合现有投资和 Demo 风险：六层相当于最多六次隔离的 `20x12` 求解，峰值仍是一层 Domain；统一三维 WFC 则是一个 `20x12x6` 联合搜索。若机械地完整枚举 6-bit 开口会有 64 种掩码；即使改用精简的带类型 Variant 集，内部结构片段、旋转和左右朝向也会显著推高状态数。
- 当前 `ZeroEscapeWfcSolver.* + ZeroEscapeWfcConstraints.*` 约 2544 行，首选方案可以把它们当作稳定内核；统一三维 WFC 会直接改动这部分及其约 1632 行现有测试，性质更接近求解器替换。
- 首选方案的主要代价是阶段边界与重启策略；统一三维 WFC 的主要代价是状态/资产作者负担、全局矛盾与性能不确定性。
- 若未来确实需要大量自然生长的跨层局部组合，可先把“完整跨层结构放置器”替换成粗粒度三维 WFC，而不必立即把每个 `600cm` 细格全部纳入统一三维域。
- 用户已确认首版采用首选方案：先确定主路线和完整跨层结构，再逐层运行二维 WFC，最后合并整栋通行图验收；不采用统一细格三维 WFC。

### 后室式体验的游戏性约束方向

- 目标应是“可控迷失”，不是不可读的立体随机迷宫：平层重复负责不安感，高天花板房间、楼梯间、楼层风格和声光差异负责重新定位。
- 宏观图应先控制主路线、追逐循环、垂直捷径、死胡同深度和楼层切换次数；WFC 负责局部走廊语法和变化，避免让局部邻接算法单独决定全部节奏。
- 双层楼梯负责连接相邻楼层；贯通三层的楼梯间是另一种现有楼梯结构。无论采用哪种楼梯组合，都必须保证每个生成楼层可达。它就是楼梯间，不再使用别的叫法。
- 玩法默认可优先考虑 `3~4` 层，`5~6` 层作为大型局或特殊配置；这是讨论建议，尚未写入正式策划或 Profile。

### 用户已表达的布局偏好（部分待冻结）

- 整体希望存在一条隐含主路线，并从主路线长出支路与回接循环；不希望由局部 WFC 偶然形成完全无层次的迷宫。
- 每个生成楼层都必须从 Start 可达，并且能继续走到 Exit；这不等于主路线必须经过该层的每个房间。
- 用户确认“每个生成楼层都必须可达”。以三层为例，最低配置固定为至少一座连接 1—2 层的楼梯，以及至少一座连接 2—3 层的楼梯；两座楼梯在二层不能紧挨，玩家从一座楼梯出来后必须在二层走过一段达到最短长度要求的路线，才能到达另一座楼梯。
- 用户确认采用“主路线通常大体朝目标楼层推进、额外楼梯主要承担循环/捷径”的默认策略；`1→2→1→3` 一类折返只作为受限的高复杂度变化，不作为标准主路线。
- 用户认可禁止楼层级死路，但允许有界的局部短支路；短支路应能承载奖励、机关、线索或遭遇，具体最大深度与内容要求留给关卡 Profile 和 Seed 验收。

### 2026-08-02 楼梯口作为必达端点的讨论

- 用户提出：对每层建立必达端点集合，集合包含该层全部楼梯落脚口，以及位于该层的 Start/Exit；只需证明这些端点处于同一可达分量，不必为每对端点分别求路。
- 该方向与现有实现兼容：当前 Connected 已把所有被迫非空/开边节点作为 Relevant 集合，在 Potential 图上做分量与 Tarjan 传播；最终 Plan 也只从一个根执行一遍 BFS 并检查全部非空 Cell。
- 性能风险主要不是最终 BFS，而是楼梯位置、保留区、MaxWalkable 与强制开边共同收紧候选后导致的 WFC 回溯/整轮重试；必须以批量 Seed 的成功率、P95/P99 重试与耗时验证，暂不凭估计给出毫秒承诺。
- 最低楼梯数量与端点连通共同保证每个楼层可达；楼梯之间再设置最短行走距离，避免玩家从一座楼梯出来后立即进入下一座楼梯、直接跳过该层内容。

### 2026-08-02 楼梯约束设计输入

- 用户确认：以三层为例，至少生成一座 1—2 层楼梯和一座 2—3 层楼梯；两座楼梯在二层必须通过平面网络互相可达，并满足最短行走距离。起点层与终点层分别还要连接 Start/Exit。
- 在满足最低配置后，可以少量增加双层楼梯来提高地图复杂度和趣味性，但不会大量生成；每层相关的额外双层楼梯最多增加一到两座。也可能再生成一座贯通三层的楼梯间。额外双层楼梯的数量、贯通三层楼梯间是否生成及相应概率，都由难度配置控制。
- 同一座楼梯的落脚平台可能有多个通向本层走廊的出口，目前出口上限为三个。
- 约束设计必须分开统计：物理楼梯模块实例、模块内部连接相邻楼层的垂直边、各楼层落脚平台向平面网络开放的连接口。一个三出口平台不能自动计作三条独立换层路线。
- 当前 V2 的 A/B/C/D 双层楼梯与中央贯通三层的楼梯间适合作为多模块、多连接口和占用冲突的压力样板，不直接等同于正式关卡的目标楼梯密度。
- 放置顺序固定为：先放保证所有楼层可达的最低楼梯数量，再根据难度尝试增加少量楼梯。任意两座会让玩家连续换层的楼梯都不能过近；距离阈值由配置提供，并通过批量 Seed 和实际游玩调整。单座楼梯的多个出口也不能在很短距离内立即汇合。
- 用户原始意图是让同一楼梯落脚平台实际开放的连接口组合能够随 Seed 变化，以增加复杂度和趣味性；尚未决定由模块变体固定、由放置阶段从受支持组合中随机选择，还是让二维 WFC 决定可选口。后续必须区分“独立随机开关”与“受主路线、可达性、出口间距和封口能力约束的随机选择”。
- 用户原则认可混合方案：楼梯核心与潜在连接口位置固定，由跨层结构规划阶段按 Seed 从模块支持的合法组合中选择实际开放口；未连接口封墙，开放口派生连接地板与栏杆收边。具体合法组合与权重仍待按模块逐项确认。
- 2026-08-02 通过官方 UE MCP 只读复核 `Level0` V2：A/B 双层楼梯各含固定 Base、Landing、Stair Flight 与 Platform；壳体在实际开口方向省略对应墙段。连接平台使用单位缩放 `SM_HydroLab_FloorB`，落脚区护栏使用 `SM_HydroLab_FenceC2` 等独立构件；贯通三层的楼梯间以 `StackedPort`、`F2Port`、`SouthEntry` 等局部墙段表达多方向口。资产事实支持“固定楼梯核心 + 按开放边派生墙/地板/栏杆”，无需为每个出口组合复制整座楼梯资产。
- 2026-08-03 用户再次确认：最低楼梯数量先保证每个楼层可达；额外双层楼梯每层最多增加一到两座，并可能增加一座贯通三层的楼梯间；这些额外楼梯的数量和出现概率随难度调整。正式 Plan 只需继续确定各难度的具体概率、楼梯最短行走距离和额外楼梯放置失败时的处理方式。

### 2026-08-02 高厅与后续玩法输入

- 高天花板房间的首要预期用途是承载摆锤机关，同时也可以作为路线复杂度、视野与空间节奏变化的节点。
- 项目当前只有高天花板房间，没有上层天桥需求；“上层天桥”是 Codex 在讨论中擅自扩展的内容，已撤回，后续不得把它当作候选范围。
- 摆锤当前尚未实现。继续保持现有 Plan/Population 职责分离：空间生成只提供高厅结构、上层净空与可供后续系统筛选的合法空间；不在本次 PCG 结构求解中硬编码摆锤、陷阱锚点、扫掠体积或具体机关放置。
- 主路线、支路、循环与距离属于整张通行图的规划、约束或派生结果，不复制成二维 WFC 的局部 Tile 身份。是否需要把其中某项持久保存到 Plan，必须由明确的 Population/玩法消费者驱动，不能预先堆积标签。
- 当前审计倾向保留二维 WFC 的 16 个 N/E/S/W 开口状态：多层地址、完整结构的占用/保留区、垂直内部边、开放口选择和边所有权应扩展在 WFC 外层合同中。只有出现必须由普通平面 WFC 同时求解的多种接口宽度/高度或局部几何类别时，才有证据扩展 Variant；该结论仍需随数据合同一起冻结。
- 不为本次改造预先增加异步生成。继续保持最直接的完整实现：可以设计稳定、可扩展的数据合同，但不得以“最小”为由写死资产路径、关卡名、楼层数或特定楼梯，也不得增加未经性能证据证明必要的异步、兼容层或绕过逻辑。

### 2026-08-02 跨层模块逐层投影候选（讨论稿）

- “逐层投影”是本项目候选实现描述，不是 WFC/UE 官方术语：先完整选择并放置整座楼梯或高天花板房间，再把它在各楼层产生的可行走路线、实体占用、净空保留和开闭边转换为现有二维 Solver 输入；完整结构记录仍是唯一事实源，不能把转换后的格子重新当成可独立随机选择的普通 Tile。
- 当前首选是“固定拓扑格投影”：模块在某层的可行走逻辑格以精确 N/E/S/W Mask 固定进二维 WFC；模块内部恒开平面边与本次 ActiveMouthMask 共同形成该精确 Mask。实体/支撑与净空格都对 WFC 投影为 Outside，但外层 Plan 必须保留二者差异；楼梯的跨层边不进入 4-bit Mask，待各层完成后合并到全局图。
- 该方案可复用现有 `RequiredOpenMask/RequiredClosedMask`、邻接对称传播与 Connected；固定模块格作为 singleton 参与连通性，因此多个外部出口可以通过真实落脚平台连接。模块原子性由投影前放置保证，WFC 无权只保留其中一部分。
- 不首选“把模块 footprint 全部排除、只在最终图合并”：当前二维邻接会把指向 Outside 的边关闭，Connected 也看不到模块对多个出口的连接，容易早期误拒绝或晚期大量失败。也不预先把任意模块内部图直接接入 Connected/Tarjan；后者更精确但会显著改造稳定约束内核，只在真实模块无法以每格单一平面拓扑等价投影时再讨论。
- 必须验证的主要问题：模块每层投影与真实通路图等价；同格不得存在两个不同高度且互不相连的通路；Active Mouth 必须在求解前冻结；旋转/镜像必须统一变换格偏移、方向与 Mask；模块 Walkable/Solid/Clearance 冲突必须 fail-closed；模块拥有的格和边不能被普通表现层重复展开。
- `Connected` 应看见固定模块通路；`Count` 是否按总可行走格包含模块占用仍需冻结。`MaxConsecutive` 保持现有含义，只根据同层开口是否能沿单轴连续直行计数，不为楼梯或高厅增加“重新计数”或豁免规则：只有一个同层楼梯口的格自然不构成直行贯通；若一格确实有两个相对的同层出口，则继续计数是合理的。高厅上层净空与楼梯实体支撑虽然都对 WFC 表现为 Outside，但前者相邻上层路线通常需要栏杆，后者通常需要实体墙，因此表现阶段绝不能只读取二维 Domain。
- 性能风险主要来自完整结构占用和强制出口缩小可解空间，而不是 singleton 固定格本身。候选流程为：放置完整结构并选择开放口 → 校验三维占用冲突 → 生成各层约束 → 先解约束最紧楼层 → 逐层有界重试 → 超预算后重启整套结构放置结果 → 合并垂直边并全局验收。

### 2026-08-02 正式方案制定阶段核对

- 用户确认中间层不能出现“上楼后立即进入下一座上楼楼梯”；保证通关的上下楼梯口之间必须有有意义的本层路线。当前代码只有 `MaxRequiredRouteLengthTiles` 上限，没有对中间层路线过短的校验；多层方案需在完整平面图候选上增加最短路径下限，数值必须经批量 Seed 和实际走图调整。
- 现有 `DA_LevelGenerationProfile` 官方 MCP 实读为 `20x12`、单层可走格 `48~72`、最大连续直行 `4`、路线上限 `64`。若把 `48~72` 机械复制到六层，总可走格会膨胀为 `288~432`，与“增加结构复杂度而不是单纯延长关卡”冲突。正式计划必须先冻结整栋地图的总规模预算或分层规模配置，不得直接循环调用现有单层参数。
- 官方 MCP 确认 `BP_ZeroEscapeRuntimeLevelGenerator` 仍是 `AZeroEscapeRuntimeLevelGenerator` 的纯装配蓝图，EventGraph 与 ConstructionScript 均为空，且 Tick 关闭；方案应继续保持这一边界。当前 `FWfcSolver` 与 Count/MaxConsecutive/Connected 三项约束可作为稳定单层内核；需重构的是其上层目前写死单层 Start/Exit/房间放置的布局入口，以及其下层只会在 `Z=0` 生成地板/顶/墙/柱的结构展开。

### 2026-08-02 规模与旧实现审计输入

- 推荐继续收敛：若资产与调用复核仍无其他 Region 消费者，则把 `GetGeneratedCellWorldTransforms(RegionKind,...)` 改成明确的“普通可放置格查询”，并删除整套 `RegionKind` 局部身份；Start/Exit 继续用专门查询，跨层模块由 Plan 的模块实例表达，不塞进每个 WFC Tile。
- 推荐去重：Start/Exit 的地址与可推导 LocalTransform 不再双份持久保存；Cell 稳定性以排序后的三维地址为准，评估删除仅等于数组下标的 `StableCellId`；仅测试消费的 JunctionMetrics 改为测试/报告阶段派生，避免常驻 Plan。
- 推荐合并：Profile 配置验证是编辑资产的权威入口；低层 Solver 只校验自己直接依赖的不变量，并复用公共验证函数，不复制 Profile 的全部字段判断。
- 先基准测试再决定：`MaxWfcSolveAttempts` 外层重启是否优于“一次更完整的回溯预算”，以及每类矛盾计数是否都值得继续作为 Blueprint UPROPERTY 暴露。不得仅凭代码行数删除诊断能力。
- WFC 权重先收敛为共享一份；三档难度只保存已有明确用途的楼层数、规模和可选楼梯上限。将来只有实际试玩确认三档需要不同局部形态时，才恢复每档权重。

### 二、最小多层数据合同

- 用 UE 标准 `FIntVector(X,Y,Z)` 表示逻辑格地址，其中 `Z` 是从 0 开始的楼层索引；单层 WFC 内部继续使用 `FIntPoint`，不为地址再造一套名称体系。
- 最终普通格只保存三维地址与同层 4-bit OpeningMask；垂直边不塞进 OpeningMask。
- 最终 Plan 增加 `FloorCount`、每层可走统计，以及少量跨层模块实例。每个模块实例保存：模块种类、基准地址、旋转、实际开放口掩码、所占/保留格投影和内部跨层通行边；不保存“主路线格/支路格”等局部身份。
- 第一版结构种类只覆盖已存在需求：双层楼梯、贯通三层的楼梯间、高天花板房间。表现层继续由现有 HydroLab 构件展开；新增出口只派生开墙、连接地板和栏杆，不复制每一种出口组合的整座资产。
- 高厅上层净空与楼梯实体/支撑在三维占用中保持不同类别；两者对二维 WFC 都可投影为不可用格，但表现层分别生成临空栏杆或实体收边。
- Plan 记录模块实例是为了结构展开、全局通行图和未来 Population 查询；不在本次预埋摆锤、机关锚点、扫掠体积或装饰标签。

### 三、难度与规模合同

- 讨论阶段曾暂定 `Easy/Normal/Hard = 2/3/4` 层；正式 Plan 复核到这会与“困难不靠增加地图长度”冲突，因此推荐首版三档都先用 3 层，只调整额外楼梯概率。最终选择等待用户确认；无论选哪种，楼层数都来自 `FZeroEscapeDifficultyDefinition`，算法不得写死。
- 每档只增加四个互相有独立职责的规模边界：每层普通 WFC 可走格最小/最大、整栋总可走格最小/最大。总量统计包含楼梯/高厅自带的可走格；每层普通格下限不包含模块格，确保额外楼梯不会吃光可放置内容。
- 完整楼梯/房间的放置结果确定后，先计算每层固定可走格，再把整栋总量范围确定性地分配成每层 Count 范围；所有层的下限之和与上限之和分别落入整栋范围，不在最终完成后靠随机拒绝来碰总数。
- 冲突优先级固定为：保证每层可达所需的楼梯与每层普通内容下限 > 整栋总量范围 > 在满足可达后继续增加的楼梯和高天花板房间。后加内容先减少；必要结构与普通内容下限仍不可满足时，本次整体布局失败并重试，绝不静默突破约束。
- 首轮难度数值已收敛到正式 Plan 的 4.4 节：三档推荐保持相近总可走量，以额外双层楼梯整栋上限 `1/2/3` 和贯通三层楼梯间概率 `0%/20%/40%` 作为测试起点；若用户选择 `2/3/4` 层，则重新测量各档局长后再定总格数。

### 四、求解顺序

1. 解析 Request/Profile，得到楼层数、规模、求解预算与共享 16-state 权重；不同随机职责使用隔离子流，Difficulty/FloorIndex/完整结构尝试号进入稳定 Salt。
2. 放置保证通关的最低楼梯数量：每对相邻楼层至少一条物理连接；中间层的必需“到达口”和“继续上楼口”不能是同一处或一步相邻。
3. 在容量允许时，再尝试增加少量楼梯或贯通三层的楼梯间；如果增加失败，保留已经满足各层可达要求的基础布局，不把失败包装成固定兜底布局。
4. 放置高厅并完成全楼三维占用冲突检查；随后一次性冻结每个楼梯支持的实际开放口组合。
5. 把模块逐层投影为 Required/Outside/固定同层开闭边；按约束最紧的楼层优先调用现有二维 WFC。无 Start 的楼层从稳定排序的必需楼梯口选择 Connected 根，不新增另一套连通算法。
6. 每层完成后验收：全部普通格与模块口可达；中间层必需上下口的同层最短路达到可调下限；同一楼梯多个出口移除模块内部边后不得在过短距离内重新汇合。
7. 合并所有同层边与模块内部垂直边形成整栋通行图，一次 BFS/最短路验收 Start→Exit、全部楼层可达、必要穿层次序、总规模、主路线长度、局部死路深度与循环数量。主路线是临时从全局图导出的验收结果，不写进 WFC Tile 身份。
8. 任一楼层持续失败或全局验收失败，丢弃本次完整楼梯/房间放置结果并使用下一稳定尝试号重启；预算耗尽则结构化失败，不生成无效地图，也不切换到写死关卡。

### 五、表现与 Population

- 从 `ZeroEscapeGridLayoutSolver.cpp` 移出结构展开，建立独立多层 Structure Builder；普通格、模块格、净空边和共享边分别只有一个明确所有者，避免双地板、双墙、封死楼梯口和高厅补顶。
- 表现 Profile 增加真实需要的层高、楼梯与栏杆构件绑定；当前 V2 样板 `Z=0/450/900` 作为几何验收基线，最终数值仍由真实资产测量确认。
- Runtime Generator 仍同步、无 Tick、蓝图仅装配；查询普通候选格时返回正确楼层 Z，并默认排除楼梯/净空等不可放置区域。
- Gameplay Populator 不参与结构求解；摆锤未实现前只需保证高厅模块实例可在未来被查询，不为假想消费者增加规则系统。

### 六、代码与资产实施顺序（每步独立构建/测试）

1. **恢复可信基线**：修正两项已知过期自动化假设；不改生成结果，先让现有 18 项测试全绿。

## 2026-08-03 正式方案 v0.2 决定

- **导航检查分层**：正式每局只等待 `RecastNavMesh` 完成本轮更新，不再从 Start 对 Exit 和所有楼梯口逐个执行同步寻路。完整结构的每个旋转/楼层组合在装配测试中验证，代表性完整 Seed 在 PIE 中验证实际路径；若后续仍有偶发断路，再凭日志增加仅开发版本启用的诊断。
- **不重复检查**：WFC `Connected` 只负责求解期剪枝；每层从进入点做一次最短路遍历，同时得到本层连接口可达和路线跨越比例；最终三维通行图从 Start 做一次遍历，同时得到 Exit、所有楼层和楼梯口可达。各项指标从这些结果派生，不再单独重复 BFS。
- **每层进入点与离开点**：最下层为 Start/上楼口，中间层为下层到达口/上层离开口，最高层为到达口/Exit。必需端点优先尽量远，靠近边缘只是次要偏好，不限制方向或强制角落。
- **比例而非固定步数**：空间跨越比例为端点直线距离除以楼层对角线，首轮 `0.65`；路线跨越比例为端点最短路线除以从进入点到本层最远位置的路线，首轮 `0.75`。数值按难度保存在 DataAsset，第一轮先相同以便判断算法本身。
- **额外楼梯**：逐座选择到现有 Start、Exit 和全部楼梯口的最近距离尽可能大的候选；最近距离除以楼层对角线首轮不得低于 `0.25`，否则跳过。可位于未使用边缘或中央，不要求贴边。
- **偶发捷径**：贯通三层的楼梯间最多一座，不能替代相邻楼层必需楼梯，但允许跳过中间层平层路线；仍需在其覆盖的每一层远离其他端点。
- **难度与楼层数**：每档使用 `2/3/4` 层权重而非固定映射；正式 Plan 给出第一轮覆盖用权重。额外双层楼梯和贯通三层的楼梯间仍按难度分别配置，但第一轮三档先使用相同概率，先测清它们是在增加追逐压力还是主要提供逃生捷径，再决定难度方向；不得无证据地写成“越难楼梯越多”。
- **高天花板房间**：按难度配置整栋最低数量、整栋目标数量权重、每层上限和间距。某层可为零；目标数量放不下时降到整栋最低值，最低值仍不可放置才让本轮重试。

## 2026-08-03 正式方案 v0.3 审查修订

- **Room 结论不变**：正式 Profile 已回读为 `RoomCount=3/RoomSizeTiles=2/GridSize=20×12`。旧 Room 会改变占格、开边、Hash 和实例数，但没有正式玩法消费者，仍整链删除；审查意见只证明“删除后不能要求旧 Hash 不变”，不构成保留 Room 的理由。
- **检查点 1 拆分**：1A 只迁移表现构建，要求固定 Seed 的 Plan/Hash/HISM 数量不变；1B 删除 Room 并建立新基线，明确允许旧 Hash/实例数变化。
- **真实消费者迁移**：`RegionKind` 当前由 GameMode 和 Population 使用。先把 GameMode 改为读取明确的玩家/追猎者出生结果，把 Population/资产迁移到普通玩法对象候选查询，再删除旧枚举、`RegionId` 和 WFC 元数据透传；允许机械修改 `ZeroEscapeWfcSolver.h`，不改二维接口或算法。
- **导航门槛提前**：新增检查点 0.5，在正式 `L_Game` 用与运行时方案相同的隐藏坡面组件验证动态新增几何、目标 `RecastNavMesh` 完成事件、构建结束和真实追猎者路径存在；失败即停止多层重构。
- **事件不能单独代表本轮**：UE 完成事件只回传导航数据、不带 PCG 请求编号。Generator 需持久操作编号、目标导航数据和等待状态；`GenerateFromRequest=true` 只代表请求被接受，最终成功由完成事件报告。
- **v0.2 导航条目被本条覆盖**：正式每局在导航更新后，对追猎者/玩家出生点、Exit 和全部启用楼梯口做一次 `ProjectPointToNavigation + TestPathSync` 路径存在性验收；不计算长度/代价、不在 Tick 中重复。最大端点集合首轮总预算 `10ms`，失败保留原 Seed 并 fail-closed，不自动换 Seed。
- **审查建议没有原样采用的部分**：只把端点投射到导航面无法证明互相连通，不能用所谓“同一连通岛比较”代替实际路径存在性；单 Seed 墙钟时间也不能参与算法分支，否则会破坏跨机器确定性。
- **整栋共享预算**：首版最多 `4` 次完整布局尝试；候选、回溯、WFC 搜索树上限按楼层数从当前单层 `100000/25000/10` 线性扩展，所有楼层和完整重试共同消耗，不随重试再次放大。单 Seed 超过 `15s` 时停止后续批次并报告，但不据此改变该 Seed 的搜索分支。
- **异步正式流程**：主菜单请求与直接运行 `L_Game` 的默认请求走同一等待流程；玩家/追猎者/Exit、Population 和死亡绑定全部延后到最终成功。超时或失败清理、解绑并返回 `L_MainMenu`，不在本任务增加加载界面。
- **出生与终点楼层确认**：用户确认玩家出生点与追猎者初始点都留在一楼，Exit 固定为本局最高楼层；旧合同中的 `Start` 原本指玩家出生点，当前 GameMode 将其当作追猎者位置属于语义倒置，新合同改用 `PlayerSpawnCoordinate/PursuerSpawnCoordinate/ExitCoordinate` 三个明确字段，不延续含混的 `Start`。该确认不授权开始修改功能源码。
