## 已核对基线

- 当前 Runtime PCG 是二维 `20x12` Grid-WFC，逻辑格 `600cm`；每格只保存同层 `N/E/S/W OpeningMask` 与 `RegionKind`。
- WFC 已有局部开口一致性、非空格数量、最大连续直线、全图连通、有界时间序回溯和最终 Start→Exit 路线校验。
- 成功 Plan 先展开为 `300cm` 表现结构件，再以 HISM 提交；灯光、Population 与 GameFlow 保持在空间求解器之外。
- `Level0` 当前加载且非 Dirty。V1/V2 分别为 1836/1857 Actor；V2 保持 `600cm` 网格与 `Z=0/450/900` 三层走行面。
- V2 包含四座不可拆的 2x2 双层楼梯宏块、一座贯通三层的 2x2 楼梯塔、三层各一间 1x2 高厅，以及上层楼梯支撑/高厅贯穿所需保留占用。
- V2 可通行逻辑格数量（含每层两格高厅占用）为 L1/L2/L3=`33/27/25`；高厅位置为 L1 `(1,4)/(1,5)`、L2 `(6,4)/(6,5)`、L3 `(1,4)/(1,5)`。

## 当前核心缺口

- 二维 `FIntPoint GridSize` 与单层 `FZeroEscapeCollapsedTile` 无法表达楼层坐标、宏块实例、跨层占用和保留区。
- 单一 4-bit `OpeningMask` 无法表达接口宽度、FloorZ、净高类别、垂直连接、左右手性、落脚区和 StyleFamily。
- 现有 2x2 Room 只是四个 Required 格，不具备“不可拆原子宏块”语义。
- 当前结构展开只从同层闭边派生墙/顶/柱，缺少共享边唯一所有者、临空栏杆、楼梯固定装配、上层挖空和高度过渡派生。
- 当前 Count/Connected/路线验收只面向二维单层图；尚无每层楼梯配额、跨层全局连通和垂直宏块完整性约束。

## 初步候选方向（未决策）

- 倾向的小步方案：先在二维 WFC 之前确定少量垂直宏块和其各层占用/保留投影，再对每层剩余可用格运行现有二维求解，最后在合并后的跨层图上做全局连通与路线验收。

## 2026-08-02 双方案评估（讨论稿，未冻结）

### 共同前提

- 两种方案都需要三维 Plan/占用数据；真正的分歧是“WFC 候选域是否也统一升为三维”，不是要不要保存楼层坐标。
- 正交三维网格通常是 `±X/±Y/±Z` 六个面邻居，不是八邻居；楼梯通常横跨多个 `XY` 与楼层，不能只靠单格 `Up/Down` 开口表达。
- 高厅的上层空间是不可通行净空占用，不是垂直道路；通行连接、实体占用和净空保留必须分开建模。

### 方案 A+：三维占用骨架 + 分层二维 WFC

- 先以有界回溯放置完整的双层楼梯、三层楼梯塔和高厅宏块，并一次性写入所有受影响楼层的占用、支撑、净空与接口。
- 把宏块结果投影成各层的 Required/Blocked/Reserved/固定开口约束，再按“约束最多优先、楼层号稳定打破平局”的顺序调用现有二维 WFC。
- 各层完成后，把平面 OpeningMask 边与宏块内部跨层边合并成全局导航图，统一验证跨层连通、每对相邻楼层的连接配额、Start→Exit、循环/逃生路线和垂直切换次数。
- 第一版失败策略保持简单且确定：单层失败先消耗该层预算；持续失败则放弃本次宏块骨架并以新的派生 Seed 重启整轮，而不是维护复杂的跨阶段局部回滚。
- 可基本保留当前 `ZeroEscapeWfcSolver.*` 与 `ZeroEscapeWfcConstraints.*` 的 16 状态二维核心；主要新增宏块定义/放置器、三维 Plan/占用、全局图验收与跨层结构展开。

### 方案 B：统一三维 WFC

- 把 Wave 地址改为 `(X,Y,Z)`，邻接传播扩为六个面方向；Tile Variant 改为六面带类型接口，而不能只把 4-bit OpeningMask 扩成 6-bit。
- 双层/三层楼梯和高厅需要类似 Tessera Big Tiles 的多格模块：每种旋转/手性拆成内部 Part Variant，并用强制内部邻接保证整组同时出现；边界还要禁止残缺宏块。
- 当前 `uint16 FWfcDomain`、16 状态权重、四方向传播、Connected 展开图、MaxConsecutive、回溯 Trail、Plan Hash 和自动化测试都需直接改造。
- 统一域能自然传播任意上下层局部关系，但峰值 Domain、兼容表、全局回溯范围和矛盾定位都会显著扩大；固定 `GridSize.Z` 仍然只是有限三维 WFC，并不会自动获得无限楼层或流式生成。

### 当前比较结论

- 对固定 `2~6` 层，方案 A+ 更符合现有投资和 Demo 风险：六层相当于最多六次隔离的 `20x12` 求解，峰值仍是一层 Domain；方案 B 则是一个 `20x12x6` 联合搜索。若机械地完整枚举 6-bit 开口会有 64 种掩码；即使改用精简的带类型 Variant 集，宏块 Part、旋转和手性也会显著推高状态数。
- 当前 `ZeroEscapeWfcSolver.* + ZeroEscapeWfcConstraints.*` 约 2544 行，方案 A+ 可以把它们当作稳定内核；方案 B 会直接改动这部分及其约 1632 行现有测试，性质更接近求解器替换。
- 方案 A+ 的主要代价是阶段边界与重启策略；方案 B 的主要代价是状态/资产作者负担、全局矛盾与性能不确定性。
- 若未来确实需要大量自然生长的跨层局部组合，可先把“垂直宏块骨架放置器”替换成粗粒度三维 WFC，而不必立即把每个 `600cm` 细格全部纳入统一三维域。
- 用户已确认首版采用方案 A+：先确定主路线/跨层结构与完整多层模块，再逐层运行二维 WFC，最后合并全局通行图验收；不采用统一细格三维 WFC。

### 后室式体验的游戏性约束方向

- 目标应是“可控迷失”，不是不可读的立体随机迷宫：平层重复负责不安感，高厅、楼梯塔、楼层风格和声光差异负责重新定位。
- 宏观图应先控制主路线、追逐循环、垂直捷径、死胡同深度和楼层切换次数；WFC 负责局部走廊语法和变化，避免让局部邻接算法单独决定全部节奏。
- 双层楼梯可作为普通换层节点，三层塔可作为稀有地标/捷径，高厅可承担视野暴露、音效变化、奖励或事件空间，而不只是几何变化。
- 玩法默认可优先考虑 `3~4` 层，`5~6` 层作为大型局或特殊配置；这是讨论建议，尚未写入正式策划或 Profile。

### 用户已表达的布局偏好（部分待冻结）

- 整体希望存在一条隐含主路线，并从主路线长出支路与回接循环；不希望由局部 WFC 偶然形成完全无层次的迷宫。
- 希望玩家通常能经过生成出的各楼层，但暂不把“主路线必须经过每一层”定为硬约束；三层楼梯塔不是必备模块，若启用则再按地标、捷径或可选探索配置其角色。
- 用户已确认原话是“楼层不能成为死路”，不只是“楼层不得孤立”。这个玩法意图已确认；如何形式化为独立换层路径数量、主路线进出规则，以及三层楼梯塔能否单独满足要求，尚待讨论。
- 用户确认采用“主路线通常大体朝目标楼层推进、额外楼梯主要承担循环/捷径”的默认策略；`1→2→1→3` 一类折返只作为受限的高复杂度变化，不作为标准主路线。
- 用户认可禁止楼层级死路，但允许有界的局部短支路；短支路应能承载奖励、机关、线索或遭遇，具体最大深度与内容要求留给关卡 Profile 和 Seed 验收。

### 2026-08-02 楼梯口作为必达端点的讨论

- 用户提出：对每层建立必达端点集合，集合包含该层全部楼梯落脚口，以及位于该层的 Start/Exit；只需证明这些端点处于同一可达分量，不必为每对端点分别求路。
- 该方向与现有实现兼容：当前 Connected 已把所有被迫非空/开边节点作为 Relevant 集合，在 Potential 图上做分量与 Tarjan 传播；最终 Plan 也只从一个根执行一遍 BFS 并检查全部非空 Cell。
- 性能风险主要不是最终 BFS，而是楼梯位置、保留区、MaxWalkable 与强制开边共同收紧候选后导致的 WFC 回溯/整轮重试；必须以批量 Seed 的成功率、P95/P99 重试与耗时验证，暂不凭估计给出毫秒承诺。
- 尚需区分两个目标：端点集合连通可保证可达/可通关；若非目标楼层只有一个物理换层设施，它仍可能成为必须原路返回的楼层级叶子。是否额外禁止这种拓扑，仍待用户定义。

### 2026-08-02 楼梯约束设计输入

- 用户确认：以三层为例，中间层至少需要一个“来自下层”的落脚口和一个“通往上层”的起步口，并要求它们在本层平面网络中可达；起点层与终点层分别由 Start/Exit 补足主路线端点。
- 用户希望楼梯能扩展复杂度：同一楼层可存在少量多座楼梯，单座楼梯的落脚平台也可能有多个平面连接口，目前上限为三个。
- 约束设计必须分开统计：物理楼梯模块实例、模块内部连接相邻楼层的垂直边、各楼层落脚平台向平面网络开放的连接口。一个三出口平台不能自动计作三条独立换层路线。
- 当前 V2 的 A/B/C/D 双层楼梯与中央三层塔适合作为多模块、多连接口和占用冲突的压力样板，不直接等同于正式关卡的目标楼梯密度。
- 候选原则：先放满足 Start→Exit 的垂直主干；额外楼梯优先用于形成可测量的跨层循环/捷径。多连接口楼梯不必以强约束证明每个出口属于完全不同的关卡区域，但必须禁止数个出口在很短距离内立即重新汇合；具体距离阈值应作为可配置规则并用批量 Seed 验证，避免把视觉上不同的门洞生成成“假分支”。具体数量、主路线最短穿层距离与额外楼梯配额尚未冻结。
- 用户原始意图是让同一楼梯落脚平台实际开放的连接口组合能够随 Seed 变化，以增加复杂度和趣味性；尚未决定由模块变体固定、由放置阶段从受支持组合中随机选择，还是让二维 WFC 决定可选口。后续必须区分“独立随机开关”与“受主路线、可达性、出口间距和封口能力约束的随机选择”。
- 用户原则认可混合方案：楼梯核心与潜在连接口位置固定，由跨层结构规划阶段按 Seed 从模块支持的合法组合中选择实际开放口；未连接口封墙，开放口派生连接地板与栏杆收边。具体合法组合与权重仍待按模块逐项确认。
- 2026-08-02 通过官方 UE MCP 只读复核 `Level0` V2：A/B 双层楼梯各含固定 Base、Landing、Stair Flight 与 Platform；壳体在实际开口方向省略对应墙段。连接平台使用单位缩放 `SM_HydroLab_FloorB`，落脚区护栏使用 `SM_HydroLab_FenceC2` 等独立构件；三层塔以 `StackedPort`、`F2Port`、`SouthEntry` 等局部墙段表达多方向口。资产事实支持“固定楼梯核心 + 按开放边派生墙/地板/栏杆”，无需为每个出口组合复制整座楼梯资产。
- 用户进一步确认了楼梯数量的总体方向：先为每层建立可靠的上下通路，再把少量额外楼梯作为可调的复杂度变量；额外楼梯应谨慎增加，不以数量本身作为目标。下一步待冻结的是：中间层上/下楼梯口的最小路线距离、全局额外楼梯上限、三层楼梯塔首版是否只作可选捷径，以及额外楼梯放置失败时是否直接降低复杂度。

### 2026-08-02 高厅与后续玩法输入

- 高天花板房间的首要预期用途是承载摆锤机关，同时也可以作为路线复杂度、视野与空间节奏变化的节点。
- 项目当前只有高天花板房间，没有上层天桥需求；“上层天桥”是 Codex 在讨论中擅自扩展的内容，已撤回，后续不得把它当作候选范围。
- 摆锤当前尚未实现。继续保持现有 Plan/Population 职责分离：空间生成只提供高厅结构、上层净空与可供后续系统筛选的合法空间；不在本次 PCG 结构求解中硬编码摆锤、陷阱锚点、扫掠体积或具体机关放置。
- 主路线、支路、循环与距离属于整张通行图的规划、约束或派生结果，不复制成二维 WFC 的局部 Tile 身份。是否需要把其中某项持久保存到 Plan，必须由明确的 Population/玩法消费者驱动，不能预先堆积标签。
- 当前审计倾向保留二维 WFC 的 16 个 N/E/S/W 开口状态：多层地址、宏模块占用/保留区、模块实例/Part、垂直内部边、开放口选择和边所有权应扩展在 WFC 外层合同中。只有出现必须由普通平面 WFC 同时求解的多种接口宽度/高度或局部几何类别时，才有证据扩展 Variant；该结论仍需随数据合同一起冻结。
- 不为本次改造预先增加异步生成。继续保持最直接的完整实现：可以设计稳定、可扩展的数据合同，但不得以“最小”为由写死资产路径、关卡名、楼层数或特定楼梯，也不得增加未经性能证据证明必要的异步、兼容层或绕过逻辑。

### 2026-08-02 跨层模块逐层投影候选（讨论稿）

- “逐层投影”是本项目候选实现描述，不是 WFC/UE 官方术语：先原子选择并放置完整楼梯或高厅，再把它在各楼层产生的可行走拓扑、实体占用、净空保留和开闭边转换为现有二维 Solver 输入；模块实例仍是唯一事实源，不能把投影后的格子重新当成可独立随机选择的普通 Tile。
- 当前首选是“固定拓扑格投影”：模块在某层的可行走逻辑格以精确 N/E/S/W Mask 固定进二维 WFC；模块内部恒开平面边与本次 ActiveMouthMask 共同形成该精确 Mask。实体/支撑与净空格都对 WFC 投影为 Outside，但外层 Plan 必须保留二者差异；楼梯的跨层边不进入 4-bit Mask，待各层完成后合并到全局图。
- 该方案可复用现有 `RequiredOpenMask/RequiredClosedMask`、邻接对称传播与 Connected；固定模块格作为 singleton 参与连通性，因此多个外部出口可以通过真实落脚平台连接。模块原子性由投影前放置保证，WFC 无权只保留其中一部分。
- 不首选“把模块 footprint 全部排除、只在最终图合并”：当前二维邻接会把指向 Outside 的边关闭，Connected 也看不到模块对多个出口的连接，容易早期误拒绝或晚期大量失败。也不预先把任意模块内部图直接接入 Connected/Tarjan；后者更精确但会显著改造稳定约束内核，只在真实模块无法以每格单一平面拓扑等价投影时再讨论。
- 必须验证的主要问题：模块每层投影与真实通路图等价；同格不得存在两个不同高度且互不相连的通路；Active Mouth 必须在求解前冻结；旋转/镜像必须统一变换格偏移、方向与 Mask；模块 Walkable/Solid/Clearance 冲突必须 fail-closed；模块拥有的格和边不能被普通表现层重复展开。
- `Connected` 应看见固定模块通路；`Count` 是否按总可行走格包含模块占用仍需冻结。`MaxConsecutive` 保持现有含义，只根据同层开口是否能沿单轴连续直行计数，不为楼梯或高厅增加“重新计数”或豁免规则：只有一个同层楼梯口的格自然不构成直行贯通；若一格确实有两个相对的同层出口，则继续计数是合理的。高厅上层净空与楼梯实体支撑虽然都对 WFC 表现为 Outside，但前者相邻上层路线通常需要栏杆，后者通常需要实体墙，因此表现阶段绝不能只读取二维 Domain。
- 性能风险主要来自模块占用和强制出口缩小可解空间，而不是 singleton 固定格本身。候选流程为：放置大模块并选择开放口 → 校验三维占用冲突 → 生成各层投影 → 先解约束最紧楼层 → 逐层有界重试 → 超预算后重启整套模块骨架 → 合并垂直边并全局验收。

## 2026-08-02 正式实施 Plan 草案 v0.1（等待用户冻结）

### 一、保留、删除与先测后定

- 保留：二维 16 个 N/E/S/W OpeningMask、Count、MaxConsecutive、Connected、有界回溯、纯值 Plan、确定性 Hash、同步事务式提交、HISM 结构表现，以及 Plan/Population 分离。
- 推荐删除而不做兼容包装：`RoomSizeTiles/RoomCount/MaxRoomCount`、`FZeroEscapeGeneratedRoom`、`Plan.Rooms`、`GetGeneratedRoomWorldTransforms`、`ERandomDomain::RoomPlacement`、只服务房间的 `RegionId/RegionKind::Room` 与对应校验/Hash/测试。
- 推荐继续收敛：若资产与调用复核仍无其他 Region 消费者，则把 `GetGeneratedCellWorldTransforms(RegionKind,...)` 改成明确的“普通可放置格查询”，并删除整套 `RegionKind` 局部身份；Start/Exit 继续用专门查询，跨层模块由 Plan 的模块实例表达，不塞进每个 WFC Tile。
- 推荐去重：Start/Exit 的地址与可推导 LocalTransform 不再双份持久保存；Cell 稳定性以排序后的三维地址为准，评估删除仅等于数组下标的 `StableCellId`；仅测试消费的 JunctionMetrics 改为测试/报告阶段派生，避免常驻 Plan。
- 推荐合并：Profile 配置验证是编辑资产的权威入口；低层 Solver 只校验自己直接依赖的不变量，并复用公共验证函数，不复制 Profile 的全部字段判断。
- 先基准测试再决定：`MaxWfcSolveAttempts` 外层重启是否优于“一次更完整的回溯预算”，以及每类矛盾计数是否都值得继续作为 Blueprint UPROPERTY 暴露。不得仅凭代码行数删除诊断能力。
- WFC 权重先收敛为共享一份；三档难度只保存已有明确用途的楼层数、规模和可选楼梯上限。将来只有实际试玩确认三档需要不同局部形态时，才恢复每档权重。

### 二、最小多层数据合同

- 用 UE 标准 `FIntVector(X,Y,Z)` 表示逻辑格地址，其中 `Z` 是从 0 开始的楼层索引；单层 WFC 内部继续使用 `FIntPoint`，不为地址再造一套名称体系。
- 最终普通格只保存三维地址与同层 4-bit OpeningMask；垂直边不塞进 OpeningMask。
- 最终 Plan 增加 `FloorCount`、每层可走统计，以及少量跨层模块实例。每个模块实例保存：模块种类、基准地址、旋转、实际开放口掩码、所占/保留格投影和内部跨层通行边；不保存“主路线格/支路格”等局部身份。
- 第一版结构种类只覆盖已存在需求：双层楼梯、三层楼梯塔、高天花板房间。表现层继续由现有 HydroLab 构件展开；新增出口只派生开墙、连接地板和栏杆，不复制每一种出口组合的整座资产。
- 高厅上层净空与楼梯实体/支撑在三维占用中保持不同类别；两者对二维 WFC 都可投影为不可用格，但表现层分别生成临空栏杆或实体收边。
- Plan 记录模块实例是为了结构展开、全局通行图和未来 Population 查询；不在本次预埋摆锤、机关锚点、扫掠体积或装饰标签。

### 三、难度与规模合同

- `Easy/Normal/Hard` 暂定解析为 `2/3/4` 层；保存在 `FZeroEscapeDifficultyDefinition`，算法不得写死。
- 每档只增加四个互相有独立职责的规模边界：每层普通 WFC 可走格最小/最大、整栋总可走格最小/最大。总量统计包含楼梯/高厅自带的可走格；每层普通格下限不包含模块格，确保额外楼梯不会吃光可放置内容。
- 模块骨架确定后，先计算每层固定模块可走格，再把整栋总量范围确定性地分配成每层 Count 范围；所有层的下限之和与上限之和分别落入整栋范围，不在最终完成后靠随机拒绝来碰总数。
- 冲突优先级固定为：必要楼梯与每层普通内容下限 > 整栋总量范围 > 可选双层楼梯/三层塔/高厅。可选模块先减少；必要结构与普通内容下限仍不可满足时，本次骨架失败并重试，绝不静默突破约束。
- 首轮 Seed Sweep 建议起始区间（调参起点，不是最终策划值）：Easy `2 层 / 普通格每层 54~68 / 总可走 120~144 / 额外楼梯最多 1`；Normal `3 层 / 44~56 / 144~174 / 最多 1`；Hard `4 层 / 36~48 / 164~200 / 最多 2`。需结合模块真实占格、生成 P95/P99 和实走疲劳度调整。

### 四、求解顺序

1. 解析 Request/Profile，得到楼层数、规模、求解预算与共享 16-state 权重；不同随机职责使用隔离子流，Difficulty/FloorIndex/骨架尝试号进入稳定 Salt。
2. 放置保证通关的楼梯骨架：每对相邻楼层至少一条物理连接；中间层的必需“到达口”和“继续上楼口”不能是同一处或一步相邻。
3. 在容量允许时尝试少量额外楼梯和可选三层塔；单个可选模块失败先省略，不把失败包装成固定兜底布局。
4. 放置高厅并完成全楼三维占用冲突检查；随后一次性冻结每个楼梯支持的实际开放口组合。
5. 把模块逐层投影为 Required/Outside/固定同层开闭边；按约束最紧的楼层优先调用现有二维 WFC。无 Start 的楼层从稳定排序的必需楼梯口选择 Connected 根，不新增另一套连通算法。
6. 每层完成后验收：全部普通格与模块口可达；中间层必需上下口的同层最短路达到可调下限；同一楼梯多个出口移除模块内部边后不得在过短距离内重新汇合。
7. 合并所有同层边与模块内部垂直边形成整栋通行图，一次 BFS/最短路验收 Start→Exit、全部楼层可达、必要穿层次序、总规模、主路线长度、局部死路深度与循环数量。主路线是临时从全局图导出的验收结果，不写进 WFC Tile 身份。
8. 任一楼层持续失败或全局验收失败，丢弃本次完整模块骨架并使用下一稳定尝试号重启；预算耗尽则结构化失败，不生成无效地图，也不切换到写死关卡。

### 五、表现与 Population

- 从 `ZeroEscapeGridLayoutSolver.cpp` 移出结构展开，建立独立多层 Structure Builder；普通格、模块格、净空边和共享边分别只有一个明确所有者，避免双地板、双墙、封死楼梯口和高厅补顶。
- 表现 Profile 增加真实需要的层高、楼梯与栏杆构件绑定；当前 V2 样板 `Z=0/450/900` 作为几何验收基线，最终数值仍由真实资产测量确认。
- Runtime Generator 仍同步、无 Tick、蓝图仅装配；查询普通候选格时返回正确楼层 Z，并默认排除楼梯/净空等不可放置区域。
- Gameplay Populator 不参与结构求解；摆锤未实现前只需保证高厅模块实例可在未来被查询，不为假想消费者增加规则系统。
