## 1. 总结结论

当前实现已经是一套真实的 Runtime Grid-WFC，而不是固定路线、房间块随机拼接或仅随机撒物：

1. 每个逻辑格使用完整的 0..15 四方向 OpeningMask 状态，其中 0 是 Empty，1..15 覆盖死路、直路、拐角、T 字和十字。状态定义见 Source/Demo/Private/PCG/ZeroEscapeWfcSolver.h:57-67，固定构造见 Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:939-951。
2. WFC 同时执行局部开口一致性、非空格数量、连续直线长度和全图连通约束，并使用有界 chronological backtracking。主循环见 Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:1101-1290。
3. Start、Exit 和 2×2 房间只作为必定非空的空间约束；房间以外的连接由 WFC 自己决定，不存在预先画好的 L 型主路线。嵌入逻辑见 Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:251-340。
4. WFC 输出纯数据 Plan 后，代码从非空格边界推导地板、天花板、墙、墙顶 Trim 和柱子，再用 HISM 提交场景。结构展开见 Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:860-987，世界提交见 Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:277-375。
5. 顶灯、批量玩法对象和唯一角色/出口没有进入 WFC 状态：
   - 顶灯属于 Presentation，见 Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:378-482。
   - 地刺等批量对象属于 Population，见 Source/Demo/Private/PCG/Population/ZeroEscapeGameplayPopulator.cpp:57-133。
   - 玩家、唯一追猎者和 Exit 属于 GameFlow，见 Source/Demo/Private/GameFlow/ZeroEscapePrototypeRoundFlow.cpp:101-260。
6. 当前源码中没有 Socket、A*、Progression Graph、K-of-N 或旧 RuntimeGenerationTestHarness 逻辑。它们不是隐藏依赖，也不需要为了保留当前 WFC 而恢复。
7. “实时、非工具”在代码边界上成立：生成发生于 GameWorld 的 BeginPlay 或显式调用，且只允许 Game Thread；模块没有 UnrealEd 或 UE 官方 PCG 模块依赖。入口见 Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:125-167，模块依赖见 Source/Demo/Demo.Build.cs:5-13。

总体判断：当前空间核心可以保留，WFC 回溯也应保留。下一阶段的主要问题不在于重写 WFC，而在于补齐下游放置契约、失效通知、导航/净空验证和可视化，同时保持这些玩法规则不污染空间求解器。

## 4. 数据模型

### 4.1 请求与版本

- 一局请求只有 Seed 和 Difficulty：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:127-140。
- 默认 Seed 是 12345，但关卡中 Generator 的 DefaultRequest 可编辑：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:133-139 与 Source/Demo/Public/PCG/ZeroEscapeRuntimeLevelGenerator.h:150-156。
- UI 将来不必重新编译，可以构造 FZeroEscapeGenerationRequest 并调用 GenerateFromRequest：Source/Demo/Public/PCG/ZeroEscapeRuntimeLevelGenerator.h:64-70。
- Signature 同时记录算法、Generation Profile 和 Presentation 版本：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:142-170。
- 当前算法版本是 5：Source/Demo/Private/PCG/ZeroEscapeGenerationCore.h:17-18。

### 4.2 Plan

成功 Plan 是纯值，不保存 UObject 或素材路径：

- GridSize、LogicalTileSize：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:248-252。
- 非空 Cells：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:254-255。
- Start/Exit 坐标和 Transform：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:257-267。
- 中立房间：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:269-270。
- 形态观测计数：Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:214-233。

Cell 的 OpeningMask 是结构拓扑，RegionKind 是空间语义；两者是两个维度。一个 Room Cell 仍然使用同一套 OpeningMask，不存在“房间专用 WFC Tile”。

### 4.3 Hash 的准确含义

CanonicalLayoutHash 混入 Seed、Difficulty、算法版本、Generation Profile 版本、Grid、Start/Exit、Cells 和 Rooms：Source/Demo/Private/PCG/ZeroEscapeGenerationCore.cpp:109-170。

它不混入 PresentationVersion 和浮点 Transform。因此：

- 它适合判断“同一逻辑生成身份是否复现”。
- 它不是纯几何去重 Hash，因为相同拓扑但不同 Seed 仍会产生不同 Hash。
- 更换同尺寸 Mesh 不会改变 Hash；修改空间 Profile 版本应改变 Hash。

## 5. Grid 预约束

### 5.1 Grid 与固定锚点

- 全 Grid 初始为 Optional，外边界方向强制关闭：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:147-172。
- Start 固定在 X=1、中线偏下一格；Exit 固定在 X=GridSize.X-2、中线偏上一格：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:260-278。
- 这不是固定路线，但会形成稳定的“左侧出生、右侧出口”空间偏置。

### 5.2 房间

- 房间 X 位置不是随机搜索，而是在合法 X 区间等距分布：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:280-295。
- 每个房间随机选择中线上方或下方 Lane：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:285-305。
- 每间房当前固定为 2×2；四格全部 Required，内部水平/垂直边全部 RequiredOpen：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:307-338。
- 房间外侧没有预设门口。WFC 必须为它找到至少一条外部连接，也可以得到多个连接；Connected 约束会阻止孤立房间。

因此，当前房间的准确说法是“同一逻辑网格上的 2×2 必走区域”，不是完整房间 Actor，也不是墙面 Socket 拼接。

## 6. WFC 实现

### 6.1 状态集合

- Domain 是 uint16，每个 bit 对应 OpeningMask 0..15：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.h:24-30。
- Empty 是 mask 0；Required 排除 Empty；Optional 可 Empty 或 NonEmpty：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.h:28-55。
- 每种旋转方向是独立 mask，但同形态共享权重：Source/Demo/Private/PCG/ZeroEscapeGenerationAssets.cpp:66-92。
- 十字、T 字、拐角是“有概率出现”，不是硬性数量配额：Source/Demo/Public/PCG/ZeroEscapeGenerationAssets.h:75-102。

### 6.2 局部邻接

每条公共边只有一个规则：两侧对应方向必须同时开或同时闭。过滤实现见 Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:592-646，传播队列见 648-742。

这正是当前素材不需要 Socket 的原因：WFC 只生成抽象开口，墙体随后从“闭边”推导；Mesh 的 Pivot 差异由 Presentation 的 PivotCorrection 消化。

### 6.3 最低带权熵

- 熵计算使用 Shannon 形式：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:384-407。
- 同熵 Cell 用 Seed 驱动的蓄水池抽样消除固定行扫描偏置：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:445-496。
- 候选顺序按权重无放回一次生成，回溯时不重新消费随机数：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:499-532。

### 6.4 Count

Count 同时维护“已经被迫非空”和“仍可能非空”的数量：

- 超过 Max 或无法达到 Min 时立即矛盾：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:229-274。
- 达到 Max 时把其余 Maybe 格固定 Empty；必须全部 NonEmpty 才能达到 Min 时删除 Empty：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:276-303。

这保证最终非空格数落在 MinWalkableCellCount 与 MaxWalkableCellCount 之间。

### 6.5 MaxConsecutive

- 水平方向要求同时有 East+West，垂直方向要求同时有 North+South；T 和 Cross 也会按对应轴计入：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:56-62。
- 对长度 Max+1 的滑动窗口做线性扫描，窗口全被迫贯通就矛盾；只剩一个弹性格时 Ban 它的贯通状态：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:307-410。
- 全部行和全部列都检查：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:412-456。

它限制的是直线视线轴，不限制整条路线总长度，也不禁止多个短直段通过拐角连接。

### 6.6 Connected

Connected 不是最终才跑一次 BFS，而是在搜索过程中传播：

- 每格展开为“中心 + N/E/S/W 四个方向节点”：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.h:120-146。
- Potential 表示仍可能成为路径，Relevant 表示已经被迫成为路径：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:459-513。
- 多个 Relevant 分量立即矛盾；没有 Relevant 的孤立 Potential 分量被剪除：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:515-612。
- 唯一 Relevant 分量使用迭代 Tarjan 找关节点；必要中心强制非空，必要方向强制开口：Source/Demo/Private/PCG/ZeroEscapeWfcConstraints.cpp:620-742。

结果是所有最终非空格都必须属于 Start 的同一连通分量，不只是 Start 能到 Exit。

### 6.7 回溯

当前已经实现回溯，且不是简单“失败就换 Seed”：

- 所有 Domain 缩减先写 Trail：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:535-569。
- Decision 保存 Cell、候选顺序、下一候选和 TrailStart：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:22-41。
- 失败后逆序恢复到对应 TrailStart，再尝试同一帧下一候选：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:571-590 与 1246-1285。
- 根稳定点产生的全局 Ban 会清空 Trail 但保留 Domain，避免回溯错误恢复根约束：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:1126-1131。
- 候选和回溯都有硬预算：Source/Demo/Private/PCG/ZeroEscapeWfcSolver.cpp:1153-1166 与 1246-1279。

因此不建议删除 WFC 回溯。路线长度只在完整叶可知，房间入口和全局连通也会制造需要探索替代候选的情况；删除回溯会把大量本可恢复的分支误报成生成失败。

### 6.8 完整叶验收与有限重试

- 完成叶先导出 Plan，再用 BFS 验收全图可达、Exit、Room Anchor 和 Start→Exit 最短距离：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:409-525。
- 只有“路线过长”会作为可恢复叶拒绝继续回溯；其它 Plan 不变量错误立即终止：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:651-691。
- 单棵搜索树预算耗尽时，Grid 层才用同 Seed、不同 Salt 建立下一棵确定性搜索树：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:630-746。
- 候选和回溯总预算被平均分片，不会因重试次数成倍放大：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:575-585 与 639-646。

生成仍可能失败，主要原因是：

- Profile 或素材配置非法。
- Min/Max、房间、Grid 容量互相矛盾。
- WFC 搜索树真正无解。
- 候选或回溯预算耗尽。
- 所有完整叶都超过路线长度上限。
- HISM 或灯 Actor 实例化失败。

失败枚举见 Source/Demo/Public/PCG/ZeroEscapeGenerationTypes.h:55-79。

## 7. 结构与素材表现

### 7.1 600 cm 逻辑格与 300 cm 结构单元

当前代码硬性要求：

- LogicalTileSizeCm=600。
- RoomSizeTiles=2。
- StructureUnitSizeCm=300，且与逻辑格保持 2:1。

Generation 校验见 Source/Demo/Private/PCG/ZeroEscapeGenerationAssets.cpp:149-162，Presentation 校验见 285-300，结构展开再次校验见 Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:860-880。

每个非空 600 cm 逻辑格生成：

- 2×2 共 4 块 Floor。
- 2×2 共 4 块 Ceiling。
- 每条闭边拆成两段 300 cm Wall；共享闭边按 Key 去重。
- 每段墙可生成一段 WallTopTrim。
- 墙图的端点、转角、T/Cross 顶点生成 Pillar。

代码位置：Source/Demo/Private/PCG/ZeroEscapeGridLayoutSolver.cpp:883-987。

### 7.2 Presentation Profile

表现层可以替换：

- Floor、Ceiling、Wall、可选 WallTopTrim、可选 Pillar：Source/Demo/Public/PCG/ZeroEscapeGenerationAssets.h:182-197。
- 每类 Mesh 的 PivotCorrection、CollisionProfile 和是否影响导航：Source/Demo/Public/PCG/ZeroEscapeGenerationAssets.h:140-158。
- Floor/Wall/Ceiling Z 高度：Source/Demo/Public/PCG/ZeroEscapeGenerationAssets.h:170-180。

当前扩展边界是“同占地、同尺寸契约下换素材很方便”；不是“任意尺寸素材无代码接入”。运行时只验证 Mesh 存在、Transform 有限且 Unit Scale、碰撞 Profile 注册，并不会自动验证 Mesh Bounds、真实 Pivot、碰撞净空或接缝。校验代码见 Source/Demo/Private/PCG/ZeroEscapeGenerationAssets.cpp:17-63。

因此未来换素材时仍需做一次尺寸、Pivot、碰撞和 PIE 实拼；这不是 WFC 不可扩展，而是表现契约目前有意固定为已经验证的 600:300 基线。

### 7.3 HISM 提交

- 每种结构最多创建一个 HISM，当前最多五组：Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:304-373。
- PivotCorrection 先于规范 Transform：Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:358-369。
- 创建后立即登记，任一后续失败统一销毁：Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:337-350 与 495-516。

Generator 是“先求完整 Plan，再提交场景”。但重新生成时旧场景会在新求解开始前清除：Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:155-167。也就是说，单次新场景提交是事务式的，但跨重生成不会保留上一张成功地图作为失败回退。

### 7.4 顶灯

- 开关、灯 Actor 类和局部修正属于 Presentation：Source/Demo/Public/PCG/ZeroEscapeGenerationAssets.h:199-218。
- 生成器选择非空格中数量较少的棋盘奇偶组，约每两个逻辑格一盏；若 Start 不在选中组，额外补 Start 灯：Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:397-443。
- 灯具强度、颜色、半径仍由灯 Blueprint 拥有，PCG 不复制参数：Source/Demo/Public/PCG/ZeroEscapeGenerationAssets.h:206-218。

当前 Min/MaxWalkable=48/72 时，通常约 24 到 36 盏，再视 Start 奇偶性最多补一盏。代码没有灯数指标、性能预算或距离裁剪；是否适合当前高质量渲染设置仍需实际性能采样。

## 8. Runtime Generator 状态与查询

### 8.1 状态机

状态依次为 Idle、Planning、Validating、Instantiating、Ready 或 Failed：Source/Demo/Public/PCG/ZeroEscapeRuntimeLevelGenerator.h:22-31。

请求门禁：

- 必须在 Game Thread。

### 9.2 当前限制

- 所有规则共享一个 RNG，且按数组顺序连续消费：Source/Demo/Private/PCG/Population/ZeroEscapeGameplayPopulator.cpp:73-100。新增或重排前一条规则会改变后续规则的位置；“同 Seed 可复现”成立，但“每条规则互不扰动”不成立。
- 不同规则没有占位表，可能选择同一格；Spawn 使用 AlwaysSpawn，也不做重叠检查：Source/Demo/Private/PCG/Population/ZeroEscapeGameplayPopulator.cpp:75-78 与 80-127。
- 不验证是否封死关键路线、是否影响角色/铁板净空、是否与其它玩法对象冲突。
- 软类引用在生成回调中 LoadSynchronous：Source/Demo/Private/PCG/Population/ZeroEscapeGameplayPopulator.cpp:80-85。当前单类可接受，规则增多时可能产生运行时加载卡顿。
- 日志中的“放置 N 个”记录的是 TargetCount 位置数，不是乘以 LateralCount 后的成功 Actor 数：Source/Demo/Private/PCG/Population/ZeroEscapeGameplayPopulator.cpp:103-131。

因此，“新增一类对象只加一条规则”只适用于共享现有散布语义的简单对象。需要唯一性、顺序、占位、堵路验证、房间属性或任务状态的对象，不应硬塞进当前通用规则。

## 15. 风险与审计结论

### 15.1 未发现当前空间核心的阻断级正确性问题

静态审阅没有发现需要立刻删除回溯、恢复 A*、恢复 Socket 或重写 WFC 的证据。核心搜索的状态所有权、Trail 恢复、根稳定点和完整叶拒绝都有针对性测试。

但“未发现”只代表本轮静态审阅；当前工作区未重新跑构建和测试。

### 15.2 建议优先处理的边界问题

#### A. ClearGeneratedScene 不通知下游失效

- Generator 公开 Clear 后直接回到 Idle：Source/Demo/Private/PCG/ZeroEscapeRuntimeLevelGenerator.cpp:485-516。
- Population 与 RoundFlow 只监听 OnGenerationFinished：Source/Demo/Private/PCG/Population/ZeroEscapeGameplayPopulator.cpp:35-41；Source/Demo/Private/GameFlow/ZeroEscapePrototypeRoundFlow.cpp:63-70。

如果外部在 Ready 后只调用 ClearGeneratedScene，不紧接一次生成，旧地刺、追猎者和出口可能留在空场景中。当前流程没有这样调用，所以不是现有验收阻断；未来做重开/返回菜单时应明确“Clear 只允许内部使用”或增加失效事件。

#### B. Population 的可扩展性只到简单散布

当前没有稳定 RuleId、独立随机域、占位表、跨规则冲突或放置后路线复验。未来增加第二类陷阱、奖励和物理物体时，先补最小候选记录与占位，不要复制多个 Populator 或修改 WFC。

#### C. 当前自动化不覆盖最近改动

直走廊筛选、横向并排和玩家/追猎者位置对调都在当前未提交 diff 中，但两个测试文件未修改。用户已经做过主视口验收，仍建议下一次功能改动前补最小纯值/World 测试或至少做多 Seed PIE。

#### D. 难度当前没有空间差异

代码能力已预留，但集成测试把三档权重锁成完全相同。若产品现在就要求“困难路线更复杂但不延长单局”，应只重分配 Straight/Corner/T/Cross/DeadEnd，并保持 Empty 与非空总权重相同；不需要改 WFC 算法。

### 15.3 可按需求再处理的问题

- 600:300 和 2×2 房间硬锁：只有第二套真实尺寸契约出现时再抽象。
- Start/Exit 和房间 Lane 的固定空间偏置：需要更多入口布局变化时再扩展。
- 顶灯 Actor 数量与高质量渲染性能：先采样，不先做灯池或复杂裁剪。
- Population 同步软类加载：规则增多并出现卡顿后再预加载。
- RoundFlow 使用二维直线距离：导航和追逐质量进入验收时再换成 Grid/Nav 距离。
- 日志位置数与 Actor 数语义：排障需要精确计数时修正。

## 16. 推荐的扩展边界

### 16.1 小地图

小地图应读取空间结果，不参与 WFC。最小所需数据是 GridSize、非空 Cell 坐标、OpeningMask、Start、Exit、Room RegionId。当前 LastPlan 已有这些数据，但没有安全公开接口。

推荐后续新增只读快照或枚举接口，不把 LastPlan 设为公开可写，也不让 Widget 直接依赖 Private Solver 类型。

### 16.2 K-of-N 收集目标

K-of-N 属于一局目标状态，不属于 WFC。空间层只需提供一组可达候选 Anchor；目标系统选择 N 个、维护已收集数量 K、决定何时激活 Exit。

若候选需要“不要长回头路”，应在放置层基于 Cell 图距离挑选，而不是增加新的 WFC Tile 状态。

### 16.3 多敌人

多敌人属于 GameFlow/Enemy Spawn Policy。空间层提供候选和距离；玩法层决定数量、出生间距、房间类型和难度。不要让 Generator 直接 Spawn 第二个敌人。

### 16.4 新陷阱、奖励和磁性物体

- 只需要区域、密度、横向排列：继续加 Population Rule。
- 需要互斥、最小间距、总预算：给 Population 增加共享占位/预算。
- 可能堵路：放置后在 Cell 图或简化净空图上验证，并撤销该对象或换候选。
- 需要任务状态：由独立玩法系统拥有，Population 只负责 Spawn。

### 16.5 房间风格与素材变化

风格选择应在 Presentation/Palette 层按 RegionId 或连续走廊段决定。只有会改变开口、占地、层高或净空的模块，才需要进入结构规则；纯墙面、地板、灯、Trim 变化不增加 WFC 状态。

## 19. 最终判断

建议保留：

- 完整 16-mask WFC。
- Count、MaxConsecutive、Connected 三类约束。
- 当前有界回溯和确定性有限重试。
- 纯 Plan → 结构展开 → Runtime 提交的单向流程。
- Presentation、Population、GameFlow 的职责拆分。

下一步最值得做的不是继续扩张求解器，而是：

1. 用这份报告作为基线讨论小地图需要的只读拓扑接口。
2. 明确 Population 下一类真实对象后，再决定是否需要稳定 RuleId、占位和路线复验。
3. 在追猎者真正依赖生成地图寻路前，补多 Seed NavMesh 与追逐质量验收。
4. 需要难度差异时先改三档形态权重，不改地图规模，也不改 WFC 架构。

不建议恢复或新增：

- Socket 拼接层。
- A* 预画固定主路线。
- 旧 Harness。
- 为尚未确定的目标系统提前加入 K-of-N、任务图或通用 Validator 框架。
