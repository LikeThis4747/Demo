# AI 记忆、任务与交接工作流

## 1. 三层信息模型

| 层级 | 内容 | 位置 | 默认读取 |
|---|---|---|---|
| L0 启动 | 不可违反的规则、入口导航 | `AGENTS.md` | 是 |
| L1 工作 | 当前任务、任务卡、错误、交接 | `.ai-context/`、`claude/tasks/`、`claude/handoffs/` | 仅相关项 |
| L2 记忆 | 项目事实、架构、进度、决策、每日记录 | `memory-bank/` | 搜索后按需读取 |

不要把聊天流水写进长期记忆。长期记忆只保存未来仍有用、能改变后续决策的信息。

## 2. 记忆职责

| 文件 | 内容 |
|---|---|
| `.ai-context/current-task.md` | 主任务的一页恢复摘要：目标、阶段、阻塞、下一步 |
| `.ai-context/latest-error.md` | 当前仍有效的错误；解决后标记结论或清空 |
| `memory-bank/activeContext.md` | 当前迭代目标、活跃任务索引、近期决定 |
| `memory-bank/projectbrief.md` | 稳定项目定义、范围和非目标 |
| `memory-bank/progress.md` | 里程碑和功能完成状态 |
| `memory-bank/techContext.md` | 引擎、模块、插件、构建和性能配置 |
| `memory-bank/systemPatterns.md` | 已验证并应重复使用的架构模式 |
| `memory-bank/decisions.md` | 重要决策、理由、替代方案和影响 |
| `memory-bank/daily.md` | 按日期倒序记录完成、验证和遗留事项；每日只写一次或少量汇总 |

所有 `.ai-context/` 和 `memory-bank/` 内容必须通过 Memory MCP 读写，以获得原子写入、备份和容量限制。

## 2.1 术语与表达规范

对外交流、方案、报告、PPT 和代码说明中的技术名词必须区分来源，不得把不同层级的名称混写成通用概念：

1. **UE 官方名称**：来自 UE API、编辑器界面或引擎源码的名称，例如 `GameMode`、`Delegate`、`HISM`、`Physics Handle`。需要用户在编辑器或代码中定位时，使用“直白中文（官方英文名）”。
2. **已有算法或行业术语**：能够在论文、官方文档或可靠技术资料中核对的名称，例如 WFC（Wave Function Collapse）和 Simple Tiled Model。首次出现时给出全称和一句用途说明。
3. **项目内部命名**：只存在于当前代码、资产或文档中的类名、模块名和字段名，例如 `Population`、`Connected`、`Layout Hash`。必须明确写成“项目中的……”，并解释它在本项目里具体做什么；不得暗示它是 UE 或原始算法的标准组成。
4. **解释性简称**：AI 为方便说明而临时概括的词，例如“状态 Owner”“Grid-WFC”。面向用户和 PPT 默认不用；确有必要时必须先写“本文简称”，当场定义，并在后文保持同一含义。

输出前先用当前代码、资产、引擎源码或官方资料确认术语来源。无法确认时改用直白中文描述事实，不通过造词掩盖不确定性。用户质疑某个词时，立即说明它属于以上哪一类，并修正此前可能造成的误导，不得默认用户应该理解未定义术语。

## 3. 任务卡与并行 AI

非简单任务使用 `claude/templates/TASK_TEMPLATE.md` 创建：

`claude/tasks/active/TASK-YYYYMMDD-NNN-简短名.md`

开始编辑前填写：

- 唯一任务 ID、Owner（AI/会话标识）、状态。
- 目标、验收条件和明确非目标。
- 允许修改的文件/目录和预计共享依赖。
- 当前检查点、验证结果、阻塞与下一步。

并行规则：

1. 方案阶段按功能边界、文件归属和关键状态的唯一管理职责主动拆分任务；只并行彼此独立、修改范围不重叠的任务。
2. 文件范围重叠时，后认领者不得直接修改；先拆分范围或完成交接。
3. 有依赖的任务必须在方案中写明依赖方向、接口/数据契约、先后顺序和集成验证点，不得伪装成可并行任务。
4. 每个 AI 只更新自己的任务卡；共享长期事实由完成任务的 AI 汇总写入 Memory MCP。
5. 任务卡不是长期记忆。完成后将有价值结论写入 progress/decisions/systemPatterns/daily，再把卡移入 `claude/tasks/archive/`。

### 功能实现门禁

每项功能按以下阶段推进，未经用户明确许可不得跳过实现授权：

**最小方案与规则冲突处理**：除平台安全限制外，项目规则是默认执行边界，不得机械理解为必须通过技术绕过来保留的产品约束。若规则、当前授权或所需人工操作阻碍最直接合理的方案，而 AI 正准备新增非平凡代码、资产、映射、脚本或流程来绕开，必须先暂停实施并向用户讲清楚：（1）发生冲突的规则或授权；（2）最直接方案以及需要用户执行的具体操作或许可；（3）直接方案与绕过方案各自的影响和风险。不得默认用户不愿操作；用户明确选择前不得落盘绕过方案。

1. **讨论方案**：说明目标、非目标、职责与关键状态的唯一管理者、C++/蓝图/数据边界、完整文件路径、并行拆分或依赖、风险和验收方式；讨论稿与中间产物只放 `claude/`。
2. **确定方案**：与用户确认方案，将已确认的当日实施范围写入 `DOC/DailyPlan/`；在对话中贴出本步拟新增或修改的代码，并标明尚未写入项目。
3. **授权实现**：只有用户明确允许后才能进入实现准备；此时仍不得先写功能代码或资产。
4. **完整基线提交并推送**：首次修改 C++、Blueprint、材质、关卡、配置或其他功能文件前，记录当前 HEAD 与 `git status --short`，把工作区全部已确认改动完整纳入一次 Git commit，记录新提交哈希，并确认提交后的 `git status --short` 为空。随后按 `GIT_INTERNAL.md` 核对 `origin` 精确为 `git@git.woa.com:shiqiqiwang/Demo.git`，将该提交 push 到当前获准的内部远端分支，并确认远端分支已包含该提交。不得只提交本任务文件、遗漏其他脏改动后继续实现。若存在未确认、归属不明、审计中或由其他任务持有且暂不能提交的修改，或 commit、push、远端提交核验任一步失败，立即暂停实现，与对应 Owner 和用户协调；在工作区形成完整且已备份到内部工蜂的基线前不得落盘功能。若基线 push 后、首次功能落盘前工作区再次出现修改，必须重新执行本门禁；若当前分支没有获准的内部远端分支，也必须先由用户完成分支协调。
5. **分步实现与验证**：基线提交完成后才可按已授权范围落盘。每一步坚持最小修改，形成可独立验证、可回退的检查点，不夹带无关重构；每个检查点记录改动、验证结果和回退边界。需要用户操作蓝图或编辑器时，在操作前说明执行时机、前置条件、逐步操作和预期结果；不得用模糊指令代替步骤。UE 编辑器的组件、面板和属性名称优先使用“中文名称（English/C++ Name）”双语标注，例如“偏航（Yaw）”“目标臂长（Target Arm Length）”，方便中文版 UE 定位。
6. **联合验收**：代码与蓝图/编辑器操作完成后一起运行验收场景并检查边界情况。AI 可标记“待用户验收”，只有用户确认验收通过后才能标记任务完成并归档。

讨论、代码预览和授权结论保留在对话中；任务卡只记录当前阶段、已授权范围、检查点、人工操作和验收状态，避免复制长篇上下文。

## 4. 交接

换 AI、换会话或主动暂停时，在 `claude/handoffs/` 创建交接文件。交接必须可执行，不复制整段聊天：

- 当前目标和完成度。
- 已修改文件与关键决定。
- 已运行的验证及结果。
- 未解决问题、风险、精确下一步。
- 接手前必须读取的最少文件。

接手者先核对文件和运行状态，再继续；不得假设交接内容仍然正确。

## 5. 日计划、日报与任务完成

`讨论方案（claude/） → 用户确认 → DailyPlan/代码预览 → 授权实现 → 完整基线 commit + 内部工蜂 push → 分步实现与验证 → 夜间 DailyReport`

- 讨论稿、比较方案和代码草稿只放 `claude/`。
- 用户确认后才创建 `DOC/DailyPlan/YYYY-MM-DD-主题.md`，只记录目标、范围、完整文件路径、步骤、验证和回退点。
- 用户授权后按 DailyPlan 分步实现；范围变化先讨论并更新计划。
- 夜间在 `DOC/DailyReport/` 记录实际完成、验证证据、遗留和下一步，不把计划写成成果。
- DailyPlan 和 DailyReport 均保持简短，不复制长篇对话；未获用户验收仍标记“待用户验收”。

当天发生实质工作时，在会话结束前向 `daily.md` 当天标题下追加一条简短记录：

- 完成了什么。
- 如何验证。
- 形成了什么决定。
- 留下什么问题及下一步。

功能完成后同步更新 `progress.md`；架构决定写 `decisions.md`；可复用做法写 `systemPatterns.md`；不要只写每日流水而漏掉权威状态。

`daily.md` 接近容量上限时，把较早月份压缩成月度摘要；热上下文不加载完整日报，只在追溯历史时搜索。

## 6. `claude/` 工作区与清理

| 目录 | 用途 | 保留策略 |
|---|---|---|
| `claude/tasks/active` | 活跃任务卡 | 任务期间 |
| `claude/tasks/archive` | 已完成任务卡 | 可定期清理 |
| `claude/handoffs` | 临时交接 | 接手确认后可归档/清理 |
| `claude/scripts` | AI 创建的辅助脚本 | 有复用价值才保留 |
| `claude/scratch` | 临时文本、试验和中间结果 | 默认可清理 |
| `claude/artifacts` | 临时报告、截图等产物 | 交付后可清理 |
| `claude/templates` | 任务与交接模板 | 长期保留 |

AI 可以清理自己在 `claude/` 内创建且已无用的文件。用户文件、项目源码、资产和来源不明的文件仍需先征得许可。

## 7. 上下文控制

- 启动时只读 `AGENTS.md`、当前任务和 activeContext。
- 按任务选择一个 Skill；不要预读全部 Skills、MCP 手册或历史日报。
- 长文档先搜索标题/关键词，再读取相关段落。
- activeContext 保持一页以内；完成或过期内容移出热上下文。
- 文档冲突时以真实代码/资产和最新验证为准，并修正文档。

## 8. 夜间无人值守模式

夜间自动任务只允许“只读审计 + 受控记忆维护 + AI 报告 + Git 快照”。

### 绝对红线

- 不得修改、删除、移动或重命名任何项目代码、蓝图资产、Content、Config、Source、Plugins、`.uproject`、Build.cs、项目规范和 AI 规则。
- 不得自动实施优化、修复编译错误、重构目录或调整资产配置。
- 不得执行清理工程、删除缓存以外的任何删除；即使文件看似无用也只报告，不处理。
- 只允许写入：Memory MCP 管理的记忆文件、`claude/artifacts/nightly/` 下的新报告，以及 Git 元数据。

### 每晚任务

1. 通过 Memory MCP 检查并精简热上下文；不删除历史，只压缩重复或失效内容。
2. 更新 `daily.md`：今日完成、验证、明日建议、未解决问题。
3. 将 AI 自己的经验压缩为最多三条；只有可复用且已验证的经验才进入 `systemPatterns.md`。
4. 只读检查代码和可通过 MCP 读取的蓝图/资产，输出按优先级排列的下一步建议。
5. 考虑三周工期：优先推荐新玩法内容、交付阻塞项和高回报改进；低价值重构放到“可延后”。
6. 对白天已有改动执行一次 Git commit 和 push；不得为了让提交成功而修改项目文件。推送目标为**内部工蜂**，详见 `DOC/AI_WORK_GUIDELINES/GIT_INTERNAL.md`。执行前须确认 `git remote get-url origin` 指向 `git@git.woa.com:shiqiqiwang/Demo.git`。
7. commit/push 失败时，在夜间报告和 daily 中记录准确原因，并在下一次用户会话首先提醒。

### 夜间报告

创建 `claude/artifacts/nightly/YYYY-MM-DD.md`，只包含：

- 今日完成与验证。
- Git commit/push 结果和提交哈希。
- 明日最优先任务。
- 新内容/玩法建议。
- 优化建议（阻塞交付、高回报、可延后）。
- 最多三条精炼 AI 经验。
